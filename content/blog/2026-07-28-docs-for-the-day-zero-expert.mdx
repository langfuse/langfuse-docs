The main reader of our docs has changed. "Developer" is now not just the engineer, but the engineer & an agent. This is also confirmed by other parties: [Mintlify's traffic data](https://www.mintlify.com/blog/state-of-ai) shows agents now send about half of all requests to documentation sites, and the share is still growing. Netlify's CEO coined a name for what this new reader experiences: [agent experience](https://biilmann.blog/articles/introducing-ax/), or AX.

Seeing this shift, we invested in a full agent surface for Langfuse. There isn't a clear set of “best practices” for this category yet, and we love reading about how other teams are approaching this. So we wrote down what we've seen and learned from experimenting with different approaches and observing how it shapes developer and agent behavior.

## 1. Make it as easy as possible for agents to fetch your docs

The upper ceiling of a coding agent's implementation quality is determined by the quality of your docs, so make it as easy as possible for agents to retrieve and parse your docs pages. You don't want agents skipping this and working from (possibly outdated) training knowledge.

At Langfuse we decided to do the following things to facilitate docs fetching:

- **We make every page available as raw markdown**, by appending `.md` to the URL or sending an `Accept: text/markdown` header: the same content without the HTML around it, so fewer tokens and less noise. This is a common pattern by now; [Cloudflare](https://developers.cloudflare.com/docs-for-agents/), [Stripe](https://docs.stripe.com/building-with-llms), and [Vercel](https://vercel.com/docs/agent-resources/markdown-access) serve their docs the same way, and [Mintlify](https://www.mintlify.com/docs/ai/llmstxt) does it for every site it hosts.
- **We provide an unauthenticated docs search endpoint**, `GET https://langfuse.com/api/search-docs?query=...`, which returns matching docs pages along with indexed GitHub issues and discussions.
- **We provide a docs search [MCP server](/docs/docs-mcp)** for the agents that are set up to use one.

## 2. Name things carefully, because agents guess

Agents regularly guess the name of an endpoint, a command, or a parameter because it sounds right.

An example from our own API: the v3 endpoint `GET /api/public/traces` is [deprecated](/faq/all/deprecated-api-migration), and in v4 users now need to call `GET /api/public/v2/observations`. An agent asked to fetch traces (which are sets of observations) often reaches for the endpoint with "traces" in the name, which leads to the deprecated one.

Small things like this also made us switch from an [auto-generated CLI based on the OpenAPI spec to a customizable one](https://github.com/langfuse/langfuse-cli/pull/13).

## 3. llms.txt: useful when fetched, often skipped

We shipped [llms.txt](https://langfuse.com/llms.txt), a plain-text index of every docs page. **But not every agent will fetch this, so don't rely on it exclusively.**

<Callout type="info">
  [Ahrefs measured](https://ahrefs.com/blog/llmstxt-study) that 97% of llms.txt
  files across 137,000 domains got zero requests in a month. On the other hand,
  [Mintlify's benchmark](https://mintlify.com/blog/llms-txt-agent-benchmark)
  showed a handed-over llms.txt cutting broken doc fetches from 2.23 to 0.11 per
  task.
</Callout>

### Beware of summarizing webfetch tools

In an effort to make the Langfuse skill more discoverable, we added a line to llms.txt to convince agents to install our skill. But when testing on Claude, this didn't work. This is because Claude's webfetch tool has another model summarize the fetched page against the question the agent is currently asking, and since the skill recommendation never answered the specific question, it never surfaced on the main Claude thread.

<AgentLlmsTxtFlow />

### When the llms.txt file gets too long

Some harnesses will only retrieve the first 200 lines of a web page by default, so be careful with making this file too long. An `llms.txt` file that acts as a router to specific docs pages will grow very fast. If we listed every feature docs page, integration page, and self-hosting documentation page with its link and description, this page would already be 292 lines long. This would cut off a portion of the integration links, and for an agent fetching the file, it would look like Langfuse just didn't have some of the integrations that were cut off. Each agent that leaned on the `llms.txt` file to navigate the Langfuse docs would miss the page they needed.

<TruncatedFetch />

We now keep the number of lines contained by only showing a comma-separated list of pages, and linking out to separate .txt pages with the actual links: [llms-docs.txt](https://langfuse.com/llms-docs.txt), [llms-integrations.txt](https://langfuse.com/llms-integrations.txt), and [llms-self-hosting.txt](https://langfuse.com/llms-self-hosting.txt). Every page title stays visible in one short fetch, and the agent follows a link when it needs the detail.

## 4. Docs are the source of truth, skills are for steering agent behavior

Sometimes, skills can be information dense. For devtools, where documentation often updates, you want to keep your skills as thin as possible, and keep all information exclusively in your docs. This is for 2 reasons:

- **Reach:** every agent can fetch docs, but not every agent will have the skill installed.
- **Freshness:** we can update docs any moment, but we cannot force-push skill updates to users who installed the skill in the past.

The Langfuse skill repo has this rule baked in for agents contributing to the skill:

What does stay in the skill is the judgment an agent doesn't get from reading a docs page: which approach fits the task at hand, which context to pull in before it starts building, and when to involve the human instead of deciding alone.

## 5. One god skill instead of many smaller ones

In February we [launched three Langfuse skills](/blog/2026-02-13-will-you-be-my-cli) and expected to add many more, building a big collection for our users. But we quickly reverted to one single Langfuse skill instead. **This is because of convenience for the user:** we don't want the user to have to anticipate what skills they might need in the future. When everything is packaged into one skill, the user installs it once, and the same skill can serve them along their entire Langfuse journey (implementation, debugging, starting with evals, ...).

**This pattern is perfectly doable because of the progressive disclosure feature of skills:** the main `SKILL.md` is 150 lines and does little more than state core principles and route to more specific, elaborate _reference files_. At the moment of writing, there are 14 reference files that cover specific workflows like instrumentation, prompt migration, or judge calibration, and are only loaded when relevant to the task at hand.

## 6. Test your skills

A skill is easy to generate and hard to get right, especially when it needs to work in many different scenarios with different models. That's why it's important to test the skill. We [evaluate new skill versions](/blog/2026-02-26-evaluate-ai-agent-skills) against a dataset of scenarios we expect the agent to encounter. While we will never be able to predict all scenarios, this gives us a good-enough proxy for us to decide to merge an update.

Next to that, we also set up a GitHub automation to review every skill PR against our main principles in the repo's [AGENTS.md](https://github.com/langfuse/skills/blob/main/AGENTS.md):

## 7. Give agents a way to talk back

The MCP server has a `submitFeedback` tool. This way, the agent can report to us directly when something wasn't clear or they are struggling. The report lands in our Slack, labeled as being about the skill, the CLI, the docs, or the API.

## 8. Docs still serve humans

Every change mentioned above in the end serves the reader doing the implementation. And although engineers might read less documentation now, because the agent executes the how, **engineers still review the agent's work and own the design decisions.**

So next to investing in making our how-to docs more agent-serving, we're investing in human-facing content too. We're adding more concept pages and introduced the [Langfuse Academy](/academy) to guide users through the whole process, so they are equipped to defend design decisions to their team, make well-informed trade-offs, and generally feel confident in the setup they're building.

<Frame fullWidth>
  ![Then, the developer handled both implementation and accountability. Now, the AI agent handles implementation while the developer remains accountable.](/images/blog/2026-07-28-docs-for-the-day-zero-expert/developer-agent-accountability.png)
</Frame>

While the focus on this type of content is partially because of increased capacity of the team, it's also becoming increasingly important for humans to have something to hold onto while their agents implement tools at record speed.

Back in June we [launched](/changelog/2026-06-19-langfuse-assistant-public-beta) Halo, the [Langfuse Assistant](/docs/langfuse-assistant). You can ask it to interpret your traces, build a dashboard or dataset, or help set up evals without leaving the Langfuse UI.

It's somewhat ironic: as a company focused on helping others build agents, we didn't have an in-ui agent of our own. We've invested into building the infrastructure and tools for agent integration such as the [Langfuse skill](/docs/api-and-data-platform/features/agent-skill), [MCP server](/docs/api-and-data-platform/features/mcp-server), and [CLI](/docs/api-and-data-platform/features/cli) for using Langfuse from agents like Claude Code or Cursor but now we wanted to bring those capabilities into Langfuse itself.

<Video src="https://static.langfuse.com/docs-videos/in-app-agent.mp4" />

When we first discussed whether we should write this post, I wasn't sure there was much to write about. The first version was simply a Mastra agent, an MCP server, and some code to glue them together. Nothing a tech company would consider worth writing a blog post about. There was no sandbox yet, we didn't invent a more efficient algorithm for agent execution and we didn't rewrite anything in Rust (although there might be some other posts here coming soon). Building the in-ui agent was mostly about integrating existing pieces and making them work smoothly together as well as creating the foundations for future agentic features.

From the start, we knew we wanted to reuse as much as possible and share the tools and instructions behind Halo with people using Langfuse through Claude Code or Codex. We didn't want a second set of things to maintain just for the in-product agent. If we improved a tool or fixed some guidance for Halo, that should help people using their own agents too. That meant building on our existing MCP server as well as bringing the shared Langfuse skill into the Assistant.

## How the Assistant is put together

The first step was expanding the [MCP server](/blog/2025-12-09-building-langfuse-mcp-server). The [May 29 release](/changelog/2026-05-29-mcp-update) added tools for observations, metrics, scores, comments, datasets, and annotation queues, making most Langfuse project data available to agents. We needed these tools for Halo, but they were also useful to anyone connecting their own agent.

Then in June we launched the first Beta version of the Assistant. A [Mastra](https://mastra.ai) agent that ran behind an HTTP endpoint, streaming responses to the browser. It handled one conversation at a time, with no parallel work or background execution. In early July we then gave it write access with human-in-the-loop approvals, and later that month added a sandbox. Background execution then got launched in August. We [announced all these capabilities together in September](/changelog/2026-09-03-langfuse-assistant).

Here's the architecture that we ended up with:

```mermaid
flowchart LR
  B[Browser]

  subgraph runs[Run management]
    W[Langfuse web]
    Q[(Redis queue)]
    P[(Postgres<br/>Run state + event log)]
    K[Langfuse worker<br/>Mastra agent loop]
    W -->|Save run| P
    W -->|Enqueue run ID| Q
    Q -->|Pick up run| K
    K -->|Save progress and results| P
    P -.->|Poll new events| W
  end

  subgraph tools[Model and tools]
    M[Claude on Bedrock]
    MCP[Langfuse MCP server<br/>Project-scoped data access]
    S[Optional Lambda MicroVM<br/>Files + scripts, no egress by default]
  end

  B -->|Start run or approve action| W
  W -.->|Stream saved events over SSE| B
  K <-->|Model calls| M
  K -->|Temporary project key + approved tools| MCP
  K -->|read, write, edit, bash| S
```

For the user, this means they can ask Halo to investigate something, close the tab, and come back to its progress and results. The worker keeps going independently of the browser, while the saved event log lets the UI catch up when they return. MCP tools let Halo work with their project data; the optional sandbox lets it process larger results with scripts instead of reading everything into the model's context. Neither gives it more access than the user has, and actions that change data still need approval.

## Reusing the MCP server and skill

As mentioned earlier, sharing as much as possible between the Langfuse Assistant and users interacting with Langfuse through tools such as Claude Code or Codex was a key design goal.

Halo uses our public MCP server, the same one you can connect to. Almost all customer-data access goes through it, though the system prompt also includes some generic information about the user, similar to what you'd see in a system prompt from Claude or ChatGPT. By relying on MCP and tools, we can control which tools the Assistant gets to call without having to secure arbitrary network requests.

For each run, the worker creates a temporary API key scoped to the project. By default, it can only call read-only MCP tools. We maintain our own mapping of tool permissions rather than trusting the MCP server's read-only annotations. We also filter tools by the signed-in user's role before exposing them to the model. If the user's role doesn't allow an action, the agent doesn't get the tool for it.

Tools that change data require approval. The worker adds the approved tool to an allowlist in the MCP request headers, then removes that permission before continuing the agent loop. Choosing **Always approve** saves the approval for that conversation. We still recheck it against the user's current role on each run, so an approval can't give the agent permissions the user doesn't have.

When an organization opts into [AI feature telemetry](/docs/langfuse-assistant#data-privacy-and-security), we can use traces of Assistant runs to see where it struggles. We also see people trying to break it. These attempts started as soon as we announced Halo and still turn up regularly. One example is asking it to download an executable from a link. With no web-fetch tool and no sandbox network access configured, it can't make that request.

This does limit what Halo can do. If it needs another way to access project data, we have to add an MCP tool first. I actually like that constraint, though, because the same tool is then available to people using their own agents.

We do the same with instructions. Halo's system prompt explains how to handle approvals, link to Langfuse pages, and keep answers short. For guidance on using Langfuse, such as setting up evals or migrating prompts, we load the open source [Langfuse skill](/docs/api-and-data-platform/features/agent-skill) as a Mastra skill. It's the same one you can install in Claude Code or Cursor.

When we see Halo struggle with a tool or give poor guidance, we want to fix the MCP tool or the shared skill. Maintaining a separate set of fixes just for Halo would defeat much of the point of sharing them.

## The agent does not run in a sandbox

We added the sandbox because we knew some tasks could be handled more efficiently by writing scripts to process data than by putting raw tool outputs into the model's context. But giving the agent bash and file system tools didn't mean the agent itself had to move into a sandbox. Ours runs in the same backend workers we already operate. When it needs to run a script or read a file, it calls a tool that accesses a separate sandbox.

Many conversations don't need a sandbox at all. Answering a docs question or looking up yesterday's traces might only take a few MCP calls. Starting a VM for those conversations would cost us memory and disk without helping the agent answer.

There's also self-hosting. Langfuse is open source, and I don't think setting up an external sandbox provider should be a requirement for using the Assistant. Without one, it still works with MCP tools.

The downside is that each sandbox operation has to cross that process boundary, adding latency. The separation isn't complete either: if a conversation already has a sandbox session, we check its state before running the agent.

The tools are `read`, `write`, `edit`, and `bash`, backed by an [AWS Lambda MicroVM](https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html) for each conversation. We create it when the agent first uses a sandbox tool. It runs as an unprivileged user, with no network egress configured by default. We configure it to suspend after 60 seconds idle and expire after four hours.

If the session has expired, the next sandbox operation creates a new one. Files the agent wrote are gone, and we tell it that. We can restore saved MCP results, though, which I'll get to below.

Without network access, scripts can't use the Langfuse SDK or CLI. That's a fairly large limitation, but they can still process data the agent fetched through MCP. Keeping data access there meant we could add the sandbox without also having to secure arbitrary network calls from scripts.

## Processing tool results with code

Say you ask the Assistant to group the errors in a few hundred failed observations. It could fetch them and put every response into the model's context, but that gets slow and expensive. Much of this work is just data processing. A script can group the errors and count them without the model having to read every observation.

To make that possible, we add an optional `silent` parameter to every MCP tool when a sandbox is available:

```ts
// Simplified: when a sandbox is available, every MCP tool gets an optional `silent` flag.
tool.execute = async ({ silent, ...input }, context) => {
  const result = await execute(input, context);
  persistToolCall({ toolName, toolCallId, result }); // stored with the run

  if (!silent || isError(result)) return result; // failures are never silenced
  return `Output available at /workspace/tool_calls/${toolName}_${toolCallId}.json`;
};
```

With `silent: true`, the model gets a file path instead of the full result. The worker saves the result outside the VM. Before the next sandbox operation, we write the saved calls into the sandbox as JSON files containing the request and response. This also lets us restore them if the sandbox expires. Fetching data silently doesn't itself start a VM.

In the example above, the agent could fetch observations in ten MCP calls, write a script to group the errors across those files, and read only the script's output. Failed tool calls still return their errors to the model, even with `silent: true`.

```mermaid
flowchart TD
  %% Example workflow: the agent chooses the script and what it prints.
  A[Agent fetches observations<br/>MCP calls with silent: true] --> B[Worker retains full results<br/>outside the sandbox]
  B -->|File-path messages enter model context| C[Agent calls write<br/>with a script to group errors]
  C --> D[Sandbox session created or reused<br/>Tool-call JSON files synchronized]
  D --> E[Script written to workspace]
  E --> F[Agent calls bash to run script<br/>Tool-call JSON files synchronized again]
  F -->|Script output enters model context| G[Agent answers with grouped errors]
```

We did reinvent part of what is often called programmatic tool calling, or code mode. Mastra released [Code Mode](https://mastra.ai/blog/introducing-code-mode) in June 2026, but didn't support it when we designed this. The difference is that with code mode, a script can make the tool calls itself. Our agent still makes the MCP calls and then writes code to process the results. If your framework doesn't support code mode, this is a fairly simple workaround.

## Background runs

When we added background execution, we wanted runs to continue when someone closed the browser, but didn't need to resume every interrupted model call or tool execution. For an interactive chat, we were comfortable showing a failure and letting the user retry. Writes make that decision less straightforward, though.

We already use [BullMQ](https://docs.bullmq.io), so we use it to deliver run IDs to workers. Postgres stores the run state. A worker claims a queued run and sends a heartbeat every five seconds. When someone reads or watches the conversation, we check that heartbeat. If it's more than a minute old, we consider the worker lost and mark the run as failed.

Waiting for approval doesn't tie up a worker. The run stops, and the user's decision creates a child run that continues from the saved conversation. An approval wait can therefore survive a restart, even though we don't checkpoint active execution.

The awkward case is a worker dying after an approved action completes but before it saves the result. The data may already have changed, even though the conversation doesn't show it. That's why we don't automatically retry failed runs. If we catch the failure, we can save a warning telling the user to check the action before retrying. If the worker disappears entirely, we can only show a generic interruption. In either case, we may not know whether the write completed.

If your runs take hours, cost a lot, or have side effects you can't check afterwards, I'd probably make a different choice and use a durable workflow engine.

## What's next

We're exploring giving sandbox scripts access to the Langfuse SDK and the project's configured LLM connections. Evaluator calibration is one possible use case: testing an evaluator against human-labeled examples, changing its prompt, and checking whether the results improve.

The part we'd need to work out is how to let scripts make those requests while keeping access limited to what the user is allowed to do and has approved. This is still exploration, not functionality available in Halo today.

The Assistant is live on [Langfuse Cloud](https://cloud.langfuse.com) and in public beta for [self-hosted deployments](/self-hosting/configuration/langfuse-assistant). If one of these decisions gets in your way, tell us in the [feedback discussion](https://github.com/orgs/langfuse/discussions/14196).

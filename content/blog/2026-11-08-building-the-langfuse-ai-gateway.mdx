Coding agents now send a large share of a team's LLM traffic, and teams want to know who uses which models, what it costs, and what the agents actually do. You can instrument your own application with an SDK, but you can't instrument Claude Code or Codex. What you can change is their base URL.

The [Langfuse AI Gateway](/docs/gateway/overview) is the place every one of those calls passes through. It holds the provider keys, routes each call to OpenAI or Anthropic, and records it in Langfuse, where you can analyze and evaluate it like any other trace.

We built it around three goals:

1. **Stable for operators.** It sits on every model call, so it has to be boring to run. That's why we use Rust.
2. **Stable for users.** An agent should behave the same with or without the gateway. That's why we don't translate between provider APIs, at least for now.
3. **Best-in-class tracing.** Every call should become a Langfuse trace with enough context to unlock observability and evaluation for coding agents and other callers.

For each goal, this post covers the decision it led to, why it matters, and what we gave up for it.

## Stable for operators: why we use Rust

If the gateway falls over, every agent in the company stops. So the first goal is that operators can run it without thinking about it: memory use they can predict, clean failures under overload, nothing to tune, and scaling by adding instances.

The workload makes that harder than it sounds. Coding-agent requests are large, often a few hundred kilobytes, because every turn resends the conversation, tool definitions and tool output. Responses stream for seconds or minutes. A gateway spends almost all of its time waiting, on the client's upload and on the provider, so what matters is what each waiting request costs, and what happens when too many arrive at once.

We wrote the gateway in Rust. Without a garbage collector, the memory a request holds is the memory we allocated for it, so we can count it. Async tasks are cheap, so thousands of open streams that are mostly waiting cost little. And we forbid panics in production code, so every error path is handled explicitly.

That lets us treat memory as a budget. The gateway sizes the budget from its container's memory limit, and each request reserves its share of it while it runs. When the budget is used up, the next request gets a 503 right away instead of waiting in a queue. A queue would hold memory for work it isn't doing and turn overload into latency for everyone. A 503 tells the client immediately, a load balancer can send the retry to another instance, and the provider SDKs that coding agents use already retry 503s with backoff. The budget bounds work, but it doesn't share capacity fairly between tenants, and under sustained overload, latency rises before requests are rejected. Responses stream straight through without being buffered, so a long response costs no more memory than a short one.

The gateway also keeps no state of its own. Keys, provider credentials and routing live in Langfuse Web, which the gateway asks for each request (cached in Redis). Traces are uploaded in the background, so responses never wait for them. There's no database and nothing on disk: scaling means adding instances.

To see whether this holds up, we ran the same workload through three gateways: ours in Rust, one in Node.js and one in Python. Each had 2 vCPU and 4 GiB, and each request was a ~500 KB streaming coding-agent turn.[^setup] The point was to see how each language and runtime behaves under pressure, not to rank products, and they don't do identical work per request.

Node.js forwarded requests about as fast as Rust at light load, but JavaScript runs on a single thread, so past a point every request waited for the same event loop.

What matters most to operators is what happens when a lot arrives at once. We sent five rounds of 1,000 simultaneous requests to each gateway and watched container memory over time:

Rust served all 5,000 requests in 8 seconds, and its memory peaked at 1.7 GiB. Node.js started dropping connections 12 seconds in; it served 97% and finished after 54 seconds. Python's memory rose until it hit the 4 GiB limit about 63 seconds in and stayed there. At about 150 seconds the kernel killed a worker for running out of memory, which cut off the streams on that worker, and the run took 227 seconds, with 64% of requests served.

None of this makes your agent feel faster on a quiet day: a model takes seconds to answer, and a few milliseconds of overhead disappear in that. It changes how many instances you run, and what happens on a busy day.

Rust has real costs, and we accepted them for this goal. Langfuse is mostly TypeScript, so fewer of our engineers and contributors can review or change the gateway, and we maintain one contract with Web in two languages. Builds are slower, there's no official provider SDK for Rust, and handling every error explicitly makes first versions slower to write. Statelessness has a price too: the lookup in Web is most of the gateway's added latency, and if Web is down, requests fail. And because traces upload in the background with a bounded buffer, a gateway under heavy load drops trace records rather than slowing requests. **We chose request latency over guaranteed trace delivery.**

## Stable for users: why we don't translate between providers

The second goal is that developers can adopt the gateway without noticing it. If a team mandates the gateway and someone's agent gets slightly worse, that person will route around it, and the observability is gone.

Coding agents are sensitive in ways ordinary chat apps aren't. They depend on provider-specific reasoning state, prompt caching, tool-call formats and error handling, and their vendors tune them against one specific API. Anything that changes what the agent sends or receives is a risk.

So the gateway speaks each provider's native API and doesn't convert between them. `/anthropic/v1/messages` is the Anthropic Messages API, and `/openai/v1/responses` and `/openai/v1/chat/completions` are OpenAI's. A request looks exactly like one sent to the provider; only the base URL and the key change. The gateway relays the provider's responses without rewriting them, and it changes the request in only two places: it maps the model ID to the provider's model name, and on streamed Chat Completions it asks for usage, so the call can be priced.

The alternative is a translating gateway: one format in, usually OpenAI's, converted to and from each provider's. That works for simple chat. But our goal is to support coding agents without breaking them or subtly changing how they behave, and translation struggles with exactly the features they rely on most. Anthropic's own [OpenAI SDK compatibility layer](https://docs.anthropic.com/en/api/openai-sdk) documents several of these gaps, and notes that "most unsupported fields are silently ignored rather than producing errors." Public bug reports in open-source translation gateways show the same pattern.[^issues]

- **Prompt caching** lets the provider reuse the conversation an agent resends every turn, which makes each turn much cheaper. The compatibility layer doesn't support it, and gateways have dropped cache markers, so you silently pay the full input price on every turn.
- **Extended thinking** lets the model carry its reasoning from one turn to the next. The compatibility layer doesn't return it, and gateways have dropped it on replay, so the agent gets weaker, behaves differently, or its next request fails.
- **Strict tool schemas** keep the model's tool calls in the shape the agent expects. The compatibility layer ignores them, and gateways have streamed tool calls with empty arguments, so you see broken calls, retries and loops.
- **Cache and reasoning usage** tells you how many tokens came from cache and went to reasoning, which decides the bill. The compatibility layer always leaves these empty, and gateways have dropped them, so your usage and cost numbers are wrong.
- **Errors and retries** tell the agent whether to wait or stop, and each provider encodes that differently. Gateways have turned overloads into generic errors and dropped `retry-after`, which sent a coding agent into an infinite retry loop.

None of this looks like an outage. It looks like a bigger bill, a slightly worse agent, or numbers you can't trust, and that's the hardest kind of problem to trace back to the gateway.

Staying native avoids that whole class of problem. Reasoning state survives, because signatures and encrypted reasoning pass through as the provider sent them. New provider features work on the day they ship, because new fields and beta headers pass through without the gateway knowing about them. Provider errors keep their status, body and headers, so an agent's retry logic works unchanged. Claude Code, Codex, OpenCode, Pi and GitHub Copilot need only a base URL and a key. The overhead is small, about 3 ms at the median and 10 ms at p99 for a 500 KB request.

The cost is that you can't switch providers by changing a model string, and there's no automatic fallback to another provider. For coding agents that's a small price: each one is built for one provider's API anyway, and they'd lose the most from a translation layer. If you build your own app on a small common set of features and want to swap models across providers from one client, a translating gateway is the better tool today. That's why we say "at least initially": fallbacks between providers are on our roadmap, and they'll have to meet the same bar, that an agent can't tell the gateway is there.

## Best-in-class tracing: unlocking Langfuse for coding agents

Routing calls is only half of why you'd run a gateway. The other half is knowing what happens on them: who spends what, what the agents do, and where they go wrong. Langfuse already answers those questions for applications you instrument yourself. The third goal is to bring the same depth to traffic you can't instrument, so that a coding agent's session is as easy to analyze as your own app.

Every call becomes a native Langfuse generation, so nothing about it is gateway-specific once it lands, and everything in Langfuse works on it. Attribution comes from the key, not the caller: a user key records its owner on every call, and callers can add context such as a session or tags, but can't overwrite who made the call. Admins choose per organization whether to capture full prompts and outputs or only usage, cost and latency. The more private option is the default.

The gateway also groups calls the way the agent thinks about them. A coding agent makes many model calls per user request, with tool execution in between. The gateway recognizes Claude Code, Codex, OpenCode and Pi, groups their calls into sessions, and, where the agent sends a turn ID, puts every call in one turn into a single trace. If a caller sends its own trace context, the gateway's calls nest inside the caller's trace, next to spans from the Langfuse SDKs or any OpenTelemetry instrumentation.

That unlocks the rest of the platform without extra setup:

- **Cost and tokens per user, key and model.** Per-developer spend needs no client configuration, because user keys already know who's calling. The [gateway analytics](/docs/gateway/features/analytics) page breaks spend down by user, key and model.
- **Sessions you can read.** A coding-agent session shows up as a [session](/docs/observability/features/sessions) with its turns, tool calls, cost and tokens, so you can follow what the agent did and where the time and money went.
- **Errors you can explain.** Every failed call records whether the client, the gateway, the network or the provider caused it, so dashboards and [alerts](/docs/observability/features/alerts) can watch for retry storms or a provider having a bad hour.
- **Evaluators that spot problems.** [Online evaluators](/docs/evaluation/get-started/online) run on gateway generations like on any other. A [code evaluator](/docs/evaluation/evaluation-methods/code-evaluators) can spot tool loops in a turn's history, an [LLM-as-a-judge](/docs/evaluation/evaluation-methods/llm-as-a-judge) can spot tasks that ran on a more expensive model than they needed, and the managed PII template spots personal data sent to a provider.
- **Data for improving your setup.** With full capture, real coding-agent prompts can go into [annotation queues](/docs/evaluation/evaluation-methods/annotation-queues) and [datasets](/docs/evaluation/experiments/datasets), and every trace is available through the [MCP server](/docs/api-and-data-platform/features/mcp-server) and [CLI](/docs/api-and-data-platform/features/cli).

The trade-offs here follow from staying out of the request path. Content-based checks like tool loops and PII need full capture, which stores prompts in Langfuse, so that's a choice we leave to the admin. Evaluators score one call at a time and run after it, so by the time a score flags a problem, the request has already reached the provider. And requests the gateway rejects itself, like a bad key or a full memory budget, never reach the provider and produce no trace.

## What's next

The benchmarks point to the first improvement: the lookup in Web is most of the gateway's added latency and its main external dependency, so we're looking at caching it inside the gateway. Beyond that, hard spend caps, fallbacks between providers, guardrails and PII redaction, more providers, and model routing are on the [roadmap](/docs/gateway/overview#roadmap). Each will have to meet the same three goals.

The gateway is in public beta on [Langfuse Cloud](https://cloud.langfuse.com), and you can [self-host it](/self-hosting/configuration/ai-gateway) next to your own Langfuse. If one of these decisions gets in your way, tell us in the [feedback discussion](https://github.com/orgs/langfuse/discussions/19686). The code is open source, in [`ai-gateway/`](https://github.com/langfuse/langfuse/tree/main/ai-gateway), and if you like working on this kind of problem, [we are hiring](/careers).

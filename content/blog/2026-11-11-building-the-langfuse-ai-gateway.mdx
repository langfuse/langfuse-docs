Coding agents now send a large share of a team's LLM traffic, and teams want to know what that costs per user and what the agents actually do. You can instrument your own application with an SDK, but instrumenting Claude Code or Codex requires clunky client-side hooks. Using a gateway unlocks seamless tracing by simply changing the base URL coding agents target.

The [Langfuse AI Gateway](/docs/gateway/overview) is the place every one of those calls passes through. It routes each call to OpenAI or Anthropic and soon more providers with your organization's provider keys, and records it in Langfuse, where you can analyze and evaluate it like any other trace.

Langfuse already has the analytics, evaluations and alerting to make sense of those calls. What was missing for coding agents was a reliable way to capture them, so we built the gateway. To pair with the rest of the platform, a gateway needs three things:

1. **Stable for operators.** It sits in the critical path of every model call, so it has to be reliable to run. That's why we use Rust.
2. **Stable for users.** An agent should behave the same with or without the gateway. That's why we don't translate between provider APIs, at least for now.
3. **Every call becomes a trace.** Each trace should carry enough context to unlock observability, evaluation, and other Langfuse platform features.

## Stable for operators: why we use Rust

If the gateway falls over, every agent in the company is blocked. So the first goal is that operators that are self-hosting the gateway can run it reliably: memory use they can predict, clean failures under overload, and predictable scaling by adding instances.

The workload makes that harder than it sounds. Coding-agent requests are large, often a few hundred kilobytes to even megabytes, because every turn resends the conversation, tool definitions, multimodal attachments, and tool output. Responses stream for seconds or minutes. A gateway spends almost all of its time waiting, on the client's request upload and on the provider, so what matters is what each waiting request costs, and what happens when too many arrive at once.

We've hit event-loop problems first-hand in our Node.js ingestion pipeline, and a gateway's large, long-lived requests amplify them, so we tackled the problem at the root. We wrote the gateway in Rust. Without a garbage collector, the memory a request holds is the memory we allocated for it, so we can reliably account for it. Async tasks are cheap, so thousands of open streams that are mostly waiting cost little. CPU-bound tasks such as serialization, encoding / decoding, and cryptographic work can be shared across threads.

That lets us treat memory as a budget. By default, the gateway sizes the budget from its container's memory limit, and operators can [set it explicitly](/self-hosting/configuration/ai-gateway#scaling) instead. Each request reserves its share of it while it runs. When the budget is used up, the next request gets a 503 right away instead of waiting in a queue. A queue would hold memory for work it isn't doing and turn overload into latency for everyone. A 503 tells the client immediately, a load balancer can send the retry to another instance, and the provider SDKs that agents use already retry 503s with backoff. Responses stream straight through without being buffered, so a long response costs no more memory than a short one.

The gateway also keeps no state of its own. Keys, provider credentials and routing live in Langfuse Web, which the gateway asks for each request (cached in Redis). Traces are uploaded in the background, so responses never wait for them. There's no direct database dependency and nothing on disk: scaling is straightforward by simply adding instances.

The control plane lives in the existing Langfuse Web container rather than in a new service. It reuses Web's authentication, roles and permissions, database and encrypted provider connections, so self-hosters run only the gateway itself, with no separate control-plane service next to it.

To see whether this holds up, we ran the same workload through three gateways: ours in Rust, one in Node.js and one in Python. Each had 2 vCPU and 4 GiB, and each request was a ~500 KB streaming coding-agent turn.[^setup] The point was a directional comparison of how each runtime behaves under load.

<Frame fullWidth>
  ![Added time to first token versus going direct, at 1 to 100 concurrent streams. Rust stays at about 3 ms, Node.js rises to 745 ms and Python to 1,920 ms](/images/blog/2026-11-11-building-the-langfuse-ai-gateway/ttft-under-load.png)
</Frame>

At 100 concurrent streams, Rust added 3 ms to the time to first token, Node.js about 745 ms and Python about 1,920 ms. The other two slowed down for different reasons. Python parses each request body into Python objects and counts the prompt tokens itself, so it runs out of CPU first. Node.js forwarded requests about as fast as Rust at light load, but JavaScript runs on a single thread, so past a point every request waited for the same event loop.

What matters most to operators is what happens when a lot of requests arrive at once during a burst. We sent five rounds of 1,000 simultaneous requests to each gateway and watched container memory over time:

<Frame fullWidth>
  ![Container memory over time during five rounds of 1,000 simultaneous requests. Rust peaks at 1.7 GiB and serves all 5,000 requests in 8 seconds. Node.js serves 97% and drops connections from 12 seconds in. Python fills the 4 GiB limit, has a worker killed for running out of memory, and serves 64%](/images/blog/2026-11-11-building-the-langfuse-ai-gateway/memory-under-load.png)

Rust served all 5,000 requests in 8 seconds, and its memory peaked at 1.7 GiB. Node.js started dropping connections 12 seconds in; it served 97% and finished after 54 seconds. Python's memory rose until it hit the 4 GiB limit about 63 seconds in and stayed there. At about 150 seconds the kernel killed a worker for running out of memory, which cut off the streams on that worker, and the run took 227 seconds, with 64% of requests served.

None of this makes your gateway user's agent feel faster on a regular traffic day: a model takes hundreds of milliseconds to seconds to answer, and a few milliseconds of overhead disappear in that. For operators that need to plan for bursty traffic, it changes how many instances they need to reliably run the gateway, and how predictably they can set that number.

## Stable for users: why we don't translate between providers

The second goal is that developers can adopt the gateway without noticing it. If a team mandates the gateway and someone's agent gets slightly worse, that person will route around it, and the observability is gone.

Coding agents depend on provider-specific features and are tuned against specific APIs, so anything that changes what they send or receive is a risk.

So the gateway speaks each provider's native API and doesn't convert between them. `/anthropic/v1/messages` is the Anthropic Messages API, and `/openai/v1/responses` and `/openai/v1/chat/completions` are OpenAI's. A request looks exactly like one sent to the provider; only the base URL and the authentication key change. The gateway relays the provider's responses without rewriting them, and it changes the request in only two places: it maps the model ID to the provider's model name, and on streamed Chat Completions it asks for usage, so the call can be priced.

The alternative is a translating gateway: one format is converted to and from each provider's. That is a real feature: running the Claude Code harness against OpenAI models, for example. That works for simple chat. But our goal is to support coding agents without breaking them or subtly changing how they behave, and translation struggles with exactly the features they rely on most. Anthropic's own [OpenAI SDK compatibility layer](https://docs.anthropic.com/en/api/openai-sdk) documents several of these gaps, and notes that "most unsupported fields are silently ignored rather than producing errors." Public bug reports in open-source translation gateways show the same pattern.[^issues]

- **Prompt caching** makes each turn cheaper, but providers cache differently, so a translator that gets it wrong silently bills the full input price.
- **Extended thinking** carries the model's reasoning between turns as provider-signed data that can't be converted, so losing it weakens the agent or breaks its next request.
- **Strict tool schemas** keep tool calls in the shape the agent expects, but not every format has one, so translated calls can arrive malformed.
- **Cache and reasoning usage** decides the bill, but providers report it differently, so flattening it makes your usage and cost numbers wrong.
- **Errors and retries** tell the agent whether to wait or stop, and mapping them onto one common set makes agents give up early or retry when asked to wait.

Staying native avoids this whole class of problem. New provider features usually work on the day they ship, because new fields and beta headers pass through without the gateway knowing about them. Provider errors keep their status, body and headers, so an agent's retry logic works unchanged. Claude Code, Codex, OpenCode, Pi and GitHub Copilot need only a base URL and a key.

The cost is that you can't switch providers by changing a model string, and there's no automatic fallback to another provider. For these tools that's a small price: they already speak each provider's native API, and agents like OpenCode and Pi ship a dedicated adapter per provider. People who want to switch between providers already use agents that support several, such as OpenCode, Pi or Paseo.

Skipping translation also lets us spend our time shipping real features instead of chasing format edge cases. If API schemas stabilize, we'll reconsider translation.

## Every call becomes a trace: unlocking Langfuse for coding agents

Langfuse already shows who spends what, what agents do and where they go wrong for applications you instrument yourself. The third goal is to bring the same depth to traffic you can't instrument, so that an agent's session is as easy to analyze as your own app.

Every call becomes a native Langfuse generation, so nothing about it is gateway-specific once it lands, and everything in Langfuse works on it. Attribution comes from the key, not the caller: a user key records its owner on every call, and callers can add context such as a session or tags, but can't overwrite who made the call. Admins choose per organization whether to capture full prompts and outputs or only usage, cost and latency. On self-hosted Langfuse, admins can also turn recording off, and the gateway then only routes calls. Admins also stay in control of access: people invited with the new AI Gateway role can call the gateway, manage their own keys and see their own usage, without getting access to the organization's projects.

The gateway also groups calls the way the agent thinks about them. An agent makes many model calls per user request, with tool execution in between. The gateway recognizes Claude Code, Codex, OpenCode and Pi, groups their calls into sessions (Pi needs [one setting](/integrations/developer-tools/pi-agent-gateway#add-the-providers) for this on the Anthropic route), and, where the agent sends a turn ID, puts every call in one turn into a single trace. If a caller sends its own trace context, the gateway's calls nest inside the caller's trace, next to spans from the Langfuse SDKs or any OpenTelemetry instrumentation.

That unlocks the rest of the platform without extra setup:

- **Cost and tokens per user, key and model.** Per-developer spend needs no client configuration, because user keys already know who's calling. The [gateway analytics](/docs/gateway/features/analytics) page breaks spend down by user, key and model.
- **Sessions you can read.** An agent's session shows up as a [session](/docs/observability/features/sessions) with its turns, tool calls, cost and tokens, so you can follow what the agent did and where the time and money went.
- **Errors you can explain.** Every failed call that produces a generation records whether the client, the gateway, the network or the provider caused it, so dashboards and [alerts](/docs/observability/features/alerts) can watch for retry storms or a provider having a bad hour.
- **Evaluators that spot problems.** [Online evaluators](/docs/evaluation/get-started/online) run on gateway generations like on any other. A [code evaluator](/docs/evaluation/evaluation-methods/code-evaluators) can spot tool loops in a turn's history, an [LLM-as-a-judge](/docs/evaluation/evaluation-methods/llm-as-a-judge) can spot tasks that ran on a more expensive model than they needed, and the managed PII template spots personal data sent to a provider.
- **Data for improving your setup.** With full capture, real agent prompts can go into [annotation queues](/docs/evaluation/evaluation-methods/annotation-queues) and [datasets](/docs/evaluation/experiments/datasets), and every trace is available through the [MCP server](/docs/api-and-data-platform/features/mcp-server) and [CLI](/docs/api-and-data-platform/features/cli).

## What's next

The gateway is in public beta on [Langfuse Cloud](https://cloud.langfuse.com), and you can [self-host it](/self-hosting/configuration/ai-gateway) next to your own Langfuse. If one of these decisions gets in your way, tell us in the [feedback discussion](https://github.com/orgs/langfuse/discussions/19686). The code is open source, in [`ai-gateway/`](https://github.com/langfuse/langfuse/tree/main/ai-gateway), and if you like working on this kind of problem, [we are hiring](/careers).

Every request was a ~500 KB streaming Chat Completions request (517,708 bytes, a long coding-agent turn) sent over TLS to the same mock OpenAI upstream. The latency chart shows added time to first token versus calling the mock directly (p50), with ~210 ms streams. The memory chart is one run of five rounds of 1,000 simultaneous requests, each round starting after the previous one finished. **Rust:** Tokio with axum, one process. It did API key auth through the control plane (cached in Redis) and sent a usage-only trace per request (model, parameters and token usage, no content). Its memory budget admits about 1,600 concurrent 500 KB requests and answers the rest with a fast 503. It has no rate limiting. **Node.js:** Node.js 20.19 with Hono, one process, its published image as shipped. The client sends the provider key itself, and it has no rate limiting, no persistent request logging and no admission control. It does the least work per request, so its numbers are a lower bound for a Node.js gateway doing the same work. **Python:** Python 3.13, FastAPI on Uvicorn with two worker processes, one per vCPU. It did API key auth against Postgres with a cache, sent an equivalent usage-only trace per request plus spend logs to Postgres, and had a per-worker in-flight cap sized to the same ~1,600 requests. Rate limiting was off in the measured runs; measured separately, it made no material difference. Its docs recommend 4 GiB per worker, so the shared 4 GiB limit contributed to its out-of-memory kill, though not to its latency, which was CPU-bound. Production coding-agent requests are about 290 KB at the median, which would narrow the Python gap, since its cost grows with body size.

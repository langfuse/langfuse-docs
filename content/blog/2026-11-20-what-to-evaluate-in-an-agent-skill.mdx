Once you have a harness that can run agents against a dataset, the harder question is content: **what should you actually measure?**

It is tempting to evaluate a skill the same way you evaluate a system prompt. But skills are not prompts, and skill evals are not prompt evals. Let's walk through what that means and how you should think about your skill eval setup.

## Why skill evals are not prompt evals [#why-skill-evals-are-not-prompt-evals]

Evaluating an agent skill differs from evaluating a prompt in two fundamental ways:

### 1. Progressive disclosure

Prompts are always immediately in an agent's context. A skill, on the other hand, uses a progressive disclosure mechanism: the agent starts off with only the skill's frontmatter in context. Only when the agent decides, based on this frontmatter, that it needs the skill will it load the main skill file into its context. Same for any sub-files of the skill.

This means that, unlike for prompts, you can't just blindly evaluate every agent execution assuming the agent was aware of the skill content.

<SkillContextDisclosureDiagram />

### 2. Agent behavior is (often) more complex

The decision to put something into a skill implies a decision not to put it in the system prompt. This is often done because the behavior of the agent is too complex or nuanced to put everything into one long string that's always completely in the agent's context.

Evaluating a skill therefore often means evaluating more complex behavior. This shifts the focus to a specific kind of evals.

## Separate skill routing from skill quality [#separate-routing-from-quality]

Before writing granular evaluators, you need to separate two questions that often get tangled together in a skill setup:

1. **Does the agent pick the right skill when left on its own?**
2. **Does the skill itself actually help when the agent uses it?**

This brings you to two things to test every time you edit your skill:

| Eval | Setup |
| --- | --- |
| **Skill routing** | All skills available (check the right skill is picked, with no interference) |
| **Skill quality (lift)** | `Forced skill` vs. baseline (`No skill` or previous version) |

## Evaluating skill selection & progressive disclosure (routing) [#evaluating-skill-selection-and-routing]

The mechanism here is straightforward: spin up agents in an environment with a prompt and check whether they read the skill you want, which is deterministic when you [link skills to traces](/docs/skill-management/tracing).

### 1. Skill-level triggering and coexistence

Before an agent ever reads `SKILL.md`, all it has to go on is the `name` and `description` in your frontmatter. Your first routing eval tests whether that frontmatter is clear enough for the agent to load your skill when it should, and leave it alone when it shouldn't.

**This gets harder as your skill library grows:** every new skill competes in the same routing decision, so adding one can silently pull triggers away from existing skills. Treating skill-level triggering as a regression suite gives you a fast signal to iterate your frontmatter against, both when tuning a single skill and when adding new ones alongside it.

### 2. Intra-skill routing (`SKILL.md` to reference files)

## Evaluating task outcomes & behavior (by use case) [#evaluating-task-outcomes-and-behavior]

Next, you need to grade whether the agent actually accomplished the user's goal. Because skills target multi-step work, text-similarity checks on the assistant's final message rarely suffice. Match your outcome evaluators to the type of behavior the skill governs.

Two details make behavioral outcome evals much more reliable in practice:

- **Score per constraint, not one monolithic score.** Instead of asking a judge for a single `0–100` quality rating, grade concrete sub-checks (`builds_cleanly`, `uses_production_label`, `links_prompt_to_trace`, `no_collateral_writes`) and roll them up. When a run fails, you immediately see *which* requirement broke.
- **Pick `pass@k` vs. `pass^k` based on user risk.** If your skill powers an interactive coding workflow with a test suite where the developer or agent can easily iterate once, `pass@k` (succeeding at least once in `k` attempts) reflects real value. If your skill governs an operational action—like migrating production resources, reviewing compliance, or placing an order—track `pass^k` (succeeding across *every* trial in `k` runs), because inconsistency breaks trust fast.

### Always compare against a baseline

- **Skills can produce negative lift.** In [SkillsBench](https://arxiv.org/abs/2602.12670), which evaluates 87 containerized tasks across 18 model-harness pairs with and without curated skills, skills raised average pass rates by +16.6 percentage points (from 33.9% to 50.5%), **but hurt performance on 13 of the 87 tasks** (by up to -7.4 pp). Negative lift happened when a skill prescribed an overly heavy workflow, pointed at a brittle tool, or overrode a stronger default strategy the model already knew.
- **Models outgrow capability-uplift skills.** [Anthropic distinguishes two types of skills](https://claude.com/resources/articles/improving-skill-creator-test-measure-and-refine-agent-skills): *capability uplift* skills (teaching techniques the base model struggles with) and *encoded preference* skills (sequencing your team's specific conventions or proprietary workflows). When a new frontier model drops and suddenly passes your `no-skill` baseline, a capability-uplift skill isn't broken; it is just dead weight you can retire. Teams operating large skill libraries, [like Fin AI](https://x.com/MrDHat/status/2123182107023601667), use continuous usage and baseline checks specifically to prune skills that models have outgrown or stopped triggering.
- **Lift depends on the harness, not just the model.** SkillsBench also found that the exact same model gets materially different lift depending on the coding harness (for example, Claude Opus 4.7 reached 61.2% with skills in Claude Code vs. 53.1% in OpenHands). If your skill is used across Claude Code, Codex, and Cursor, you need to measure lift per harness.

## Evaluating trajectory efficiency & cost [#evaluating-trajectory-efficiency-and-cost]

Even when an agent loads the right files and passes the task, the final verdict can hide severe friction inside the run. Strong frontier models are remarkably good at recovering from broken instructions: if a skill points to a renamed CLI flag or a stale URL, a capable model will hit an error, run `--help`, search around, and eventually succeed anyway.

Three trajectory metrics consistently earn their keep:

- **Tool and CLI error rate:** Count non-zero exit codes, `4xx` API responses, or failed tool spans per run. In our own CLI skill iterations, tracking CLI error rate caught a 25% hallucinated-flag rate and a `No server URL found` retry loop that hit 90% of runs—both fixed with two-line edits to `SKILL.md`.
- **Fallback and workaround rate:** Track when the agent abandons the path your skill recommends (for example, dropping from your SDK or CLI down to raw `curl` calls, or falling back to web search because a reference file lacked a concrete example).
- **Token cost, turns, and wall-clock time on passing runs:** As [Vercel notes in their agent eval guide](https://vercel.com/blog/agent-evals), **compute efficiency metrics on successful trials only**. Failed runs often look fast and cheap simply because the agent gave up after three steps. On passing runs, compare token usage against your `no-skill` baseline: a good skill often *reduces* total tokens on complex tasks (SkillsBench recorded drops like 1.77M to 1.09M tokens on Opus 4.7) because upfront procedural knowledge eliminates exploratory guesswork. If tokens spike without a matching jump in pass rate, your skill is injecting noise.

## How to sequence this without Goodharting yourself [#how-to-sequence-this]

Looking at routing, trajectory efficiency, and multi-constraint outcome graders together, it is easy to over-engineer your evaluation suite on day one—or worse, optimize against a flawed metric.

As we cover in [Choosing what to evaluate](/academy/evaluate/choosing-what-to-evaluate) and [AI is eating the AI engineering loop](/blog/2026-06-09-ai-is-eating-ai-engineering), your metric set should emerge from observed behavior rather than upfront guesswork:

1. **Read trajectories before writing judges.** Start by running 15 to 30 realistic prompts (explicit, implicit, and messy) through your sandboxed harness and reading the traces—either manually in Langfuse or by having a coding agent summarize failure patterns across the experiment run. Fix obvious one-line skill bugs directly instead of building permanent evaluators for typos.
2. **Separate routing checks from forced-skill baselines.** Test skill selection cheaply by stopping after the agent picks a skill, and measure skill quality by comparing a forced skill against a `no-skill` or previous-version baseline.
3. **Automate deterministic checks first.** Wire up trace-based routing evaluators (`SKILL.md` and `references/*.md` loads, including negative controls), tool/CLI error counts, and deterministic environment or build checks. They cost nothing to run and never hallucinate.
4. **Add targeted LLM-as-a-judge rubrics for stable qualitative criteria.** Once your workflow instructions settle, encode the remaining style, convention, and workflow-fidelity checks as narrow boolean rubrics—and keep a reminder to re-run your `no-skill` baseline whenever new frontier models ship so you know which parts of your skill you can delete.

Once you have a harness that can run agents against a dataset, the harder question is content: **what should you actually measure?**

It is tempting to evaluate a skill the same way you evaluate a system prompt. But skills are not prompts, and skill evals are not prompt evals. Let's walk through what that means and how you should think about your skill eval setup.

## Why skill evals are not prompt evals [#why-skill-evals-are-not-prompt-evals]

Evaluating an agent skill differs from evaluating a prompt in two fundamental ways:

### 1. Progressive disclosure

Prompts are always immediately in an agent's context. A skill, on the other hand, uses a progressive disclosure mechanism: the agent starts with only the frontmatter in context, and loads `SKILL.md` (and any reference files) only if it decides it needs them.

This means that, unlike for prompts, you can't just blindly evaluate every agent execution assuming the agent was aware of the skill content.

<SkillContextDisclosureDiagram />

### 2. Agent behavior is (often) more complex

The decision to put something into a skill implies a decision not to put it in the system prompt. This is often done because the behavior of the agent is too complex or nuanced to put everything into one long string that's always completely in the agent's context.

Evaluating a skill therefore often means evaluating more complex behavior. This shifts the focus to a specific kind of evals.

## Separate skill routing from skill quality [#separate-routing-from-quality]

Before writing granular evaluators, you need to separate two questions that often get tangled together in a skill setup:

1. **Does the agent pick the right skill when left on its own?**
2. **Does the skill itself actually help when the agent uses it?**

This brings you to two things to test every time you edit your skill:

| Eval | Setup |
| --- | --- |
| **Skill routing** | All skills available (check the right skill is picked, with no interference) |
| **Skill quality (lift)** | `Forced skill` vs. baseline (`No skill` or previous version) |

## Evaluating skill selection & progressive disclosure (routing) [#evaluating-skill-selection-and-routing]

The mechanism here is straightforward: spin up agents in an environment with a prompt and check whether they read the skill you want, which is deterministic when you [link skills to traces](/docs/skill-management/tracing).

### 1. Skill-level triggering and coexistence

Before an agent ever reads `SKILL.md`, all it has to go on is the `name` and `description` in your frontmatter. Your first routing eval tests whether that frontmatter is clear enough for the agent to load your skill when it should, and leave it alone when it shouldn't.

**This gets harder as your skill library grows:** every new skill competes in the same routing decision, so adding one can silently pull triggers away from existing skills. Treating skill-level triggering as a regression suite gives you a fast signal to iterate your frontmatter against, both when tuning a single skill and when adding new ones alongside it.

## Evaluating task outcomes (by use case) [#evaluating-task-outcomes-and-behavior]

Next, you need to grade whether the agent actually accomplished the user's goal. Because skills target multi-step work, the focus will likely be on outcome evaluators and trajectory evaluators, for example:

<Tabs items={["Coding", "CLI/API operations", "Encoded team workflows"]}>
<Tab>

- **Build passes (outcome):** Does the edited repo still compile without errors?
- **Tests pass (outcome):** Does the test suite still pass?
- **Expected code patterns (outcome):** Are the required SDK calls or imports present in the diff?
- **Clean workspace (outcome):** Is `git status` free of stray temporary files or artifacts?

</Tab>
<Tab>

- **No collateral writes (outcome):** Did the agent avoid unintended mutations (`collateral_writes == 0`)?
- **Tool adherence (trajectory):** Did the agent use the skill's CLI or SDK instead of ad-hoc workarounds?

</Tab>
<Tab>

- **Step order (trajectory):** Did the agent run required steps in order (such as a dry run before a destructive action)?
- **Structure (outcome):** Does the final artifact follow the team's expected format?

</Tab>
</Tabs>

### Score per constraint, not one monolithic score

Instead of asking a judge for a single `0–100` quality rating, grade concrete sub-checks (`builds_cleanly`, `uses_production_label`, `links_prompt_to_trace`, `no_collateral_writes`) and roll them up. When a run fails, you immediately see *which* requirement broke.

### Pick `pass@k` vs. `pass^k` based on user risk

If your skill powers an interactive workflow where the agent can easily iterate, the `pass@k` (succeeding at least once in `k` attempts) metric represents reality pretty well.

If your skill governs an operational action (e.g., migrating production resources, reviewing compliance, placing an order), you should use `pass^k` (succeeding across every trial in `k` runs).

## Evaluating trajectory efficiency & cost [#evaluating-trajectory-efficiency-and-cost]

Even when an agent succeeds at the task, the final verdict can hide severe friction inside the run. Strong frontier models are remarkably good at recovering from broken instructions.

### Tool error rate

Count non-zero exit codes, `4xx` API responses, or failed tool spans per run.

<Callout type="info">
  In our own CLI skill iterations, tracking CLI error rate caught a 25% hallucinated-flag rate and a `No server URL found` retry loop that hit 90% of runs—both fixed with two-line edits to `SKILL.md`.
</Callout>

### Workaround rate

Track when the agent abandons the path your skill recommends, for example:

- Dropping from your SDK or CLI down to raw `curl` calls
- Falling back to web search because a reference file lacked a concrete example

### Token cost, turns, and wall-clock time on passing runs

**For efficiency metrics, you need to make a distinction between successful and failed runs.** Failed runs often look fast and cheap simply because the agent gave up after three steps. A good skill often *reduces* total tokens on complex tasks because upfront procedural knowledge eliminates exploratory guesswork. If tokens spike without a matching jump in pass rate, your skill is injecting noise.

## How to sequence this without Goodharting yourself [#how-to-sequence-this]

Looking at routing, trajectory efficiency, and multi-constraint outcome graders together, it is easy to over-engineer your evaluation suite on day one—or worse, optimize against a flawed metric.

As covered in [Choosing what to evaluate](/academy/evaluate/choosing-what-to-evaluate) and [AI is eating the AI engineering loop](/blog/2026-06-09-ai-is-eating-ai-engineering), your metric set should emerge from observing your agent's traces:

1. **Start by reading traces.** You will learn a lot from just observing how your agent is behaving and form an opinion on how you'd prefer things to go in specific scenarios.
2. **Add routing evals first.** Everything else is noise if the skill never gets loaded.
3. **Layer in outcome and trajectory evals.** Keeping them separate prevents Goodharting a single composite score.
4. **Re-run your `no-skill` baseline when models upgrade.** Newer models absorb older skills, so you know what to drop.

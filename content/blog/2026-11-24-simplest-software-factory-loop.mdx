Most "software factory" setups are overengineered. You don't need a dark factory shipping features from scratch to get real leverage.

The highest-ROI version is much smaller: an **agent improver** (a loop that watches production, asks you when something looks off, and turns your feedback into PRs).

Every self-improvement loop only needs five things:

1. **Data to analyze:** production [traces](/docs/observability/get-started) of what your agent actually did.
2. **A take on what "good" is:** doesn't need to be a huge spec on day one.
3. **A way to tell if it is:** automated signals (errors, latency/cost spikes, [topics](/docs/observability/features/topics), [user feedback](/docs/observability/features/user-feedback)) and a way to inspect individual traces step by step when something looks off.
4. **A scheduled run to check on it:** a cron or routine that sweeps production daily.
5. **An agent that can act on it:** repo access to update its own context and open PRs.

Two things make this loop actually work (and stay simple):

## 1. Do error analysis over time. Calibrate taste daily [#calibrate-taste-daily]

Usually, you figure out what "good" looks like through [error analysis](/academy/monitoring/error-analysis): sitting down with a big batch of production traces, reading through them, and writing down every failure mode and rule upfront.

That works, and it's also understandable why most teams stall on it. Doing it all in one big pass is painful.

You can do error analysis over time instead, and figure out what you want to be true as real production cases show up. Start with hard signals (errors, latency/cost spikes, tool loops) plus an open-ended sample of recent traces. Then tell your bot one thing:

> "Whenever you're unsure whether a behavior is good or bad, bring me 2–3 examples to judge, and update your context daily with my feedback."

Signals narrow 10,000 runs down to 5. Clicking into those traces one by one (seeing the exact prompts, tool calls, and outputs) is how you judge gray areas in two minutes instead of guessing from aggregates.

- **If it's off?** You tell it why. It updates its written instructions so it doesn't flag the same thing tomorrow.
- **If it's right?** You greenlight the fix and it opens a PR.

Your taste compounds into written instructions automatically, one 2-minute review a day.

## 2. The richer your traces, the simpler your bot can stay [#richer-traces-simpler-bot]

A lot of people try to fix a blind bot by adding more prompts and sub-agents. Usually the leverage is on the data side instead.

The more your traces are enriched, the less guessing the bot has to do:

- **[Topics](/docs/observability/features/topics)** attached to traces let the bot spot what's trending across thousands of runs (new intents, sudden spikes, topics with higher error rates) instead of guessing from 10 random samples.
- **[Conversation signals](/blog/2026-09-23-catching-conversation-signals-in-langfuse) and [user feedback](/docs/observability/features/user-feedback)** (like user disagreement or thumbs-down) catch silent failures where nothing crashed: the answer was just frustrating.
- **[Releases](/docs/observability/features/releases-and-versioning), [sessions](/docs/observability/features/sessions), [prompt versions](/docs/prompt-management/features/link-to-traces), and clean tool I/O** let the bot trace a regression back to the exact change instead of hunting through the repo.

You don't need a heavier bot to get better PRs. Just richer traces.

## How to wire this up in 10 minutes (Langfuse + Grok Bot) [#setup]

This pattern works with any observability tool and scheduled coding agent. Here is the minimal setup using Langfuse and [Grok Bot](https://x.ai/news/grok-bot-1-0):

<Steps>

### Connect Langfuse and GitHub to Grok Bot

Open a Grok Bot chat and ask it to connect to your Langfuse project via API keys. It surfaces masked Secrets cards right in chat, with no config files to wrangle.

<Frame className="block max-w-xl mx-auto my-8">
  ![Grok Bot surfacing a masked Secrets card for Langfuse API keys right in chat](/images/blog/2026-11-24-simplest-software-factory-loop/grokbot-langfuse-secrets.png)
</Frame>

Ask it to install the [Langfuse skill](/docs/api-and-data-platform/features/agent-skill) so it queries traces, topics, and scores cleanly via the [Langfuse CLI](/docs/api-and-data-platform/features/cli):

```bash
npx skills add langfuse/skills --skill "langfuse"
```

Then connect GitHub (so it can branch and open PRs) and Slack (if you want daily digests in a channel).

### Drop a starter spec in your repo (`docs/agent-quality.md`)

Keep it tiny on day one and let it grow from your replies:

```markdown filename="docs/agent-quality.md"
# Agent Quality Spec (living doc)

> Updated daily from trace review feedback. Don't try to make this complete upfront. Let it grow from real production examples.

## What to sweep (last 24h)
- Telemetry anomalies: errors, latency spikes (e.g., p95 > 12s), token/cost spikes, or repeated identical tool calls
- Topics: new or spiking topics, unexpected user intents, or topics with higher error / escalation rates
- Conversation signals (optional): e.g., user disagreement, frustration, or thumbs-down feedback
- Open-ended sample: inspect 10–20 traces one by one (including runs with no errors) for silent misunderstandings, awkward handoffs, or wasted steps

## How to handle gray areas
- Whenever you're unsure whether a behavior is good or bad, pull 2–3 concrete trace links and ask me to judge them
- After I reply, fold my judgment into the rules below so future sweeps reflect it

## What good looks like (grown from past reviews)
- <!-- Example: Always check `get_policy` before answering policy questions -->
- <!-- Example: Ask a clarifying question instead of guessing when input is ambiguous -->
- <!-- Example: Escalate out-of-scope requests clearly instead of hallucinating -->

## Known non-issues (don't flag again)
- <!-- Add false alarms here after human review -->

## PR guardrails
- Never push directly to `main`: always open a PR for review
- Link the underlying production trace(s) in every PR description
- Never open a PR without explicit approval on the sweep finding
- (Optional) If a dataset/experiment command is configured (e.g., `npm run eval:run`), run it before opening the PR and include the before/after score delta
```

### Run one sweep and save it as a Skill

Paste this into Grok Bot, tweak the output once, and tell it to save the workflow as a skill:

```text filename="Prompt"
Every sweep, read docs/agent-quality.md (if it exists) and check the last 24h of Langfuse traces for:
  - errors, latency/cost spikes, and repeated tool calls
  - topics added to traces (new/spiking topics or topics with higher failure rates)
  - conversation signals / negative user feedback (if enabled)
  - a quick open-ended review of 10–20 sampled traces inspected one by one

Post a short digest and wait for my reply:
  1. Trending topics worth noticing
  2. Clear issues (max 3) with trace links, suspected root cause, and proposed fix
  3. Gray areas (2–3 examples) where you're unsure what "good" looks like, so I can judge them

Update docs/agent-quality.md (and your context) daily with my feedback. Only branch and open a PR once I approve a fix.
```

### Put it on a schedule

Tell Grok Bot:

> "Every weekday at 9:00 AM, run this sweep for the last 24 hours and post it here. Never open a PR without my ok."

Click **Test** once on the routine to verify it runs cleanly.

</Steps>

## Optional next step: add a dataset as your PR gate [#optional-dataset-pr-gate]

You don't need datasets or offline evals to start.

Once your daily sweeps surface recurring failure modes you never want to regress on, save those traces into a [Langfuse Dataset](/docs/evaluation/experiments/datasets) and have the bot run your [experiment script](/docs/evaluation/experiments/experiments-via-sdk) before opening a PR, attaching the before/after [score comparison](/docs/evaluation/experiments/compare-experiments) right in the PR description.

<Frame fullWidth className="w-full my-8">

</Frame>

Start with traces, a daily sweep, and 2–3 examples to judge. If you have good traces and signals, simplicity rules.

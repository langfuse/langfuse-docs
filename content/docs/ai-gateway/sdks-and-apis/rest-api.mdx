# REST API reference

<AiGatewayBetaCallout />

The gateway serves each provider's native API. Point your client's base URL at the gateway route for its format and use a gateway API key instead of the provider key. Request and response bodies are the provider's own: the gateway doesn't translate between formats, so an OpenAI request needs an OpenAI provider credential and an Anthropic request an Anthropic credential.

The examples use the `LANGFUSE_GATEWAY_HOST` and `LANGFUSE_GATEWAY_KEY` variables from [Send your first request](/docs/ai-gateway/get-started/first-request#export-the-key). For your region's host, see [gateway hosts](/docs/ai-gateway/get-started/first-request#gateway-hosts).

## Routes [#routes]

| Base URL                              | Endpoints                                                                   | Generation name           |
| ------------------------------------- | --------------------------------------------------------------------------- | ------------------------- |
| `$LANGFUSE_GATEWAY_HOST/openai/v1`    | `GET /models`, [`POST /responses`](#responses), `POST /responses/compact`   | `openai.responses`        |
| `$LANGFUSE_GATEWAY_HOST/openai/v1`    | [`POST /chat/completions`](#chat-completions)                               | `openai.chat-completions` |
| `$LANGFUSE_GATEWAY_HOST/anthropic/v1` | `GET /models`, [`POST /messages`](#messages), `POST /messages/count_tokens` | `anthropic.messages`      |

[Model listings](#list-models) and `count_tokens` are proxied but not recorded. Websockets, realtime APIs, and decision model APIs (OpenAI Decisions, TypeSafe System One) are not served. Other paths return `404`.

Every response carries a `langfuse-request-id` header, and recorded calls also return the trace and observation IDs. See [response headers](/docs/ai-gateway/features/tracing#response-headers). All [request headers](/docs/ai-gateway/features/tracing#request-headers) work on every route.

## Authentication [#authentication]

- The OpenAI routes read the gateway key only from `Authorization: Bearer <gateway key>`.
- The Anthropic route accepts the key as `Authorization: Bearer` or `x-api-key`. If you send both, they must have the same value.

## List models [#list-models]

Both routes serve a models endpoint that lists the models your key can call, in the provider's own response format. Use the returned `id` as the `model` of your requests. The IDs have the form `<credential>:<model>`, see [model IDs](/docs/ai-gateway/features/models#model-ids).

```sh
curl -s "$LANGFUSE_GATEWAY_HOST/openai/v1/models" \
  -H "Authorization: Bearer $LANGFUSE_GATEWAY_KEY"
```

```json
{
  "object": "list",
  "data": [
    {
      "id": "openai-prod:<model>",
      "object": "model",
      "created": 1767225600,
      "owned_by": "openai"
    }
  ]
}
```

```sh
curl -s "$LANGFUSE_GATEWAY_HOST/anthropic/v1/models" \
  -H "x-api-key: $LANGFUSE_GATEWAY_KEY"
```

```json
{
  "data": [
    {
      "type": "model",
      "id": "anthropic-prod:<model>",
      "display_name": "<display name>",
      "created_at": "2026-01-01T00:00:00Z"
    }
  ],
  "has_more": false,
  "first_id": "anthropic-prod:<model>",
  "last_id": "anthropic-prod:<model>"
}
```

- `/openai/v1/models` lists the models of OpenAI credentials, and `/anthropic/v1/models` the models of Anthropic credentials. Models an admin turned off are not listed.
- Both endpoints return every model in one response. Pagination parameters aren't needed, and `has_more` on the Anthropic route is always `false`.
- The response follows the provider's list models format: see the [OpenAI](https://developers.openai.com/api/reference/resources/models/methods/list) and [Anthropic](https://platform.claude.com/docs/en/api/models/list) references.

## Responses [#responses]

`POST /openai/v1/responses` serves the OpenAI Responses API, and `POST /openai/v1/responses/compact` compacts a conversation. Both use the request and response bodies documented in the [OpenAI Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create).

```sh
curl "$LANGFUSE_GATEWAY_HOST/openai/v1/responses" \
  -H "Authorization: Bearer $LANGFUSE_GATEWAY_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"<model-id>","input":"Say hello"}'
```

## Chat Completions [#chat-completions]

`POST /openai/v1/chat/completions` serves the OpenAI Chat Completions API. See the [OpenAI Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) for the request and response bodies. Any client that speaks Chat Completions, such as the [OpenAI SDK](/docs/ai-gateway/sdks-and-apis/openai-sdk) or frameworks built on it, works by changing the base URL and the API key.

```sh
curl "$LANGFUSE_GATEWAY_HOST/openai/v1/chat/completions" \
  -H "Authorization: Bearer $LANGFUSE_GATEWAY_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"<model-id>","messages":[{"role":"user","content":"Say hello"}]}'
```

### Streaming usage [#streaming-usage]

OpenAI only reports usage for a streamed Chat Completions request when the request sets `stream_options.include_usage`. So that every streamed call still gets token usage and cost, the gateway adds `"include_usage": true` to the request it sends upstream when a request has `"stream": true` and does not already set it.

- The recorded input and model parameters are your original request, without the added option.
- The response stream is relayed unchanged. Your client therefore receives OpenAI's final usage chunk even if it did not ask for usage: an extra event with an **empty `choices` array** and a `usage` object, just before `data: [DONE]`. The other chunks carry `"usage": null`.
- Requests that already ask for usage and non-streamed requests are forwarded without this change.

<Callout type="warning">
  Make sure your client tolerates a chunk without choices. The OpenAI SDKs pass
  it through like any other chunk, so code that reads `chunk.choices[0]` on
  every chunk needs a guard.
</Callout>

### What gets recorded [#chat-completions-recording]

- **Model parameters:** scalar parameters such as `temperature`, `top_p`, `max_tokens`, `max_completion_tokens`, `seed`, `reasoning_effort`, and `stream` are recorded in the `FULL` and `USAGE` [ingestion modes](/docs/ai-gateway/features/tracing#ingestion-modes). In `FULL` mode, `stop`, `response_format`, `tool_choice`, `stream_options`, and similar structured options are added.
- **Input** (`FULL` mode): `messages`, `tools`, legacy `functions`, and unknown fields.
- **Output** (`FULL` mode): the native `choices` list. Streamed choices are rebuilt from their deltas, including tool call arguments.
- **Metadata** (`FULL` mode): `metadata`, `prompt_cache_key`, `safety_identifier`, and `user` from the request are stored under `langfuse.gateway.client.request.*`, for example `langfuse.gateway.client.request.metadata`.
- Usage, cost, latency, and time to first token, as on the other routes.

## Messages [#messages]

`POST /anthropic/v1/messages` serves the Anthropic Messages API, and `POST /anthropic/v1/messages/count_tokens` counts the tokens of a message. See the Claude API references for [Messages](https://platform.claude.com/docs/en/api/messages/create) and [token counting](https://platform.claude.com/docs/en/api/messages/count_tokens).

```sh
curl "$LANGFUSE_GATEWAY_HOST/anthropic/v1/messages" \
  -H "x-api-key: $LANGFUSE_GATEWAY_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"model":"<model-id>","max_tokens":1024,"messages":[{"role":"user","content":"Say hello"}]}'
```

## Compressed requests [#compressed-requests]

The gateway only accepts uncompressed request bodies. A request with a `Content-Encoding` header other than `identity` is rejected with `415` `Unsupported request Content-Encoding`. Turn off request compression in your client.

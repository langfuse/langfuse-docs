# Evaluation Overview

Evals give you a repeatable check of your LLM application's behavior. You replace guesswork with data, and catch regressions before you ship a change.

Evaluation runs across most of the [AI engineering loop](/academy/ai-engineering-loop): you score live traces in production, turn interesting examples into datasets, run experiments to compare changes, and judge the results with manual or automated evaluators. It happens both **online**, on live production traces, and **offline**, before you ship a change.

## Getting Started

Start with [Evaluate an existing application](/docs/evaluation/get-started/existing-application): run your application on fixed test cases, reuse deterministic checks, [compare changes](/docs/evaluation/experiments/compare-experiments), and [block regressions in CI](/docs/evaluation/experiments/experiments-ci-cd). The Python and TypeScript examples run without model-provider calls.

You can evaluate both:

- [live incoming traces](/docs/evaluation/get-started/online) to measure quality on production data and track trends over time.
- [results from running tests on a pre-defined dataset](/docs/evaluation/get-started/offline), to make sure your changes are ready for production.

For more information on how evaluators, scores, datasets, and experiments fit together, read [Core Concepts](/docs/evaluation/core-concepts).

To catch regressions before they ship, run experiments in CI: add the [`langfuse/experiment-action`](/docs/evaluation/experiments/experiments-ci-cd) GitHub Action to a `pull_request` workflow and raise `RegressionError` from your experiment script when a score violates your threshold; the action then fails the job. It works with Langfuse Cloud and self-hosted Langfuse.

## Choose where evaluations run [#where-evaluations-run]

| Approach                                                                       | Execution and setup                                                                                                                                                               |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing Python or TypeScript graders                                          | Run in your application or CI process. The SDK sends experiment inputs, outputs, and scores to Langfuse. No managed code evaluator dispatcher is required.                        |
| [Managed Code Evaluators](/docs/evaluation/evaluation-methods/code-evaluators) | Langfuse executes your checks. Self-hosted deployments require a configured dispatcher.                                                                                           |
| [LLM-as-a-Judge](/docs/evaluation/evaluation-methods/llm-as-a-judge)           | Use a model for checks that need semantic judgment. Configure a model connection for managed evaluators, or provider credentials in your own process for SDK evaluator functions. |

Use [Langfuse Cloud](/cloud) for hosted storage and reporting, or [self-host Langfuse](/self-hosting) to operate the platform yourself. Both accept experiments from your own runner. Model-based evaluations send data to the model endpoint you configure. If that endpoint is an external provider, those requests leave your environment even when Langfuse is self-hosted. Deterministic graders require no model-provider calls, but Langfuse storage and infrastructure still have their own [pricing](/pricing) and operational requirements.

For a small suite that only needs a local pass/fail result, existing tests may be sufficient. Add Langfuse when you need shared experiment history, comparison, or review. A local dataset is a data source for an experiment, not a promise of offline-only storage.

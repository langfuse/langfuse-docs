# Status

Traces can have many [observations](/docs/observability/data-model#observations-traces-and-sessions). Use an observation's **status** to highlight errors and warnings and focus on the relevant parts of a trace. Available statuses are `DEBUG`, `DEFAULT`, `WARNING`, and `ERROR`.

The API accepts `status` and returns it alongside the equivalent `level` field. Existing `level` fields remain supported. When both fields are supplied with non-null values, `status` takes precedence. The SDK examples below continue to use the supported `level` parameter to set the status.

You can also include a `statusMessage` to provide additional context.

<Tab>
When using the [`@observe()` decorator](/docs/sdk/python/decorators):

```python
from langfuse import observe, get_client

@observe()
def my_function():
    langfuse = get_client()

    # ... processing logic ...
    # Update the current observation with a warning status
    langfuse.update_current_span(
        level="WARNING",
        status_message="This is a warning"
    )
```

When creating [observations](/docs/observability/data-model#observations-traces-and-sessions) directly:

```python
from langfuse import get_client

langfuse = get_client()

# Using context managers (recommended)
with langfuse.start_as_current_observation(as_type="span", name="my-operation") as span:
    # Set status and status message on creation
    with span.start_as_current_observation(
        name="potentially-risky-operation",
        level="WARNING",
        status_message="Operation may fail"
    ) as risky_span:
        # ... do work ...

        # Or update status and status message later
        risky_span.update(
            level="ERROR",
            status_message="Operation failed with unexpected input"
        )

# You can also update the currently active observation without a direct reference
with langfuse.start_as_current_observation(as_type="span", name="another-operation"):
    # ... some processing ...
    langfuse.update_current_span(
        level="DEBUG",
        status_message="Processing intermediate results"
    )
```

Status can also be set when creating generations:

```python
langfuse = get_client()

with langfuse.start_as_current_observation(
    as_type="generation",
    name="llm-call",
    model="gpt-4o",
    level="DEFAULT"  # Default status
) as generation:
    # ... make LLM call ...

    if error_detected:
        generation.update(
            level="ERROR",
            status_message="Model returned malformed output"
        )
```

<Tab title="JS/TS SDK">

When using the context manager:

```ts
import { startActiveObservation, startObservation } from "@langfuse/tracing";

await startActiveObservation("context-manager", async (span) => {
  span.update({
    input: { query: "What is the capital of France?" },
  });

  updateActiveObservation({
    level: "WARNING",
    statusMessage: "This is a warning",
  });
});
```

When using the `observe` wrapper:

```ts
import { observe, updateActiveObservation } from "@langfuse/tracing";

// An existing function
async function fetchData(source: string) {
  updateActiveObservation({
    level: "WARNING",
    statusMessage: "This is a warning",
  });

  // ... logic to fetch data
  return { data: `some data from ${source}` };
}

// Wrap the function to trace it
const tracedFetchData = observe(fetchData, {
  name: "observe-wrapper",
});

const result = await tracedFetchData("API");
```

When creating observations manually:

```ts
import { startObservation } from "@langfuse/tracing";

const span = startObservation("manual-observation", {
  input: { query: "What is the capital of France?" },
});

span.update({
  level: "WARNING",
  statusMessage: "This is a warning",
});

span.update({ output: "Paris" }).end();
```

See [JS/TS SDK docs](/docs/sdk/typescript/guide) for more details.

## How statuses are stored and mapped [#status-mapping]

`status` and its compatibility field `level` use the four strings `DEBUG`, `DEFAULT`, `WARNING`, and `ERROR`. There is no numeric encoding: the Observations API, table exports, trace JSON downloads, and filters use these exact strings. [Scheduled blob-storage exports](/docs/api-and-data-platform/features/export-to-blob-storage#export-field-groups) retain the `level` field. You can filter by `status` or `level` in the [Observations API](/docs/api-and-data-platform/features/public-api#observations-filters). Observations ingested without either field have status `DEFAULT`.

When you send spans through the [OpenTelemetry endpoint](/integrations/native/opentelemetry), Langfuse derives the status in this order:

1. A recognized `langfuse.observation.status` span attribute, falling back to the compatibility attribute `langfuse.observation.level` when status is absent or unrecognized. Matching is case-insensitive and accepts common aliases: `TRACE` and `VERBOSE` map to `DEBUG`; `INFO`, `LOG`, `NOTICE`, `OK`, and `SUCCESS` map to `DEFAULT`; `WARN` maps to `WARNING`; `FATAL` and `CRITICAL` map to `ERROR`. Unknown values are ignored. If neither attribute has a recognized value, Langfuse uses the next rule.
2. Otherwise, a span whose OpenTelemetry status code is `ERROR` becomes `ERROR`.
3. Otherwise, `DEFAULT`.

`statusMessage` is taken from the `langfuse.observation.status_message` attribute, falling back to the span's OpenTelemetry status message. OpenTelemetry log-record severity fields (`SeverityNumber`, `SeverityText`) are not read; set the span attribute when you need a status other than `DEFAULT` or `ERROR`.

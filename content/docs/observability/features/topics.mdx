# Topics

Topics groups similar traces into clusters to easily discover patterns in your trace data. See what users ask for, how interactions go, and where your application struggles without having to look at all of your traces by hand.

## How Topics works and what it is [#how-it-works]

A **facet** is a question you want to answer about each trace. Topics summarizes each trace for the selected facets, embeds those summaries, and groups similar summaries into named topics.

| Facet     | Question                                         |
| --------- | ------------------------------------------------ |
| Intent    | What is the user trying to do?                   |
| Sentiment | How does the user feel about the interaction?    |
| Outcome   | What was delivered, and is the result confirmed? |
| Issues    | What problems affected the final result?         |

```text
Describe what the user, or the calling application, wanted from this run as a whole.

Format: an imperative verb phrase stating the goal, such as "Find…", "Fix…", "Summarize…".

- Describe the goal of the whole run, not its last step. Follow-up requests to verify, save, show, fix, or reformat earlier work belong to the goal they serve.
- A run can contain several unrelated requests, for example a user who finishes one job and then starts another. Name each of them in a few words, in the order they were asked, joined with "and". Describing only the latest request misses the earlier ones.
- Earlier conversation can clarify the goals of this run but does not add goals of its own.
- In an automated run with no human author (extraction, classification, routing, templated generation), describe the job the input sets. Do not invent a person asking for it.
- When the user asks the assistant to work on supplied material, describe that work and name the material's subject in a few words.
- Keep the user's own verb and object. "Fix the date filter in a SQL query" must not become "Improve a data workflow".
- Describe goals only. Leave out how the assistant approached them, what went wrong, and whether they succeeded.
- Social or casual messages have a goal too; state it plainly.

Status: applicable whenever a goal can be identified, even if the run failed or produced nothing. insufficient_input when no request or input survives. Do not use not_applicable.

Examples:
- Export last quarter's orders to CSV grouped by region.
- Classify an inbound support email by product area and urgency.
- Fix a failing nightly data import and draft a welcome email for new customers.
- Chat about plans for the weekend.
```

</Tab>

<Tab>

```text
Describe how the end user felt about the responses they got, from an assistant, agent or application, and how they expressed it. Do not describe what the conversation was about.

Format: "<Label>: user <expression> <target>." with Label one of Negative, Positive, Mixed, Neutral.

Decide in this order, looking at what the end user wrote in this run, above all their last message:
1. Negative if the user shows dissatisfaction with the assistant, even calmly or in a few words: says its answer or fix is wrong or did not work ("still failing", "it gives a compile error", "not this"), corrects or overrides what it did ("no, I meant …", "do not do that"), repeats or tightens an earlier instruction, objects to how it answered ("too long, just say yes or no"), asks why it did something unexpected, or shows frustration, distrust, or giving up.
2. Positive if the user approves the result ("perfect", "cool", "looks good", "good work"), shows relief or warmth, or thanks the assistant in a message that is mainly thanks ("thanks", "thank you and good night"). Approval stays Positive when a new request follows.
3. Mixed if both 1 and 2 hold and both matter.
4. Otherwise Neutral: requests, first instructions even when terse or strict, answers to the assistant's questions, factual questions, and a "thanks" that only opens the next request ("Thanks. Next, …").

- Only text the end user wrote counts as a signal. Assistant, tool, and system text shows what the user reacts to.
- A calm report of a problem the assistant did not cause, such as a bug the user brings in or a personal hardship, is not negative by itself.
- Expression, pick the closest. Negative: reported that … failed, corrected, repeated an instruction after, objected to, complained about, questioned, gave up on. Positive: approved, praised, thanked the assistant for, was relieved by. Mixed: one Positive and one Negative expression joined by "but".
- Target, pick the closest: a wrong or unsupported answer, a fix or action that did not work, an ignored instruction, an unwanted action, the answer's length or format, slow or repeated attempts, the result, the help overall.
- Never name the task's subject, domain, product, code, files, data, people, or the user's circumstances. Those belong to other facets.
- For Neutral, name only the kind of message (a procedural request, an answer to a question, a factual question), not its subject, so that neutral runs read alike.

Status: not_applicable when the run has no end-user text, as in automated pipelines. insufficient_input when user text exists but is unreadable.

Examples:
- Negative: user reported that a fix failed again.
- Negative: user objected to an unwanted action.
- Negative: user repeated an instruction the assistant ignored.
- Positive: user approved the result.
- Mixed: user praised the result but corrected a wrong answer.
- Neutral: user gave a procedural request.
```

</Tab>

<Tab>

```text
Describe where this run ended: what was delivered or done, and whether the transcript confirms it.

Format: "<State>: <the concrete result>", where State is one of:
- Completed: the requested answer was given, or a tool result confirms the requested action.
- Partial: part of the request was delivered and part was not.
- Unconfirmed: the assistant says an action happened, but no result confirms it.
- Needs input: the run ends waiting on the user, such as a clarifying question or an approval.
- Not completed: the run stopped, was blocked, or was declined without delivering the request.

- Start from the end of this run: the last assistant message and the last tool results decide the state.
- Base the state on results, not on the assistant's words. A tool result confirms an action; a message saying "done" does not. A returned draft is a delivered draft, not a sent message.
- For questions, explanations, and analyses, the delivered answer is the result.
- Name the concrete deliverable or stopping point, not just the state. Mention remaining work only when the transcript shows it.
- Say where the run stopped, not why something failed, unless the reason is itself the result, as with a declined request.

Status: applicable whenever the run has a final response or result, including failures. insufficient_input when no response or result survives. Do not use not_applicable.

Examples:
- Completed: returned a SQL query that filters orders by signup month.
- Unconfirmed: said the meeting was booked, but no calendar tool result confirms it.
- Needs input: asked which of two accounts the transfer should come from.
- Not completed: stopped after the payments tool failed, without answering the user.
```

</Tab>

<Tab>

```text
Describe the problem that did the most damage to the result of this run: the mistake that made the final answer or action wrong, unsupported, or missing.

Format: one sentence that names the mistake, the kind of step where it happened, and its consequence, for example "Answered from memory instead of querying the dataset, so the reported value is unverified."
- Describe the mechanism in plain, generic words: what the assistant did wrong and how, such as answering from memory, inventing data, claiming a check that never ran, choosing the wrong tool, breaking a required format, or stopping before the answer. Use the words that fit this run.
- Name the kind of step (a web search, a file read, a calculation, a code change, the final answer), not the task's subject. "Skipped the file read and guessed the count" is right; "gave a wrong count of crustacean slides" is not.
- Do not start with a label or category.

How to find it:
- Start from the end. Check the final answer or action against the request: is it on target, complete, and backed by what the run actually retrieved or did? Then work back to the step that caused the gap.
- Report the cause with its consequence, not the symptom. When a tool fails and the assistant then answers anyway from guesses or invented data, the problem is the unsupported answer, not the tool failure.
- When several problems occur, report the one with the biggest effect on the result. Prefer, in this order: an answer or reported result that is wrong or not backed by the run; a task left unfinished or answered off target; a wrong tool, approach, or argument; a broken instruction or format; a tool failure that blocked the result. A problem the assistant fully recovered from counts only when nothing worse happened.
- Keep the symptoms of one problem together; do not list separate problems.

Before you return not_applicable, check these four points. Return not_applicable only when all of them hold:
1. When the request depends on data, files, tools, or current facts that the run had to look up, every such fact, number, or result in the final answer comes from a tool result or user input in this run, not from memory or assumption. General knowledge, explanations, and writing do not need a lookup.
2. Every tool call used a tool suited to its input, such as a file tool on a local file rather than a web address, with valid arguments.
3. The run followed the output format, tags, and steps that the system prompt or the assistant's own plan required.
4. The final answer addresses exactly what was asked: the right quantity, unit, entity, and scope.

- Only problems in this run count. An error the user pastes for explanation, a problem in earlier conversation, or a complaint about something outside the run is not an issue here.
- A clarifying question, a justified refusal, a short answer, and a retry that succeeds are not issues.
- Check the end of this run before calling it unfinished: if a later assistant message delivers an answer or fallback, the run is finished.
- Report only what the transcript shows directly. A run-specific fact that needed a lookup but has none is shown directly. A problem that is only a possibility is not.

Status: not_applicable when the run is complete enough to judge and shows no problem. insufficient_input when too much is missing to judge, for example only the first request survives.

Examples:
- Answered from a made-up example after the data file could not be read, so the reported result is invented.
- Reported the total instead of the requested minimum, so the answer misses the question.
- Searched the web for figures the attached spreadsheet contained, so the answer used outdated data.
- Every inventory lookup timed out, so no quote could be produced and the user was asked to retry later.
```

A **live map** follows a filtered set of traces over time. A **snapshot** analyzes a chosen time window once. Use separate maps for different applications or workflows so unrelated traffic does not dominate the results. Topics are discovered from your data; you do not need to define categories beforehand.

## Get started [#get-started]

The project setup is the same on Langfuse Cloud and self-hosted deployments. Self-hosted administrators should first check the [Topics infrastructure configuration](/self-hosting/configuration/topics).

<Callout type="warning">
  Topics sends observation content (input and output) to
  the summary model configured in your LLM connections. Embedding and grouping models receive generated summaries. Apply [masking](/docs/observability/features/masking) before ingestion if content must
  not reach those providers. Summarization does not guarantee anonymization.
</Callout>

<Steps>

<Step>

### Connect your models

Add an [LLM connection](/docs/administration/llm-connection) under **Settings > LLM Connections**, or use an existing project or inherited organization connection. Open [Topics](https://cloud.langfuse.com/project/~/topics), choose **Set up topics**, then select your facets and models:

- **Summaries**: a fast, cost-efficient text model that analyzes each trace.
- **Embeddings**: an embedding model that represents the summaries for similarity comparisons. Only embeddings of a single model are comparable, therefore keep this consistent ideally.
- **Grouping**: a text model that names and describes the discovered groups. A stronger model can produce clearer topic names.

<Callout type="info">
  Members, Admins, and Owners can configure Topics; Viewers can explore results.
  Adding an LLM connection requires an Admin or Owner.
</Callout>

</Step>

<Step>

### Select your traces

Choose filters and a sampling rate. Start with one workflow and a small sample if you want to check relevance and provider costs before analyzing more traffic.

<Callout type="info">
  Topics needs recorded model conversations: capture generation observations with
  inputs and outputs. A trace containing only a root span's input and output is
  not enough. Follow the [tracing guide](/docs/observability/get-started) if your
  model calls are not recorded yet.
</Callout>

</Step>

<Step>

### Start a live map

Review the selection and start processing. Setup reuses existing summaries and summarizes recent matching traces to build the first topics. The live map then analyzes new matching traces automatically.

Follow setup progress on the Topics page. Open a topic once results appear to check that its traces match the pattern you expected.

</Step>

</Steps>

## Live maps and snapshots [#maps-and-snapshots]

Open the map picker to create a **New live map** or **New snapshot**.

| Type     | Behavior                                                                                      |
| -------- | --------------------------------------------------------------------------------------------- |
| Live map | Analyzes new matching traces and updates topics daily from up to 30 days of recent summaries. |
| Snapshot | Groups traces from a selected time window once, without changing live maps.                   |

Live maps wait for a trace to become idle before analyzing it. The default is five minutes after the last event; adjust **Trace readiness** in **Topics > ⋮ > Settings** for long-running workflows.

Use **Edit map** to change filters, facets, or sampling. Turn off **Live updates** to pause a map while retaining its results. **Refresh map** in the map picker rebuilds its topics on demand.

Snapshots can reuse existing summaries or **Summarize more traces** first. Choose the time window, filters, and facets; when summarizing more traces, choose a random sample or the latest matching traces. This lets you investigate traffic that your live maps have not processed.

<Callout type="info">
  A snapshot needs at least 10 applicable summarized traces per selected facet.
  Small samples can produce broad topics. Counts describe the analyzed subset,
  not all project traffic.
</Callout>

## Explore your topics [#explore]

Select a live map or snapshot and a facet. Use **Treemap** to see the largest topics or **Scatter** to explore similar traces spatially. Select a topic to read its description and summaries, then open a trace to inspect the conversation and model calls.

Within each map, a trace can belong to one topic per facet. **Unassigned** includes traces that do not fit a discovered topic, are awaiting an update, or lack enough applicable content.

Treat topics as starting points for investigation. Similar conversations can have different outcomes, and a generated label may not describe every trace in a group. Review examples before turning a pattern into an evaluation or product decision (see the [Error Analysis chapter](/academy/monitoring/error-analysis) in the Academy).

<Callout type="info">
  The scatter plot represents the traces used in the last grouping. New traces
  can appear in topic trace lists before the next update adds them to the map.
  Topic groups and names can change when topics are rebuilt.
</Callout>

## Models and costs [#models-and-costs]

Your provider charges for summarization, embeddings, and topic naming. Reduce processing costs with narrower filters, a lower sampling rate, or a less expensive summary model.

<Callout type="info">
  **Summaries and embeddings** in History shows estimated per-run costs where
  pricing is available. The estimate excludes topic naming and failed calls, and can change
  when summaries are replaced or deleted. Use your provider's billing for the total
  cost.
</Callout>

<Callout type="warning">
  The embedding model and dimensions are shared across the project and cannot
  change once summaries have been embedded. Choose them before starting,
  because embeddings from different models cannot be compared.
</Callout>

## Access results via API [#api]

Use the read-only [Topics API](https://api.reference.langfuse.com/#tag/unstabletopics) to retrieve current live-map topics, summaries, and assignments for your own analyses.

<Callout type="info">
  These endpoints use the `/api/public/unstable` namespace and may change between
  releases.
</Callout>

## Paused processing

If Topics pauses because of a provider or billing error, resolve the error, then select **Turn back on** in the Topics banner and save. Updating model settings alone does not resume processing.

# Version Control

In Langfuse, version control & deployment of prompts and skills is managed via `versions` and `labels`.

## Implementation

### Versions & Labels [#versions--labels]

Each prompt or skill version is automatically assigned a `version ID`. Additionally, you can assign `labels` to follow your own versioning scheme.

Labels can be used to assign prompts and skills to environments (staging, production), tenants (tenant-1, tenant-2), or experiments (prod-a, prod-b).

Use the Python SDK to assign labels to a prompt when creating a new prompt version.

```python {5}
langfuse.create_prompt(
    name="movie-critic",
    type="text",
    prompt="As a {{criticlevel}} movie critic, do you like {{movie}}?",
    labels=["production"],  # add the label "production" to the prompt version
)
```

Alternatively, you can also update the labels of an existing prompt version using the Python SDK:

```python {5}
langfuse = Langfuse()
langfuse.update_prompt(
    name="movie-critic",
    version=1,
    new_labels=["john", "doe"], # assign these labels to the prompt version
)
```

```ts {5}
import { LangfuseClient } from "@langfuse/client";

const langfuse = new LangfuseClient();
```

```ts {5}
await langfuse.prompt.update({
  name: "movie-critic",
  version: 1,

```

#### Publish a skill version [#publish-a-version]

Publish a new version when a skill's instructions or supporting files change. Use labels to control which version your agents receive. Check the [file and path limits](/faq/all/skill-management-limits-and-troubleshooting#limits) before uploading.

<Tabs items={["UI", "CLI", "API"]}>
<Tab>

To update an existing skill:

1. Open **[Skills](https://cloud.langfuse.com/project/~/skills)** and select the version to start from.
2. Click **Edit** to create a local draft.
3. Edit `SKILL.md` or its supporting files, then click **Publish**.
4. Review the file changes, add an optional version note, and confirm with **Create version**.

Saved versions are read-only. Keep the same frontmatter `name` to add a version to the existing skill. Changing it to an unused name creates a separate skill starting at version 1.

To import existing skills, open **New skill → Import skills → Upload**. Upload files, folders, or ZIPs containing `SKILL.md`, review the detected skills, and select those to import. Changed skills create a new version; unchanged skills show **Already up to date**. Importing leaves existing `production` labels unchanged.

</Tab>
<Tab>

[Configure project credentials](/docs/skill-management/get-started#get-api-keys) and install the CLI, then push the skill folder:

```bash
langfuse skills push ./skill_name --label staging
```

The folder must contain a root `SKILL.md`. The CLI creates a version unless the files match the latest saved version, in which case it reuses it. The command assigns `staging` to the resulting version.

</Tab>
<Tab>

Send every file the new version should contain to `POST /api/public/skills`. Omitting a file removes it from the new version; earlier versions stay unchanged. Langfuse reads the name and description from the frontmatter in `SKILL.md`:

```bash
curl --request POST "$LANGFUSE_BASE_URL/api/public/skills" \
  --user "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "files": [{
      "path": "SKILL.md",
      "content": "---\nname: skill_name\ndescription: Describe when to use this skill.\n---\nInstructions for the agent."
    }],
    "commitMessage": "Update skill instructions"
  }'
```

Use the version number in the response to [assign a label](#labels). Publishing assigns `latest`; assign `staging` or `production` separately. To reuse file content already stored in the project, provide its `sha256Hash` instead of `content`. See the [Skills API reference](https://api.reference.langfuse.com/#tag/skills).

</Tab>

## Fetching by Label or Version

When fetching prompts or skills to use them in your application you can either do so by fetching a specific version or label.

<LangTabs items={["Prompts", "Skills"]}>
<Tab>

Here are code examples for fetching prompts by label or version.

**To "deploy" a prompt version**, you have to assign the label `production` or any environment label you created to that prompt version.

Some notes on fetching prompts:

- The `latest` label points to the most recently created version.
- When using a prompt without specifying a label, Langfuse will serve the version with the `production` label.
- If no version carries the requested label, the request fails with `404 Not Found`. Langfuse never silently falls back to `production` or `latest`; see [how label resolution works](#label-resolution).

<Tabs items={["Python SDK", "JS/TS SDK"]}>
<Tab>

```python
from langfuse import get_client

# Initialize Langfuse client
langfuse = get_client()

# Get specific version
prompt = langfuse.get_prompt("movie-critic", version=1)

# Get specific label
prompt = langfuse.get_prompt("movie-critic", label="staging")

# Get latest prompt version. The 'latest' label is automatically maintained by Langfuse.
prompt = langfuse.get_prompt("movie-critic", label="latest")
```

</Tab>

<Tab>

```ts
import { LangfuseClient } from "@langfuse/client";

const langfuse = new LangfuseClient();

// Get specific version of a prompt (here version 1)
const prompt = await langfuse.prompt.get("movie-critic", {
  version: 1,
});

// Get specific label
const prompt = await langfuse.prompt.get("movie-critic", {
  label: "staging",
});

// Get latest prompt version. The 'latest' label is automatically maintained by Langfuse.
const prompt = await langfuse.prompt.get("movie-critic", {
  label: "latest",
});
```

</Tab>

</Tabs>

</Tab>

Install skill files with the CLI or fetch a skill manifest through the API. You can select a label or pin an exact version.

**To "deploy" a skill version**, assign the label `production` or any environment label you created to that skill version.

Some notes on fetching skills:

- The `latest` label points to the most recently created version.
- When fetching a skill without specifying a label or version, Langfuse will serve the version with the `production` label.
- If no version carries the requested label, the request fails with `404 Not Found`. Langfuse never silently falls back to `production` or `latest`; see [how label resolution works](#label-resolution).

<Tabs items={["CLI", "API"]}>
<Tab>

Install the version labeled `staging`, or pin version `2`:

```bash
langfuse skills install skill_name --label staging
langfuse skills install skill_name --version 2
```

Run `langfuse skills update` to fetch the versions currently assigned to saved labels. Exact version pins stay fixed.

</Tab>
<Tab>

Fetch the version labeled `staging`:

```bash
curl --get "$LANGFUSE_BASE_URL/api/public/skills/skill_name" \
  --user "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
  --data-urlencode "label=staging"
```

For a fixed version, replace `label=staging` with `version=2`. See [Load Skills](/docs/skill-management/load-skills) for SDK examples and file retrieval.

</Tab>

### How label resolution works [#label-resolution]

<LangTabs items={["Prompts", "Skills"]}>
<Tab>

The SDKs fetch prompts from `GET /api/public/v2/prompts/{name}`, so these rules apply whether you call the API directly or use `get_prompt` / `prompt.get`:

| You pass                      | Langfuse returns                                                                                                            |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Neither `label` nor `version` | The version labeled `production`. If no version has that label, the request fails with `404`.                               |
| `label="staging"`             | The version that currently carries `staging`. If no version does, `404` — there is no fallback to `production` or `latest`. |
| `version=3`                   | Version 3, regardless of its labels.                                                                                        |
| Both `label` and `version`    | A `400` error: the two are mutually exclusive.                                                                              |

Because a missing label is an error rather than a fallback, a typo in a label name or an environment whose label was never assigned surfaces immediately as a failed fetch, not as the wrong prompt being served. The SDKs handle this with a [fallback prompt](/docs/prompt-management/features/guaranteed-availability) if you configure one; otherwise the error propagates to your code.

To check which labels exist without fetching a specific version, list prompts: `GET /api/public/v2/prompts` returns every prompt with its `labels` array, and `GET /api/public/v2/prompts?label=staging` returns only prompts that have a version carrying that label. Labels are also visible on the prompt's version table in the UI.

</Tab>
<Tab>

The CLI and SDKs fetch skill manifests from `GET /api/public/skills/{name}`, so these rules apply whether you call the API directly or use a Langfuse client:

| You pass                      | Langfuse returns                                                                                                            |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Neither `label` nor `version` | The version labeled `production`. If no version has that label, the request fails with `404`.                               |
| `label="staging"`             | The version that currently carries `staging`. If no version does, `404` — there is no fallback to `production` or `latest`. |
| `version=3`                   | Version 3, regardless of its labels.                                                                                        |
| Both `label` and `version`    | A `400` error: the two are mutually exclusive.                                                                              |

Because a missing label is an error rather than a fallback, a typo in a label name or an environment whose label was never assigned surfaces immediately as a failed fetch, not as the wrong skill being served.

Labels are visible in the skill's version history in the UI. For CLI installations, moving a label does not change installed files until you run `langfuse skills update`. An exact version pin remains fixed.

</Tab>
</LangTabs>

## Operational workflows

### Rollbacks [#labels]

<LangTabs items={["Prompts", "Skills"]}>
<Tab>

When a prompt has a `production` label, then that version will be served by default in the SDKs. You can quickly rollback to a previous version by setting the `production` label to that previous version in the Langfuse UI.

</Tab>
<Tab>

Move `production` to the version you want agents to fetch. Move it to an earlier version to roll back. Requests pinned to an exact version are unaffected.

In the UI, select a version, open **Labels**, select `production`, and click **Save and promote to production**. For the API, replace `2` below with the version you want to promote:

```bash
curl --request PATCH \
  "$LANGFUSE_BASE_URL/api/public/skills/skill_name/versions/2" \
  --user "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
  --header "Content-Type: application/json" \
  --data '{"labels":["production"]}'
```

The request replaces this version's user-managed labels. Include every label it should retain. Assigning a label moves it from any other version of the same skill. Langfuse manages `latest` automatically.

Publishing version 2 leaves `production` on version 1 until you move the label. API clients receive the change on their next manifest request; refresh any application cache to pick it up. For CLI installations, run `langfuse skills update`.

</Tab>
</LangTabs>

### Protected prompt labels [#protected-prompt-labels]

<AvailabilityBanner
  availability={{
    hobby: "not-available",
    core: "not-available",
    pro: "team-add-on",
    enterprise: "full",
    selfHosted: "ee",
  }}
/>

Protected prompt labels give project admins and owners ([RBAC docs](/docs/rbac)) the ability to prevent labels from being modified or deleted, ensuring better control over prompt deployment.

Once a label such as `production` is marked as protected:

- `viewer` and `member` roles cannot modify or delete the label from prompts, preventing changes to the `production` prompt version. This also blocks the deletion of the prompt.
- `admin` and `owner` roles can still modify or delete the label, effectively changing the `production` prompt version.

Admins and owners can update a label's protection status in the project settings.

### Tags [#tags]

Tags apply to a prompt or skill across all versions.

<LangTabs items={["Prompts", "Skills"]}>
<Tab>

Edit **Tags** in the prompt header to organize and filter related prompts.

</Tab>
<Tab>

Edit **Tags** in the skill header or set them through the API:

```bash
curl --request PATCH "$LANGFUSE_BASE_URL/api/public/skills/skill_name" \
  --user "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
  --header "Content-Type: application/json" \
  --data '{"tags":["tag"]}'
```

This replaces the skill's tag list. Include every tag you want to retain. You can then [install all skills with a tag](/docs/skill-management/load-skills#cli-install).

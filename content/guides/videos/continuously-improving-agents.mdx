# Continuously Improving Agents With Langfuse

An agent can look perfectly healthy from the outside while giving bad answers. Requests return 200, latency is normal, there are no exceptions, and the user still did not get the help they needed. Because agents are nondeterministic, knowing that your software runs tells you very little about whether its responses are any good.

In this workshop from AI Engineer, Lotte Verheyden and Annabell Schäfer build the online half of the improvement loop with a small sample app called **Specs, the Dad IT support agent**. You will see what a useful trace looks like, how to decide what is worth monitoring for your application, how to wire up evaluators that read exactly the parts of a trace they need, and how a coding agent can dig through production traces to find problems nobody set up a score for.

This video is a good fit if you already have an agent in production (or close to it) and want a practical way to catch the conversations that go wrong. You can follow along step by step with the free [Langfuse workshop](/workshop).

## The AI engineering loop: online and offline [#ai-engineering-loop]

The workshop frames improvement as a loop with two parts:

- **Online:** you trace your application in production and monitor those traces with dashboards, evaluators, and user feedback.
- **Offline:** you build datasets of test cases, run experiments on proposed changes, and evaluate the results before you deploy.

For getting started, teams outside high-risk industries can get very far with the online part alone. Find a problem during monitoring, make a simple fix, deploy, and watch the next traces come in. Once your product matures, or when any mistake has serious consequences, add the offline part for structured testing. Your datasets will be heavily inspired by what you saw during monitoring, and you only ship a change once experiments show it is better and introduces no regressions.

This video focuses on the online part.

## Build traces that are worth monitoring [#useful-traces]

Everything starts with the trace. If your trace is missing information, monitoring misses things, your datasets end up weaker, and you make less informed decisions about what to evaluate. So it pays to take the time to get tracing right.

A trace is made of **observations**: the steps your agent takes to produce an answer. These are LLM calls, tool calls, and other steps, and they can be nested so the tree mirrors how your agent actually ran.

What you record depends on the type of observation:

- **LLM calls:** duration, token usage, cost, the model, and the prompt version. Anything that helps you judge the quality of that call.
- **Tool calls:** whatever is relevant to the operation. For a web search, for example, the query that was used.

Cost, latency, and tokens are captured per observation and rolled up to the trace level. See [Get started with tracing](/docs/observability/get-started) to set this up, or ask your coding agent to do it with the [Langfuse Agent Skill](/docs/api-and-data-platform/features/agent-skill).

## Three jobs of monitoring [#monitoring]

Monitoring does a few things at once:

1. **Aggregate metrics.** Cost, latency, and evaluator scores become trends you watch over time, so you notice if quality starts to drop. See [metrics and dashboards](/docs/metrics/overview).
2. **Signal detection through user feedback.** As traffic grows you cannot read every trace. [User feedback](/docs/observability/features/user-feedback) surfaces the ones worth looking at right now.
3. **Feedback and evals.** Automatic evaluators scale to all your traces, but they mostly catch problems you already thought of. User feedback and human annotation scale less well, and they are where you discover the things you never anticipated. Use both.

## Meet Specs, the Dad IT support agent [#meet-specs]

Specs started as a side project for a dad who kept asking on WhatsApp how to set up his phone, his printer, and his computer. In the workshop it has a small web UI.

Specs is a TypeScript app built on the OpenAI Agents SDK. It uses the OpenAI API to generate replies and has two tools:

- `get_support_context` to look up Dad's phone, operating system, and installed apps
- `search_help_library` to search a set of frequently asked questions with guidance on common issues

To run it yourself, follow the [setup lesson](/workshop/learner/00-setup): clone the [langfuse-workshop repository](https://github.com/langfuse/langfuse-workshop), copy `.env.example` to `.env`, create a Langfuse account (a project is created for you) and add your API keys, install dependencies, and start the app with `npm run dev`.

Ask a question like "How do I turn on my Bluetooth on my iPhone?" and a trace shows up in Langfuse. It is rooted in an **agent** observation, with **generations** and **tool calls** nested underneath. The sample app comes fully instrumented, so the workshop can focus on working with traces instead of setting them up.

## Choose signals that fit your application [#choose-signals]

Monitoring starts with a question: what can go wrong in this specific app? You do not sit next to Dad while he uses Specs, so you want the traces to tell you when something went wrong. For a support agent, the workshop picks two signals to start with:

- **User disagreement.** Dad asks how to turn on Bluetooth, then replies "Where's the button?" That usually means the instructions were unclear or not detailed enough.
- **All-caps frustration.** When people get frustrated with a chat app, they often start typing in all caps.

These are examples. Do not just copy them. It often makes sense to [check out the specific failure modes for your application](/academy/evaluate/choosing-what-to-evaluate). In chat-like applications, [conversation signals](/academy/monitoring/capturing-signals#conversation-signals) are generally a good starting point for monitoring how people interact with your application.

To follow along, switch to the monitoring checkpoint with `git checkout checkpoint/04-monitoring` and open the [monitoring lesson](/workshop/learner/04-monitoring).

## Evaluators for Specs [#evaluators]

Langfuse offers three kinds of evaluators:

- **[Code evaluators](/docs/evaluation/evaluation-methods/code-evaluators)** handle deterministic checks. You write a Python or TypeScript function, and the same input returns the same score every time.
- **[LLM-as-a-judge](/docs/evaluation/evaluation-methods/llm-as-a-judge)** evaluators handle the more implicit things you want to get out of a conversation. A model scores the trace and can explain the grade.
- **[Decision model evaluators](/docs/evaluation/evaluation-methods/decision-models)** ask a typed question and write the answer as a score: a label, a level on a rubric, or a yes or no. Use them when the possible answers are known before you call the model.

This workshop covers the first two. To set one up, connect an evaluator model, choose the observations to target, and point the evaluator at the parts of the observation JSON that should be in context. The [evaluator setup](/docs/evaluation/evaluation-methods/llm-as-a-judge#set-up-step-by-step) walks through that in the UI.

These are the three the workshop sets up for Specs, and why each one is built that way:

- **User disagreement** needs judgment, so it is an LLM judge on the **agent** observation. It reads the user's side of the conversation.
- **All-caps frustration** is a concrete text check, so it is a code evaluator. A short Python function returns `true` when the user message is written in all caps.
- **Out-of-scope requests** need the system prompt as well as the latest user message, so this one targets **generation** observations, where that prompt is available. Specs is scoped to phone support, and Dad also asks about a printer and a computer.

They run on live observations. Scores attach to the observation, so you can filter for disagreement or all-caps frustration and bring those conversations to the top of your review queue. The same evaluators can also run later on experiments.

## Let a coding agent investigate your traces [#coding-agent]

Next, the workshop seeds a batch of example production traces and scores into the project with a script from the monitoring lesson. Now there are pages of traces. How do you find what is going wrong at that scale?

Install the [Langfuse CLI](/docs/api-and-data-platform/features/cli) and the [Langfuse Agent Skill](/docs/api-and-data-platform/features/agent-skill). Asking your coding agent to install them is enough. The CLI exposes the Langfuse API, so your coding agent can read your traces, scores, datasets, and experiment runs, and start them too. The same skill can also add tracing to an app in the first place.

Then ask your coding agent something like:

> Please use the Langfuse skill to find issues in our traces.

The agent looks at the scores you configured, such as disagreement and frustration, and also goes beyond them: latency, tool calls, and anything else that might be silently failing. In the workshop, the report on the seeded traces surfaced:

- **A silent retrieval failure** in `search_help_library`. None of the evaluators checked for this, and nobody had noticed the tool was not returning useful information.
- **Retries adding latency and cost.** Retrieval misses led to repeated tool calls.
- **An evaluation coverage gap.** Only a subset of recent traces had evaluation scores at all.
- A live run in Codex also flagged an issue with the **prompt version**.

This shows the limits of the first monitors. Disagreement and all-caps scores tell you a user was unhappy. They do not tell you whether retrieval, retries, or something else caused it. Looking at the tool observations gives you that next level of diagnosis.

Because the coding agent also has your repository as context, it can propose code changes and not only Langfuse configuration. In the workshop, the follow-up is to remove the `search_help_library` tool, since it does not seem to help. A change like this still needs testing before you ship it, which leads to the offline part of the loop.

## Close the loop [#close-the-loop]

Catching signals is only the first half. To keep improving an agent over time, you need to maintain two things:

- **Your evaluation criteria.** Check that evaluators are not over-indexing on one behavior and that they still tell you something useful.
- **Your datasets.** When you first build an app, you think you know what people will do with it. Production shows you all the edge cases you did not account for. Turn good production examples into dataset items, add them to your offline evals, and run experiments on every change. You can make this part of your CI/CD with [experiments in CI/CD](/docs/evaluation/experiments/experiments-ci-cd) so you ship with confidence and catch regressions.

None of this is a one-off. You need to put in the reps and close the loop continuously so your dataset keeps representing what your users actually do.

## If you start tomorrow [#start-tomorrow]

1. Use the Langfuse Agent Skill to add tracing to your repository, so you know what is happening in your app.
2. Review traces manually to understand what people are really doing.
3. Build evaluators for your production traces around the failures that matter to you.
4. Use those signals to build datasets and experiments, and start optimizing offline.

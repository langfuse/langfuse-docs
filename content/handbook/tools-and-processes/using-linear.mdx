# Using Linear

We use Linear as the source of truth for engineering work. Slack, Pylon, GitHub, and docs provide context, but the owner, scope, status, target date, and next decision live in Linear.

Linear is the backbone of our [product ops](/handbook/product-engineering/how-we-work/product-ops). It helps us move quickly as a small team while staying accountable to customers and open source users.

## Principles

- We maintain our own issues and projects. There is no central backlog manager, so every active item has an owner.
- We create issues for work that we are likely to do within the next six months. Longer-term ideas belong on the [roadmap](/docs/roadmap) or in [GitHub Ideas](/ideas).
- We keep Linear current instead of recreating status in Slack or a weekly document.
- We plan around outcomes, not collections of tasks. A project has a clear finish line and a target date.

## Choose the right level

| Level      | Use it for                                                                 | Example                              |
| ---------- | -------------------------------------------------------------------------- | ------------------------------------ |
| Initiative | A durable product area or strategic direction that groups related projects | Evaluation platform                  |
| Project    | A bounded outcome with one lead, a target date, and a clear end            | Support evaluation datasets at scale |
| Milestone  | A meaningful checkpoint on the way to the project outcome                  | Private beta ready                   |
| Issue      | A concrete unit of work that one person can own                            | Add dataset pagination               |

Do not use one evergreen project for a whole product area. Keep the initiative durable and create bounded projects beneath it.

## Set up projects consistently

The project lead creates and maintains the project. Before work starts, set:

- **Lead:** one person accountable for progress and communication.
- **Initiative and team:** the strategic area and engineering team that own the work.
- **Target date:** the current estimated finish date, not an aspirational placeholder.
- **Roadmap quarter:** the agreed quarter label so the project appears in planning views.
- **Milestones:** meaningful checkpoints, each with a short definition of done.
- **Description:** the outcome, context, scope, non-goals, and success criteria.
- **Resources:** the RFC, customer evidence, designs, and relevant decisions.

Write RFCs in a Linear Doc when practical so discussion and delivery stay together. If an RFC lives in Google Docs or elsewhere, link it from the project and record the final decision in Linear.

Every project should have milestones and issues covering the known work to the next milestone. Discovery work can start with fewer issues, but the next decision and its owner must be explicit.

## Keep issues current

Engineers own the accuracy of their issues:

- Give each issue one owner and link it to the relevant project and milestone.
- Add work planned for the week to the current Linear cycle before the Monday check-in.
- Use sub-issues when they make ownership or sequencing clearer.
- Keep the status accurate. If blocked, add the blocker, the next action, and who can unblock it.
- Link the source conversation or customer request instead of copying context without attribution.
- Use the branch name generated by Linear so the pull request links back automatically.
- Move an issue to `Done` only after the change is deployed and any follow-up work is tracked.

Clear the Linear inbox at least once each working day. Treat issue comments as the primary channel for discussion that future contributors need to find.

## Post weekly project updates

Before the Monday engineering check-in, each active project lead posts a project update and sets the project health. Engineers update their issues and cycle commitments, but do not write a second prose summary for the same work.

Use this short update format:

```text
Outcome: What changed since the last update?
Next: What is the next milestone or decision?
Risk: What could move the target date or scope?
Ask: What decision, help, or dependency is needed?
Change: What changed in scope, health, or target date?
```

Keep updates factual and useful for decisions. If nothing important changed, say so in one line. An active project without an update in the last seven days is stale.

Use project health consistently:

- **On track:** We expect to hit the next milestone and target date without intervention.
- **At risk:** A known risk could change scope or timing. The update names the mitigation or decision needed.
- **Off track:** We no longer expect to hit the current scope or date. The update proposes a new plan.

## Run the Monday engineering check-in from Linear

We use two Linear views for the meeting:

- The [Engineering updates Pulse](https://linear.app/clickhouse/pulse/view/engineering-updates-200438883801) is the reading view. It shows the full project and initiative updates in chronological order.
- The [Monday current-quarter project view](https://linear.app/clickhouse/view/current-quarter-projects-8f42f51603fa) is the decision-making agenda. It contains planned and in-progress projects for the current quarter, grouped by initiative and health, with the lead, milestone progress, target date, and latest update date visible.

Before the meeting:

- Project leads post their update and set health, milestone progress, and target date.
- Engineers update current-cycle issues and flag blockers.
- Everyone reads the Engineering updates Pulse and comments asynchronously where no group discussion is needed.

We use the 30-minute meeting for exceptions and decisions:

1. **Silent read, 5 minutes:** Scan the Engineering updates Pulse, starting with off-track and at-risk work.
2. **Exceptions, 15 minutes:** Resolve risks, cross-team dependencies, and decisions. Skip unchanged on-track projects.
3. **Cycle check, 5 minutes:** Confirm this week's commitments and surface capacity gaps.
4. **Decisions, 5 minutes:** Assign owners and dates for every action, then record them in Linear.

This is not a round-robin status report. Engineers only summarize individual work when it is not represented by a project or when the team needs to make a decision. We end early when there are no exceptions.

## Handle feature requests and customer feedback

Linear is the source of truth for feature requests. Feedback may arrive through Pylon, Slack, GitHub, or a customer conversation, but a specific customer ask should become or link to a structured Linear request.

During triage:

1. Confirm the product area, customer, use case, and urgency.
2. Search for an existing request and merge duplicates so demand accumulates in one place.
3. Route the request to the product area owner.
4. Link it to planned engineering work when we commit to it. A request is evidence, not automatically a roadmap commitment.
5. Close the loop with the requester when the work ships or the decision changes.

See [product ops](/handbook/product-engineering/how-we-work/product-ops) for the customer support and feedback flow.

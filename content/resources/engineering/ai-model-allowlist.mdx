# Control which AI models your company can use

Without a central policy, the model mix in a company is whatever each developer and service picks. That makes cost unpredictable, because the most capable model is often the most expensive one, and it makes compliance reviews harder, because nobody can say which models process company data. A model allowlist at the gateway answers both: admins decide which models can be called, and every call goes through that decision.

<SignupCTA className="my-6" />

**TL;DR:** In the [Langfuse AI Gateway](/docs/gateway/overview), owners and admins turn models on or off per provider credential. Gateway keys can only call enabled models. A credential with every model enabled also allows models the provider publishes later; once you turn one model off, the credential keeps an explicit list, so new models stay off until an admin enables them. Everyone with gateway access can see which models are available.

## Why approve models centrally [#why]

Teams usually introduce a model allowlist for one of three reasons:

1. **Cost control.** Large models cost an order of magnitude more per token than small ones. Restricting routine workloads to approved models keeps spend predictable before hard budgets exist.
2. **Vendor and data review.** Security and legal teams approve specific providers and models for company data. An allowlist enforces that approval instead of documenting it.
3. **Consistency.** When everyone uses the same set of models, cost and quality comparisons across teams mean something.

## How the allowlist works [#how-it-works]

Model access is set on each provider credential, under **AI Gateway → Providers & Models → Models**:

- **By default, a credential allows every model** the provider offers, including models released later.
- **Turning a model off switches the credential to an explicit list.** From then on, only enabled models can be called, and new provider releases stay off until someone enables them.
- **Enable all** returns the credential to allowing every model.
- **Refresh provider models** fetches the provider's current list, so newly released models show up for review.

Gateway keys can only call models that are enabled on a credential. See [model management](/docs/gateway/features/models#manage-models) for the steps.

## Use separate credentials for separate policies [#multiple-credentials]

An organization can add several credentials per provider, each with its own model list. Each credential's name becomes the prefix of its model IDs, in the form `<credential>:<model>`.

That gives you a simple way to express different policies:

| Credential         | Enabled models                        | Intended for              |
| ------------------ | ------------------------------------- | ------------------------- |
| `anthropic-prod`   | The models approved for production    | Services and CI           |
| `anthropic-agents` | The models approved for coding agents | Developers' coding agents |
| `openai-research`  | A wider set for evaluation work       | A small research group    |

Separate credentials make each policy explicit and easy to review, and they separate cost per credential on the analytics page. They don't restrict who can call what: clients choose a credential through the model ID prefix. Coding agents that send provider model names without a prefix (IDs starting with `gpt-`, `codex-`, `ft:`, or `claude-`) are routed to the oldest matching credential, so put your default policy on the oldest one. Amazon Bedrock model IDs always need the prefix. See [model IDs](/docs/gateway/features/models#model-ids).

<Callout type="info">
  The allowlist controls which models can be called, not who can call them.
  Every gateway key, user or service account, can call the enabled models of
  every credential in the organization. Per-key or per-team model restrictions
  are not part of the gateway today. Review calls per key and per user on the
  [analytics page](/docs/gateway/features/analytics).
</Callout>

## Make the policy visible [#visibility]

Everyone with gateway access, including Viewers and people with the AI Gateway role, can open the model list and see what is available. Developers find out what they can use before they hit an error, and reviewers can check the policy without admin rights.

For an audit trail of which key called which model, see [AI audit trail](/resources/engineering/ai-audit-trail). Every recorded generation stores the model and the provider credential that served it.

## When a new model is released [#new-models]

A practical review routine:

1. Keep the production credential on an explicit list, so new models stay off.
2. Enable the new model on a research credential and compare cost and quality on real traffic with [experiments](/docs/evaluation/experiments/datasets).
3. Enable it on the production credential once it is approved.

## FAQ

<FaqDetails>

<Details id="why-cant-i-call-a-new-model">
<Summary>Why can't I call a newly released model through the gateway?</Summary>

The credential has an explicit model list because an admin turned at least one model off. New models stay off until an admin enables them under **AI Gateway → Providers & Models → Models**. Select **Refresh provider models** if the model doesn't appear in the list yet.

</Details>

<Details id="per-user-model-restrictions">
<Summary>Can I allow a model for one team but not another?</Summary>

The allowlist is per provider credential, not per key or user. Teams that need different policies can use different credentials, but any gateway key can call any enabled model. Review per-team usage with key metadata on the analytics page.

</Details>

<Details id="which-providers">
<Summary>Which providers does the allowlist apply to?</Summary>

All providers the gateway supports: OpenAI, Anthropic, and Amazon Bedrock, as of November 2026. Each credential has its own model list.

</Details>

</FaqDetails>

# How to trace and debug a multi-agent system built with LangGraph

A multi-agent LangGraph system fails in ways a single chain does not. The supervisor routes a request to the wrong worker, a worker retries a failing tool until the graph hits its step limit, one agent consumes most of the token budget, or a sub-graph returns a good answer that the parent never uses. Watching `graph.stream()` print state updates shows the order of events, not which LLM call made the routing decision, what a tool returned, or what the run cost. Tracing does, and this guide shows how to set it up with Langfuse.

**TL;DR:** Pass the Langfuse `CallbackHandler` from `langfuse.langchain` in the graph's `config`, and every invocation becomes one trace with the supervisor, the workers, their LLM calls, and their tool calls nested inside it. Wrap the invocation in `propagate_attributes` to set a trace name, user, session, tags, and metadata, and give each invocation a `run_name`. When one graph calls another graph, share a trace ID through `trace_context` so the whole run lands in one trace. Debug in the agent graph view: Aggregated mode shows the agent's shape and its loops, Expanded mode shows one run step by step. Group conversation turns with a session ID, and use tags, the filter search bar, and Pulse to find the runs worth opening.

## Instrument the graph with the callback handler

Langfuse traces LangGraph through LangChain callbacks. LangGraph is built on LangChain, so the same `CallbackHandler` that traces a chain traces a compiled graph; the `langfuse` Python package ships it in `langfuse.langchain`, and there is no separate LangGraph SDK. This is the production shape of the second example in the [LangGraph integration cookbook](/integrations/frameworks/langgraph).

```python
from langfuse import get_client, propagate_attributes
from langfuse.langchain import CallbackHandler
from langchain_core.messages import HumanMessage

langfuse = get_client()  # reads LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, LANGFUSE_BASE_URL
langfuse_handler = CallbackHandler()

with propagate_attributes(
    trace_name="support-supervisor",
    user_id="user-123",
    session_id="thread-abc",
    tags=["langgraph", "multi-agent"],
    metadata={"release": "v42"},
):
    result = graph.invoke(
        {"messages": [HumanMessage(content="Where is my order?")]},
        config={
            "callbacks": [langfuse_handler],
            "run_name": "handle-support-message",
        },
    )
```

Each `invoke` or `stream` call creates one trace. With only `config={"callbacks": [langfuse_handler]}`, traces carry generic names such as `LangGraph`. Three additions make a trace findable:

- `trace_name`, set through `propagate_attributes`, names the trace and appears in the Trace Name column. Name it after the graph.
- `run_name` in the LangChain `config` names the invocation and appears in the Name column. Name it after the operation.
- `user_id`, `session_id`, `tags`, and `metadata` propagate to every observation created inside the block, including LLM and tool calls deep inside a worker agent.

When a context manager is inconvenient, the handler also reads `langfuse_user_id`, `langfuse_session_id`, and `langfuse_tags` from the LangChain `metadata` dict in `config`. The [LangChain integration page](/integrations/frameworks/langchain) covers both options and the JS/TS handler in `@langfuse/langchain`.

The trace mirrors your code:

| In your code                              | In the Langfuse trace                                                             |
| ----------------------------------------- | --------------------------------------------------------------------------------- |
| One `graph.invoke` or `graph.stream` call | One trace, with the invocation named after `run_name`                             |
| A chat model call inside a node           | A `generation` observation with the messages, the response, token usage, and cost |
| A function decorated with `@tool`         | A `tool` observation with its input and output                                    |
| A LangChain retriever                     | A `retriever` observation                                                         |
| A sub-graph invoked from inside a tool    | Nested under the calling observation, as long as it shares the trace              |

## Keep a multi-agent run in one trace

Multi-agent systems come in two shapes, and only one needs extra work.

**Supervisor and workers in one `StateGraph`.** An LLM node picks the next worker through structured output, worker nodes are agents with their own tools, and conditional edges route between them until the supervisor answers `FINISH`. Because the team is one compiled graph, one invocation is one trace: the routing decisions and every worker's LLM and tool calls nest under the same root. Node names become the labels in the trace tree and the agent graph, so name nodes after roles (`supervisor`, `researcher`, `billing`) rather than implementation details.

**One graph calling another graph.** When a worker is itself a compiled graph exposed to the parent as a tool, each `invoke` would create its own trace with no link to the parent. Generate a trace ID up front and pass it as `trace_context` on a span around each invocation:

```python
from langfuse import get_client, Langfuse, propagate_attributes
from langfuse.langchain import CallbackHandler
from langchain_core.messages import HumanMessage
from langchain_core.tools import tool

langfuse = get_client()
langfuse_handler = CallbackHandler()


@tool
def research(question: str) -> str:
    """Delegates a research question to the research sub-graph."""
    with langfuse.start_as_current_observation(
        as_type="span",
        name="call-research-sub-agent",
        trace_context={"trace_id": langfuse.get_current_trace_id()},
    ) as span:
        span.update(input=question)
        response = research_graph.invoke(
            {"messages": [HumanMessage(content=question)]},
            config={"callbacks": [langfuse_handler], "run_name": "research-sub-agent"},
        )
        answer = response["messages"][-1].content
        span.update(output=answer)
    return answer


def handle_request(user_question: str) -> tuple[str, str]:
    trace_id = Langfuse.create_trace_id()
    with langfuse.start_as_current_observation(
        as_type="span",
        name="run-main-agent",
        trace_context={"trace_id": trace_id},
    ) as span:
        with propagate_attributes(trace_name="research-assistant", session_id="thread-abc"):
            span.update(input=user_question)
            response = main_agent.invoke(
                {"messages": [{"role": "user", "content": user_question}]},
                config={"callbacks": [langfuse_handler], "run_name": "main-agent"},
            )
            span.update(output=response["messages"][-1].content)
    return response["messages"][-1].content, trace_id
```

Generating the trace ID inside `handle_request` keeps it scoped to one invocation; a module-level ID would be reused by every request in a long-lived server or worker, merging unrelated conversations into a single trace. The `research` tool picks up the same ID through `get_current_trace_id()` because it runs nested inside this span's context. The wrapping span also records the question handed to the sub-agent and the answer it returned, which is where a "sub-agent answered correctly but the parent ignored it" bug becomes visible: compare the span's output with the input of the parent's next generation. The returned trace ID lets you attach feedback after the request completes, with `langfuse.create_score(trace_id=trace_id, name="user-feedback", value=1, data_type="NUMERIC")`.

## Read the trace

A LangGraph trace opens in two views. The observation tree shows every generation with its input messages, output, and token usage and cost by usage type, and every tool observation with what the agent passed in and what came back. The [agent graph view](/docs/observability/features/agent-graphs) draws the same trace as a graph. It appears automatically for traces from the LangGraph integration, and for any trace containing an observation typed as something other than `span`, `event`, or `generation`.

The graph has two modes, switched with the Aggregated / Expanded toggle in the top-left corner.

| Question                                    | Mode       | What you see                                                                                    |
| ------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------- |
| What does this agent do, and is it looping? | Aggregated | One node per step name, with a counter such as `retrieve_docs (3/3)`, and loops drawn as cycles |
| Where exactly did this run go wrong?        | Expanded   | One node per call in execution order, with loops unrolled into an acyclic graph                 |

Start in Aggregated mode: a worker node with a high counter or a cycle edge between the supervisor and one worker tells you within seconds that the run looped. Then switch to Expanded mode to walk the specific run and find the exact call where state went wrong. Cost lives on `generation` and `embedding` observations only, computed from ingested usage and the model's price definition, so the cost of one worker is the sum of the generations under its node.

## A debugging playbook for multi-agent runs

Most multi-agent failures fall into a handful of patterns. The table maps each symptom to the place in the trace that explains it and to the usual root cause.

| Symptom                                       | Where to look                                                                                                         | What it usually is                                                                                                                 |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| The wrong worker handled the request          | The supervisor's `generation`: its input messages and the routing decision in its output                              | Worker descriptions in the supervisor prompt overlap, or the router lacks context from the user message                            |
| A tool fails and the agent retries in a loop  | Aggregated graph: a tool node with a high counter and a cycle edge; filter observations with `level:ERROR type:TOOL`  | The tool raises on a malformed argument and the agent retries with the same argument                                               |
| The run never terminates                      | Expanded graph: the supervisor-to-worker cycle repeats and the supervisor's outputs never contain the finish decision | The stop condition depends on a state field no worker writes, or the supervisor prompt has no stop rule                            |
| One agent dominates the cost                  | Generations under that agent's node: input tokens per call; Pulse in Cost mode across many runs                       | The worker receives the full message history on every call (`add_messages` appends by design), so input tokens grow with each turn |
| One step is slow                              | Latency on each observation; filter with `latency:>2` and Pulse in Latency mode                                       | A single external tool call, or a worker that runs several tool calls sequentially                                                 |
| The sub-agent answered, the parent ignored it | The wrapping span's `output` versus the input of the parent's next `generation`                                       | The tool returns the answer but the parent node does not write it into state                                                       |
| Generations show tokens but no cost           | The `model` field on the generation                                                                                   | The model name matches no Langfuse model definition; set `model="gpt-4o"` on `AzureChatOpenAI`, or add a custom model definition   |

## Follow multi-turn conversations with sessions

A conversational agent produces one trace per turn, and the bug is often between turns: the agent forgot a constraint from three messages ago, or the supervisor routed a follow-up to a different worker. [Sessions](/docs/observability/features/sessions) group traces that share a `session_id` and replay the whole interaction as the user experienced it.

Set the session ID in `propagate_attributes`, as in the first snippet. LangGraph gives you a natural key: pass the identifier you already use as the graph's thread ID, so a Langfuse session and a LangGraph thread refer to the same conversation. Session IDs must be US-ASCII strings under 200 characters. Sessions can be bookmarked, published, and scored in the UI.

## Run it in production

**LangGraph Server.** When LangGraph Server invokes your graph, you do not control the `invoke` call, so attach the handler at compile time: `graph_builder.compile().with_config({"callbacks": [langfuse_handler]})` returns a compiled graph with the callback included, and every server-side invocation is traced.

**Tags and metadata.** Tags are strings up to 200 characters, aggregated from a trace's observations onto the trace, and they cannot be added or edited in the UI afterwards, so decide the taxonomy up front. Propagated metadata takes string values up to 200 characters with alphanumeric keys and is filterable in the UI and API. Keep environment out of both and set `LANGFUSE_TRACING_ENVIRONMENT` instead.

**Finding the run to open.** The [filter search bar](/docs/observability/features/filter-search-bar) turns the playbook into one-line queries: `tags:multi-agent level:ERROR type:TOOL` for failing tool calls, `session:thread-abc` for one conversation, `name:*billing* latency:>2` for slow billing-worker steps, `metadata.release:v42` for one deployment. Bare words search input and output as full text. The search bar and Pulse run on the Langfuse v4 data model, which is live on Langfuse Cloud and generally available for self-hosted deployments as of September 2026.

**Hunting outliers with Pulse.** [Pulse](/docs/observability/features/pulse) is a chart strip above the observations table that plots count, cost, or p95 latency per time bucket for the current filtered query. A cost spike from a looping worker or a latency spike from a slow tool is a tall bar; click it and the table narrows to that window.

**Short-lived processes.** The SDK batches events in the background. In a script, a job, or a serverless function, call `get_client().shutdown()` before exit so the last traces are flushed.

## From debugging to evaluation

Debugging finds one bad run; evaluation tells you how often it happens and whether your fix held. Add the debugged trace's input to a dataset, and write the violated property as a code evaluator that runs on every experiment and, with sampling, on production traffic. Recorded tool calls are exposed to evaluators as a structured field, so tool-selection and step-budget checks are a few lines of Python. The [AI agent evaluation guide](/resources/engineering/ai-agent-evaluation) covers trajectory, tool-call, task-completion, and multi-turn evaluation for this kind of system, and the [code evaluator examples](/resources/engineering/code-evaluator-examples) include paste-ready checks to start from.

## FAQ

### Does Langfuse trace LangGraph automatically? [#langgraph-automatic-tracing]

Yes, through the LangChain callback handler. Instantiate `CallbackHandler` from `langfuse.langchain`, pass it in `config={"callbacks": [langfuse_handler]}` on `invoke` or `stream`, and the run appears as a trace with LLM calls, tool calls, and retrievers as nested observations. The JS/TS handler in `@langfuse/langchain` works the same way, and the Python integration requires Python 3.11 or newer.

### How do I get the supervisor and all workers into one trace? [#one-trace-supervisor-workers]

If the supervisor and workers are nodes of one compiled `StateGraph`, they already share a trace, because one invocation of the graph is one trace. Pass the handler once at the top-level `invoke`; worker agents do not need it separately.

### How do I trace an agent that calls another LangGraph graph? [#nested-langgraph-graphs]

Generate a trace ID with `Langfuse.create_trace_id()` and pass it as `trace_context={"trace_id": ...}` on a `start_as_current_observation` span around both the parent invocation and the sub-graph invocation inside the tool. Both runs then land in the same trace, with the sub-graph nested under the span that called it. Set the span's `input` and `output` to the delegated question and the returned answer so the hand-off is visible.

### How do I see whether my LangGraph agent is looping? [#see-agent-loops]

Open the trace's agent graph view in Aggregated mode. Steps that share a name collapse into one node with a counter, so a tool that ran five times shows as `tool_name (5/5)`, and a loop between the supervisor and a worker is drawn as a cycle edge. Switch to Expanded mode to see the same loop unrolled in execution order and find the call where it should have stopped.

### How do I track cost per agent in a multi-agent system? [#cost-per-agent]

Cost is recorded on each `generation` observation from the model's token usage, so the cost of one agent is the sum of the generations nested under its node in the trace tree. Across many runs, tag traces by graph and use Pulse in Cost mode or a custom dashboard segmented by tag. Only `generation` and `embedding` observations carry cost; tool observations carry latency.

# AI Gateway

The Langfuse AI Gateway relays model requests from your applications and coding agents to your LLM providers and records every call as a generation in Langfuse. Clients only change their base URL and API key. This guide covers how to deploy and operate the gateway on a self-hosted Langfuse instance.

<Callout type="warning">

**Beta.** The AI Gateway is in beta on self-hosted deployments. Its configuration, including the `langfuse.gateway.*` Helm values, is not covered by SemVer and may change in minor releases. [Subscribe to Langfuse OSS updates](/self-hosting/oss-newsletter) to hear when it leaves beta.

</Callout>

## Requirements [#requirements]

- **Kubernetes with the [Helm chart](/self-hosting/deployment/kubernetes-helm)**, in a release after `2.2.0` that includes the `langfuse.gateway` values. The chart deploys and configures the gateway. The chart is the supported deployment path during the beta: the Docker Compose setup does not include the gateway. To run it another way, run the gateway image with the [gateway variables](#configuration) and set the web variables on Langfuse Web.
- **Langfuse `v4.72.0` or later** for web and the gateway image, and the same version for both. Use the latest release: newer gateway features, such as the AI Gateway organization role, ship after `v4.72.0`. Image tags have no `v` prefix, for example `4.72.0`.
- **The v4 data model.** The gateway is unavailable while `LANGFUSE_MIGRATION_V4_WRITE_MODE=legacy`, because gateway generations are only stored in the v4 tables. `events_only` (the default) and `dual` work. See the [v4 upgrade guide](/self-hosting/upgrade/upgrade-guides/upgrade-v3-to-v4#step-2).
- **A DNS name for the gateway**, such as `gateway.langfuse.example.com`, with a TLS certificate that covers it. See [TLS](#tls).
- **Direct outbound HTTPS from the gateway pods and from web to your LLM providers**, `api.openai.com` and `api.anthropic.com`. Web calls the providers too, to validate credentials and discover models. The gateway ignores `HTTP_PROXY`, `HTTPS_PROXY`, and other egress proxy settings, and it always calls the providers' official API URLs, so Azure OpenAI, Amazon Bedrock, and internal LLM proxies aren't supported.
- **`ENCRYPTION_KEY` on web.** Provider credentials are stored encrypted with it, like [LLM connections](/docs/administration/llm-connection). If it changes, stored provider credentials can no longer be read and have to be added again.

## How it works [#architecture]

The gateway is a separate, stateless container (`ghcr.io/langfuse/ai-gateway`) on its own host. It has no database, Redis, ClickHouse, or S3 credentials; it only talks to Langfuse Web and your LLM providers.

import ArchitectureDiagram from "@/components-mdx/architecture-diagram-v3.mdx";

<ArchitectureDiagram />

1. A client sends a request to the gateway's public URL, for example `https://gateway.langfuse.example.com/anthropic/v1/messages`, with a gateway API key.
2. The gateway asks Langfuse Web to resolve the key. Web checks the key and returns the organization's provider connection, including the provider API key.
3. The gateway forwards the native request to the provider, with the provider credential in place of the gateway key, and streams the response back. See [what the gateway changes](/docs/ai-gateway/troubleshooting-and-faq#does-the-gateway-change-requests).
4. The gateway uploads the generation to Langfuse Web, which ingests it like any other trace.

Organization admins then set up provider connections and gateway API keys in the Langfuse UI.

## Deploy with Helm [#helm]

Enable the gateway and give it its own Ingress host in your `values.yaml`:

```yaml filename="values.yaml"
langfuse:
  nextauth:
    url: https://langfuse.example.com
  gateway:
    enabled: true
    image:
      repository: ghcr.io/langfuse/ai-gateway
    ingress:
      enabled: true
      className: nginx
      hosts:
        - gateway.langfuse.example.com
      tls:
        enabled: true
        secretName: langfuse-gateway-tls
      annotations:
        cert-manager.io/cluster-issuer: letsencrypt
        # Streams can run for up to 600 s and stay quiet for up to 120 s.
        nginx.ingress.kubernetes.io/proxy-read-timeout: "620"
        nginx.ingress.kubernetes.io/proxy-send-timeout: "620"
        nginx.ingress.kubernetes.io/proxy-buffering: "off"
        nginx.ingress.kubernetes.io/proxy-request-buffering: "off"
        # The gateway accepts request bodies of up to 16 MiB.
        nginx.ingress.kubernetes.io/proxy-body-size: "17m"
    resources:
      requests:
        cpu: "1"
        memory: 2Gi
      limits:
        memory: 2Gi
```

Set `image.repository` to `ghcr.io/langfuse/ai-gateway`, where the gateway image is published. The image tag follows `langfuse.image.tag` and the chart's `appVersion`, like web. If your chart's `appVersion` is older than `4.72.0`, set `langfuse.image.tag` to a newer release.

Then apply it with `helm upgrade` and check that the gateway pods become ready:

```bash
helm upgrade langfuse langfuse/langfuse -n langfuse -f values.yaml
kubectl get pods -n langfuse -l app.kubernetes.io/component=gateway
```

With `gateway.enabled: true`, the chart:

- Deploys the gateway as its own Deployment, Service (port `8080`), Ingress, optional HorizontalPodAutoscaler, and PodDisruptionBudget.
- Sets `LANGFUSE_AI_GATEWAY_DEPLOYED=true` on web, which turns on the gateway pages in the UI for all organizations.
- Points the gateway at web's in-cluster Service, so gateway traffic to web does not leave the cluster. See [Gateway to Langfuse Web](#gateway-to-web).
- Generates the two shared secrets into the `<release>-app` Secret: the service key that web and the gateway use to authenticate each other, and the private key web uses to sign the gateway's trace upload tokens.

<Callout type="warning">

With `helm template`-based GitOps tools such as Argo CD, the chart cannot read existing Secrets, so the generated keys change on every sync and gateway requests fail until both web and gateway restart. In that case, create the keys yourself and reference them with `langfuse.gateway.serviceKey.secretKeyRef` and `langfuse.gateway.jwt.privateKey.secretKeyRef`:

```bash
kubectl create secret generic langfuse-gateway -n langfuse \
  --from-literal=ai-gateway-service-key="$(openssl rand -hex 32)" \
  --from-file=ai-gateway-jwt-private-key=<(openssl ecparam -name prime256v1 -genkey -noout)
```

```yaml filename="values.yaml"
langfuse:
  gateway:
    serviceKey:
      secretKeyRef:
        name: langfuse-gateway
        key: ai-gateway-service-key
    jwt:
      privateKey:
        secretKeyRef:
          name: langfuse-gateway
          key: ai-gateway-jwt-private-key
```

</Callout>

For the full list of values, see the [chart README](/self-hosting/deployment/kubernetes-helm#readme). To turn the gateway on only for some organizations, see [Access and roles](#roles).

### Public URL [#public-url]

Langfuse shows the gateway's public URL in the UI and in the setup snippets for coding agents. The chart sets it on web as `LANGFUSE_AI_GATEWAY_PUBLIC_URL`, in this order:

1. `langfuse.gateway.publicUrl`, if set.
2. Otherwise the first host in `langfuse.gateway.ingress.hosts`, over `https://` when the gateway Ingress has TLS enabled or `langfuse.nextauth.url` starts with `https://`, and `http://` otherwise.
3. Without either, web shows `gateway.<host of NEXTAUTH_URL>`.

Set `publicUrl` explicitly when you expose the gateway in another way, such as your own Ingress, the Gateway API, or a `LoadBalancer` Service. The value must be an origin without a path, such as `https://llm.example.com`.

## TLS [#tls]

We strongly recommend serving the gateway over HTTPS:

- Every request carries a gateway API key, and request and response bodies contain full prompts and model outputs.
- Coding clients such as Claude Desktop expect an `https://` gateway URL.

Like Langfuse Web, the gateway does not terminate TLS itself. Terminate TLS in front of it, at the Ingress controller or at a load balancer. The gateway's host needs its own DNS record and a certificate that covers it.

<Tabs items={["cert-manager", "Your own certificate", "TLS at a load balancer"]}>

<Tab>

If cert-manager runs in your cluster, add its issuer annotation to the gateway Ingress. cert-manager then issues and renews a certificate for the gateway host and stores it in `secretName`:

```yaml filename="values.yaml"
langfuse:
  gateway:
    ingress:
      enabled: true
      hosts:
        - gateway.langfuse.example.com
      tls:
        enabled: true
        secretName: langfuse-gateway-tls
      annotations:
        cert-manager.io/cluster-issuer: letsencrypt
```

Use a `secretName` that differs from web's `langfuse.ingress.tls.secretName`, so the two certificates do not overwrite each other. With an HTTP-01 issuer, the gateway host must be reachable from the internet; for internal hosts, use a DNS-01 issuer.

</Tab>

<Tab>

Create a Kubernetes TLS Secret from your certificate and key, and reference it without a cert-manager annotation:

```bash
kubectl create secret tls langfuse-gateway-tls -n langfuse \
  --cert=gateway.crt --key=gateway.key
```

```yaml filename="values.yaml"
langfuse:
  gateway:
    ingress:
      enabled: true
      hosts:
        - gateway.langfuse.example.com
      tls:
        enabled: true
        secretName: langfuse-gateway-tls
```

If web's certificate already covers the gateway host, as a wildcard such as `*.langfuse.example.com` or as a subject alternative name, you can reference web's Secret instead. Include the full chain in `gateway.crt`, since clients reject certificates whose intermediates are missing.

</Tab>

<Tab>

If TLS terminates at a cloud load balancer, for example an AWS Application Load Balancer, leave `tls.enabled` off and configure the certificate on the load balancer. The chart still uses `https://` for the [public URL](#public-url) when `langfuse.nextauth.url` is `https://`; otherwise set `langfuse.gateway.publicUrl`.

With the AWS Load Balancer Controller:

```yaml filename="values.yaml"
langfuse:
  gateway:
    ingress:
      enabled: true
      className: alb
      hosts:
        - gateway.langfuse.example.com
      annotations:
        alb.ingress.kubernetes.io/scheme: internet-facing
        alb.ingress.kubernetes.io/target-type: ip
        alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
        alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:<region>:<account>:certificate/<id>
        alb.ingress.kubernetes.io/healthcheck-path: /ready
        alb.ingress.kubernetes.io/load-balancer-attributes: idle_timeout.timeout_seconds=620
```

The idle timeout applies to the whole load balancer. If the gateway shares web's load balancer through `alb.ingress.kubernetes.io/group.name`, the timeout changes for web too, so use a separate group for the gateway.

</Tab>

</Tabs>

To verify, check that the gateway answers over HTTPS with a valid certificate:

```bash
curl -v https://gateway.langfuse.example.com/health
# {"status":"ok"}
```

### Gateway to Langfuse Web [#gateway-to-web]

The gateway calls Langfuse Web to resolve every request and to upload generations. Web's responses contain the provider API keys of your organization, so this connection must stay private or be encrypted.

By default, the chart points the gateway at web's in-cluster Service, `http://<release>-web.<namespace>.svc.cluster.local:3000`. This traffic stays inside your cluster network, avoids a round trip through the Ingress, and keeps request resolution fast. Because the URL is plain HTTP, the chart sets `LANGFUSE_AI_GATEWAY_ALLOW_HTTP_WEB_URL=true` on the gateway. Without that setting, the gateway only accepts `https://` web URLs. For end-to-end encryption inside the cluster, use a service mesh with mutual TLS, as described in [Encryption](/self-hosting/configuration/encryption#https).

If the gateway cannot reach web's Service, for example because web runs in another cluster, set `langfuse.gateway.webUrl` to an `https://` URL such as your `NEXTAUTH_URL`. Requests then pass through web's Ingress, so its body size limit must allow the gateway's requests. The chart's in-cluster default has no path, so if web runs under a [custom base path](/self-hosting/configuration/custom-base-path), set `langfuse.gateway.webUrl` including the path, for example `http://langfuse-web.langfuse.svc.cluster.local:3000/langfuse`.

If web's certificate is signed by a private CA, mount the CA bundle with `langfuse.gateway.pod.extraVolumes` and `extraVolumeMounts`, and point `SSL_CERT_FILE` at it with `langfuse.gateway.pod.additionalEnv`.

<Callout type="warning">

`SSL_CERT_FILE` replaces the gateway's trust store for all connections, including the ones to your LLM providers. The bundle must contain the public root certificates as well as your private CA, or provider calls fail with TLS errors.

</Callout>

<Callout type="warning">

Never use a plain `http://` web URL across a public network. Web's responses contain provider API keys, and the gateway's requests carry the service key and upload tokens.

</Callout>

## Proxy timeouts and buffering [#timeouts]

Model responses are streamed and can take minutes. The gateway ends a request after 600 seconds (`LANGFUSE_AI_GATEWAY_MAX_EXECUTION_SECONDS`) or after 120 seconds without progress (`LANGFUSE_AI_GATEWAY_STALL_TIMEOUT_SECONDS`). Everything between the client and the gateway must allow this:

- Set proxy read and send timeouts, or the load balancer idle timeout, above 120 seconds. `620` covers the full 600 seconds.
- Turn off response buffering, so streamed tokens reach the client as they arrive.
- Allow request bodies of at least 16 MiB (`LANGFUSE_AI_GATEWAY_MAX_REQUEST_BYTES`).

The chart sets no proxy annotations by default, because they depend on your Ingress controller. See the examples in [Deploy with Helm](#helm) for ingress-nginx and in [TLS](#tls) for the AWS Load Balancer Controller.

## Health checks [#health-checks]

The gateway serves two unauthenticated endpoints on port `8080`, which the chart uses as Kubernetes probes:

| Endpoint  | Probe     | Response                                                                                                                                                                  |
| --------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/health` | Liveness  | `200 {"status":"ok"}` while the process serves HTTP, including during shutdown. It does not check dependencies.                                                           |
| `/ready`  | Readiness | `200 {"status":"ready"}` once the gateway is configured with a web URL and service key. `503 {"status":"unconfigured"}` without that configuration and `503 {"status":"draining"}` during shutdown. |

`/ready` does not call web or the providers, so it stays `200` when they are unreachable. Those failures show up as errors on individual requests and in the gateway logs. Use `/ready` for load balancer health checks.

## Graceful shutdown [#graceful-shutdown]

Rollouts and scale-in stop gateway pods while clients may still be streaming. The chart configures the pod so that in-flight streams can finish:

1. **`preStopSleepSeconds` (10 s):** the pod keeps serving while Kubernetes removes it from the Service and Ingress, so no new requests arrive.
2. **`connectionDrainTimeoutSeconds` (300 s):** after `SIGTERM`, the gateway rejects new requests, reports `503` on `/ready`, and lets in-flight requests finish.
3. **`telemetryShutdownTimeoutSeconds` (30 s):** after the drain, the gateway uploads the remaining generations to Langfuse.
4. **`terminationGracePeriodSeconds` (350 s):** Kubernetes kills the pod after this time. It must be greater than the sum of the three steps above; the chart rejects values that are not.

All four are set under `langfuse.gateway`.

<Callout type="info">

Streams that run longer than the drain timeout are cut on every rollout and scale-in. The drain timeout is capped at 300 seconds, while requests can run for up to 600 seconds, so the longest streams can still be cut.

</Callout>

## Access and roles [#roles]

When the gateway is deployed, it is available to every organization on the instance. To limit it to some organizations, set these variables on web through `langfuse.web.pod.additionalEnv`:

```yaml filename="values.yaml"
langfuse:
  web:
    pod:
      additionalEnv:
        - name: LANGFUSE_AI_GATEWAY_ENABLED
          value: "false"
        - name: LANGFUSE_AI_GATEWAY_ORGANIZATION_ID_ALLOWLIST
          value: "<org-id-1>,<org-id-2>"
```

Within an organization, [organization roles](/docs/administration/rbac) control what users can do:

| Organization role | Gateway access                                                                                       |
| ----------------- | ---------------------------------------------------------------------------------------------------- |
| Owner, Admin      | Manage the gateway setup, provider connections, models, analytics, and all gateway API keys (`gateway:manage`) |
| Member            | Create and use their own gateway API keys (`gateway:invoke`)                                         |
| AI Gateway        | Same as Member, with no access to projects or other organization settings                            |
| Viewer            | View the enabled models, without gateway API keys (`gateway:read`)                                   |
| None              | No gateway access                                                                                    |

When a user's role changes to one without gateway access, Langfuse deletes their gateway API keys. See [roles and permissions](/docs/administration/rbac) for all scopes.

On self-hosted deployments, admins can also choose the capture mode `NONE`, which routes requests without recording them. It isn't available on Langfuse Cloud. See [capture modes](/docs/ai-gateway/features/tracing#capture-modes).

## Rotate keys [#rotate-keys]

Web accepts a previous service key and a previous JWT public key next to the current ones. Rotate in three rollouts so that every web pod accepts both keys while pods restart. Set the `_PREVIOUS` variables on web with `langfuse.web.pod.additionalEnv`, and pin the current keys with `secretKeyRef` as shown in [Deploy with Helm](#helm).

**Service key**, shared by web and the gateway:

1. On web, set the **new** key as `LANGFUSE_AI_GATEWAY_SERVICE_KEY_PREVIOUS` and roll out web. Web now accepts both keys.
2. Switch `langfuse.gateway.serviceKey` to the new key, which changes it on web and the gateway, and in the same rollout set `LANGFUSE_AI_GATEWAY_SERVICE_KEY_PREVIOUS` to the **old** key.
3. Remove `LANGFUSE_AI_GATEWAY_SERVICE_KEY_PREVIOUS` and roll out web.

**JWT signing key**, used only by web:

1. On web, set the **new** public key as `LANGFUSE_AI_GATEWAY_JWT_PREVIOUS_PUBLIC_KEY` and roll out web. Derive a public key with `openssl ec -in private-key.pem -pubout`.
2. Switch `langfuse.gateway.jwt.privateKey` to the new private key, and in the same rollout set `LANGFUSE_AI_GATEWAY_JWT_PREVIOUS_PUBLIC_KEY` to the **old** public key.
3. Wait at least 15 minutes, the lifetime of upload tokens signed with the old key. Then remove the previous public key and roll out web.

Key IDs are derived from the public keys. Set `LANGFUSE_AI_GATEWAY_JWT_PREVIOUS_KEY_ID` only if you set `LANGFUSE_AI_GATEWAY_JWT_KEY_ID` explicitly.

## Troubleshooting [#troubleshooting]

**The UI says the AI Gateway isn't deployed.** Web does not have `LANGFUSE_AI_GATEWAY_DEPLOYED=true`. Check that `langfuse.gateway.enabled` is `true` and that web runs `v4.72.0` or later. If the gateway pages are still missing, check that `LANGFUSE_MIGRATION_V4_WRITE_MODE` is not `legacy` and, when `LANGFUSE_AI_GATEWAY_ENABLED=false`, that your organization is on the allowlist.

**Gateway pods are not ready.** `/ready` returns `503` until the gateway has a web URL and service key. Check the pod logs: invalid configuration fails at startup with the name of the offending variable.

**Requests fail with `401`.** Check that the client sends a gateway API key, not a Langfuse project API key, and that the key has not been revoked.

**Every request fails while `/ready` returns `200`.** `/ready` does not check web. Check the gateway logs for failed calls to web: either the gateway cannot reach `LANGFUSE_AI_GATEWAY_WEB_URL`, or the service key differs between web and the gateway. To change the service key without failing requests, follow [Rotate keys](#rotate-keys).

**Long responses stop after 60 seconds or arrive all at once.** A proxy in front of the gateway has a short timeout or buffers responses. See [Proxy timeouts and buffering](#timeouts).

**Large requests fail with `413`.** Raise the body size limit of your Ingress controller, for example `nginx.ingress.kubernetes.io/proxy-body-size: "17m"`.

**Streams break during deployments.** Streams longer than `connectionDrainTimeoutSeconds` are cut when a pod stops. Check the values in [Graceful shutdown](#graceful-shutdown) and that `terminationGracePeriodSeconds` is greater than their sum.

**Requests succeed but no generations appear in Langfuse.** The gateway uploads generations to web after each request. Check the gateway logs for upload errors, and check that web runs the v4 data model, not the `legacy` write mode.

**Image pull fails with `401` or `unauthorized`.** Pull the gateway image from `ghcr.io/langfuse/ai-gateway` by setting `langfuse.gateway.image.repository`.

**Provider calls fail with TLS errors after you set `SSL_CERT_FILE`.** The bundle replaces the trust store, so it must also contain the public root certificates. See [Gateway to Langfuse Web](#gateway-to-web).

**Clients report certificate errors.** The certificate must cover the gateway host and include the full chain. Test with `curl -v https://<gateway-host>/health`.

When you report a problem, include the `langfuse-request-id` response header of the failing request.

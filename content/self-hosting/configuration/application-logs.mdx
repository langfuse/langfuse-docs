# Export application logs to ClickStack

This guide walks through exporting application logs from a self-hosted Langfuse deployment to ClickHouse, then reading them in ClickStack.

It starts from a Langfuse instance already running on Kubernetes with the [Helm chart](/self-hosting/deployment/kubernetes-helm). That chart runs two deployments:

- `langfuse-web` serves the UI and API.
- `langfuse-worker` runs background jobs.

Both write their logs to stdout. With `langfuse.logging.format` set to `json`, each line is a JSON object. The steps below collect those lines from the node, store them in ClickHouse Cloud, and open them in ClickStack.

Store these logs in a second ClickHouse Cloud service. Langfuse already has one, set with `CLICKHOUSE_URL` in the Helm values, and that service holds traces, observations, and scores. Leave it for Langfuse. Application logs go to their own ClickHouse Cloud service so the two stay isolated: separate compute, storage, credentials, and schema. The gateway creates `otel_logs` on the logs service. Reusing Langfuse's service would put that table, and the log insert load, on the same service Langfuse uses for product data.

Langfuse can also send its own OpenTelemetry traces to a collector with `OTEL_EXPORTER_OTLP_ENDPOINT` ([Observability via OpenTelemetry](/self-hosting/configuration/observability)). That setting does not ship stdout logs. This guide collects the log files on each node instead.

## How the pieces fit together

Langfuse does not push stdout logs anywhere. Kubernetes writes each container's stdout to a file on the node. Two collectors sit between those files and ClickStack:

- An **OpenTelemetry Collector agent** runs on every node, reads the Langfuse log files, and forwards them with OTLP. It uses the contrib collector image because that build includes the `file_log` receiver.
- A **ClickStack collector** runs as a single gateway Deployment. It receives that OTLP stream and writes it to ClickHouse.

The agent could write to ClickHouse itself. The contrib ClickHouse exporter creates an `otel_logs` table by default too. The gateway is there for three reasons:

- It ships ClickStack's own exporter settings and schema. That is what lets ClickStack detect the source and map its columns automatically.
- ClickHouse credentials stay in one Deployment instead of on every node.
- Logs from every node are batched in one place, so ClickHouse gets fewer, larger inserts.

| Component                       | Where it runs                                                        | Role in this setup                                                           |
| ------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Langfuse web                    | Pod `langfuse-web`                                                   | Writes application logs to stdout.                                           |
| Langfuse worker                 | Pod `langfuse-worker`                                                | Writes application logs to stdout.                                           |
| OpenTelemetry collector (agent) | DaemonSet, one pod per node                                          | Reads Langfuse container logs, parses the JSON, and forwards them over OTLP. |
| ClickStack collector (gateway)  | Deployment                                                           | Receives OTLP and inserts rows into ClickHouse using the ClickStack schema.  |
| ClickHouse Cloud (logs)         | Its own Cloud service, separate from the service in `CLICKHOUSE_URL` | Stores the logs in the `otel` database.                                      |
| ClickStack                      | UI connected to that ClickHouse service                              | Search, filter, and read the logs.                                           |

## What you configure

Three changes stand up this path: JSON logging on Langfuse, the ClickStack gateway, and the node agent that sends logs to that gateway. Postgres, Redis, S3, and the ClickHouse Cloud service Langfuse uses for traces stay as they are. The gateway gets a different ClickHouse endpoint from `CLICKHOUSE_URL`.

Deploy the gateway before the agent. The agent exports to the gateway Service, so that Service has to exist first.

### 1. Turn on JSON logs for web and worker

Langfuse accepts a log format in the Helm values. JSON is what makes the later parsing step possible: the agent reads `level` and `message` from each line and turns them into the severity and body ClickStack displays. Plain-text lines are still collected, but they stay a single unparsed string.

`langfuse.logging.format` maps to [`LANGFUSE_LOG_FORMAT`](/self-hosting/configuration). `langfuse.logging.level` maps to `LANGFUSE_LOG_LEVEL`.

```yaml
langfuse:
  logging:
    level: info
    format: json
```

`format: json` applies to both web and worker. Each line is one JSON object. `level` sets how much is written (`error`, `warn`, `info`, `debug`, `trace`).

A pod label is optional. The agent copies every pod label onto the log record, so you can filter on it in ClickStack. The agent decides which files to read by namespace, so logs are collected whether or not this label is set.

```yaml
langfuse:
  web:
    pod:
      labels:
        observability/logs: clickstack
  worker:
    pod:
      labels:
        observability/logs: clickstack
```

Upgrade the existing Helm release with the same values file you used to install Langfuse:

```bash
helm upgrade langfuse langfuse/langfuse -n langfuse -f <your-values-file>.yaml
```

Check that both deployments are writing JSON:

```bash
kubectl -n langfuse logs deploy/langfuse-web --tail=5
kubectl -n langfuse logs deploy/langfuse-worker --tail=5
```

A line looks like `{"level":"info","message":"..."}`. A plain-text line means `format: json` is not on the running pods. The usual cause is an upgrade that omitted `-f` and reused the previous values.

### 2. Deploy the ClickStack collector

The gateway is the OpenTelemetry Collector Helm chart in Deployment mode, with the image replaced by the ClickStack collector (`docker.clickhouse.com/clickhouse/clickstack-otel-collector`). That image comes preconfigured with the schema ClickStack reads. On first start it creates `otel_logs` and a few related tables in the database you name.

It listens for OTLP on gRPC port 4317 and HTTP port 4318, and writes to ClickHouse with credentials from a Secret:

| Variable                                    | Purpose                                                                                                                                       |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `CLICKHOUSE_ENDPOINT`                       | HTTPS URL of the ClickHouse Cloud service created for logs, including port `8443`. This is a different host from Langfuse's `CLICKHOUSE_URL`. |
| `CLICKHOUSE_USER`                           | The `clickstack_ingest` user created below.                                                                                                   |
| `CLICKHOUSE_PASSWORD`                       | Password for that user.                                                                                                                       |
| `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE` | Database name. This setup uses `otel`.                                                                                                        |

On the logs ClickHouse Cloud service, open the SQL console as the admin user (`default`) and create a database and an ingest user for the collector. Run this on the logs service, not on the ClickHouse Cloud service Langfuse uses for traces.

```sql
CREATE DATABASE otel;
CREATE USER clickstack_ingest IDENTIFIED WITH sha256_password BY '<password>';
GRANT SELECT, INSERT, CREATE DATABASE, CREATE TABLE, CREATE VIEW ON otel.* TO clickstack_ingest;
```

`SELECT` and `INSERT` let the collector write and read rows. `CREATE DATABASE`, `CREATE TABLE`, and `CREATE VIEW` let it create `otel_logs` and the related tables on first start. The user is limited to `otel.*`.

Create the Secret from that same logs service. Its host, user, and password are separate from the ClickHouse Langfuse is configured with. A different database name on Langfuse's service is not enough: the two Cloud services stay isolated.

```bash
kubectl -n langfuse create secret generic clickhouse-cloud \
  --from-literal=CLICKHOUSE_ENDPOINT='https://<logs-service>.<region>.aws.clickhouse.cloud:8443' \
  --from-literal=CLICKHOUSE_USER='clickstack_ingest' \
  --from-literal=CLICKHOUSE_PASSWORD='<password>'
```

Use the same password in the `CREATE USER` statement and in `CLICKHOUSE_PASSWORD`.

Save the gateway values as `clickstack-gateway-values.yaml`:

```yaml
mode: deployment
fullnameOverride: clickstack-otel-collector

image:
  repository: docker.clickhouse.com/clickhouse/clickstack-otel-collector
  tag: "2.40.0"

replicaCount: 1

ports:
  otlp:
    enabled: true
  otlp-http:
    enabled: true
  jaeger-compact:
    enabled: false
  jaeger-thrift:
    enabled: false
  jaeger-grpc:
    enabled: false
  zipkin:
    enabled: false

resources:
  requests: { cpu: 200m, memory: 1Gi }
  limits: { memory: 2Gi }

extraEnvs:
  - name: CLICKHOUSE_ENDPOINT
    valueFrom:
      secretKeyRef:
        name: clickhouse-cloud
        key: CLICKHOUSE_ENDPOINT
  - name: CLICKHOUSE_USER
    valueFrom:
      secretKeyRef:
        name: clickhouse-cloud
        key: CLICKHOUSE_USER
  - name: CLICKHOUSE_PASSWORD
    valueFrom:
      secretKeyRef:
        name: clickhouse-cloud
        key: CLICKHOUSE_PASSWORD
  - name: HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE
    value: otel
```

Install the gateway:

```bash
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update

helm upgrade --install clickstack-gateway open-telemetry/opentelemetry-collector \
  --version 0.175.1 \
  -n langfuse \
  -f clickstack-gateway-values.yaml
```

`fullnameOverride: clickstack-otel-collector` sets the Service name. The agent in the next step sends logs to that name. After the pod is running, connect ClickStack to this same ClickHouse Cloud service. Creating the Logs source in the UI is a separate step, covered below.

The image ships its own collector configuration, tuned for ClickHouse inserts with batching, compression, retries, and [asynchronous inserts](https://clickhouse.com/docs/optimize/asynchronous-inserts). The values only set credentials, ports, and resources. The ClickStack collector listens only for OTLP, so the chart's Jaeger and Zipkin ports are off. Raise the resources for high log volumes; ClickHouse sizes a gateway at [about 3 cores and 12 GB of RAM per 60,000 events per second](https://clickhouse.com/docs/clickstack/ingesting-data/collector). Pin the image tag instead of using `latest`, because the collector applies its schema to ClickHouse on start.

#### Choose how long to keep logs

How long to keep Langfuse logs is your decision. The collector sets a TTL on `otel_logs` and its rollup table when it creates them, and rows older than the TTL are deleted. Without a setting, the TTL is 30 days (`720h`).

To use a different retention period, add `HYPERDX_OTEL_EXPORTER_LOGS_TTL` to `extraEnvs` before the first install. The value is in hours, for example `168h` for 7 days or `2160h` for 90 days:

```yaml
extraEnvs:
  # ...the entries above...
  - name: HYPERDX_OTEL_EXPORTER_LOGS_TTL
    value: <hours>h
```

The variable only applies when the tables are created. To change retention after the first start, run this as the admin user on the logs service, with your own interval:

```sql
ALTER TABLE otel.otel_logs MODIFY TTL toDateTime(Timestamp) + INTERVAL 90 DAY;
ALTER TABLE otel.otel_logs_kv_rollup_15m MODIFY TTL Timestamp + INTERVAL 90 DAY;
```

### 3. Deploy the OpenTelemetry collector agent

The agent is the same Helm chart in DaemonSet mode, using `otel/opentelemetry-collector-contrib`. One pod per node tails the log files Kubernetes already wrote for the Langfuse containers and forwards them to the gateway over OTLP/HTTP.

The example values make five choices:

- **Which files are read.** The `file_log` receiver includes only `/var/log/pods/langfuse_*/*/*.log`, which is the `langfuse` namespace. Delete that `include` list to collect every namespace.
- **Kubernetes metadata.** The `kubernetesAttributes` preset adds the namespace, pod name, deployment name, and the pod labels from step 1.
- **Service name.** A resource processor copies `k8s.deployment.name` to `service.name`. ClickStack shows that value as the service, so rows appear as `langfuse-web` or `langfuse-worker`.
- **JSON parsing.** A transform processor runs when the log body starts with `{`. It maps `level` to severity, replaces the body with `message`, and copies the remaining JSON keys to log attributes.
- **Where logs are sent.** The OTLP/HTTP exporter posts to the gateway address stored in a ConfigMap. The exporter appends `/v1/logs`, so the address is the gateway base URL.

The chart's logs preset also strips the container-runtime prefix on disk, so the transform sees the JSON line Langfuse wrote.

Create the ConfigMap in the agent's namespace. The key name has to match `extraEnvs` in the agent values. This example uses `OTEL_COLLECTOR_ENDPOINT`.

```bash
kubectl -n langfuse create configmap otel-config-vars \
  --from-literal=OTEL_COLLECTOR_ENDPOINT=http://clickstack-otel-collector.langfuse.svc.cluster.local:4318
```

Save the agent values as `otel-agent-values.yaml`:

```yaml
mode: daemonset

image:
  repository: "otel/opentelemetry-collector-contrib"
  tag: "0.162.0"

presets:
  logsCollection:
    enabled: true
    includeCollectorLogs: false
  kubernetesAttributes:
    enabled: true
    extractAllPodLabels: true
    extractAllPodAnnotations: true

extraEnvs:
  - name: OTEL_COLLECTOR_ENDPOINT
    valueFrom:
      configMapKeyRef:
        name: otel-config-vars
        key: OTEL_COLLECTOR_ENDPOINT

tolerations:
  - operator: Exists

resources:
  requests: { cpu: 100m, memory: 256Mi }
  limits: { memory: 512Mi }

config:
  receivers:
    file_log:
      include:
        - /var/log/pods/langfuse_*/*/*.log
      exclude: []
  processors:
    resource/langfuse:
      attributes:
        - key: service.name
          from_attribute: k8s.deployment.name
          action: upsert
    transform/langfuse:
      error_mode: ignore
      log_statements:
        - context: log
          conditions:
            - IsMatch(body, "^\\s*\\{")
          statements:
            - merge_maps(cache, ParseJSON(body), "upsert")
            - set(severity_text, cache["level"]) where cache["level"] != nil
            - set(severity_number, SEVERITY_NUMBER_TRACE) where severity_text == "trace"
            - set(severity_number, SEVERITY_NUMBER_DEBUG) where severity_text == "debug"
            - set(severity_number, SEVERITY_NUMBER_INFO) where severity_text == "info"
            - set(severity_number, SEVERITY_NUMBER_WARN) where severity_text == "warn"
            - set(severity_number, SEVERITY_NUMBER_ERROR) where severity_text == "error"
            - set(severity_number, SEVERITY_NUMBER_FATAL) where severity_text == "fatal"
            - set(body, cache["message"]) where cache["message"] != nil
            - delete_key(cache, "message")
            - delete_key(cache, "level")
            - merge_maps(attributes, cache, "insert")
  exporters:
    otlp_http:
      endpoint: "${env:OTEL_COLLECTOR_ENDPOINT}"
      compression: gzip
      sending_queue:
        enabled: true
        queue_size: 5000
      retry_on_failure:
        enabled: true
  service:
    pipelines:
      logs:
        processors: [memory_limiter, resource/langfuse, transform/langfuse, batch]
        exporters: [otlp_http]
      metrics:
        exporters: [otlp_http]
      traces:
        exporters: [otlp_http]
```

Pin the contrib version (`0.162.0` or newer) instead of `latest`.

Install the agent:

```bash
helm upgrade --install otel-agent open-telemetry/opentelemetry-collector \
  --version 0.175.1 \
  -n langfuse \
  -f otel-agent-values.yaml
```

The DaemonSet has to land on every node that runs Langfuse. The example values tolerate every taint so a tainted Langfuse node group is still covered.

The gateway accepts OTLP from inside the cluster without authentication. To require a token, store one in a Secret, set it as `OTLP_AUTH_TOKEN` in the gateway's `extraEnvs`, and send the same value from the agent. Add the token to the agent's `extraEnvs` from that Secret, then add the header to the agent exporter:

```yaml
config:
  exporters:
    otlp_http:
      headers:
        authorization: Bearer ${env:OTLP_AUTH_TOKEN}
```

## Read the logs in ClickStack

ClickStack does not query `otel_logs` until you define a Logs source. The UI needs that source to know which table to read and which columns are the timestamp, service, severity, and body. With the default OpenTelemetry schema those columns are filled in for you. The database is not: the form defaults to `default`, and this setup writes to `otel`.

In ClickStack, open **Team Settings → Sources** and add a Logs source:

| Setting           | Value                                                                                                 |
| ----------------- | ----------------------------------------------------------------------------------------------------- |
| Name              | A name you will recognize in log search, such as `Langfuse Logs`.                                     |
| Source Data Type  | `Logs`                                                                                                |
| Server Connection | The connection for the logs ClickHouse Cloud service, not the service in Langfuse's `CLICKHOUSE_URL`. |
| Database          | `otel`                                                                                                |
| Table             | `otel_logs`                                                                                           |

Leave **Timestamp Column** and **Default Select** on the values ClickStack infers from the table. Save the source. Column reference: [ClickStack source settings](https://clickhouse.com/docs/clickstack/managing/config).

<Frame fullWidth>
  ![ClickStack Logs source: Name Langfuse Logs, Source Data Type Logs, database otel, table otel_logs](/images/docs/clickstack-logs-source.png)
</Frame>

Open log search and select that source.

<Frame fullWidth>
  ![ClickStack log search on the Langfuse Logs source, with langfuse-web and langfuse-worker rows showing timestamp, service, level, and body](/images/docs/clickstack-log-search.png)
</Frame>

| What you see in ClickStack | Where it comes from                                                                                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------- |
| Service                    | `service.name`, copied from the deployment name. Filter `langfuse-web` or `langfuse-worker`.             |
| Severity                   | The JSON `level` field (`info`, `warn`, `error`, and so on).                                             |
| Body                       | The JSON `message` field.                                                                                |
| Log attributes             | Every other key in the JSON line.                                                                        |
| Resource attributes        | Kubernetes metadata: namespace, pod, deployment, and pod labels such as `observability/logs=clickstack`. |

To confirm the path is complete, filter ClickStack to service `langfuse-web` and severity `error`, then compare with `kubectl logs` for that deployment. The same lines should show up in both places.

The same rows are in ClickHouse if you want to check the table directly:

```sql
SELECT Timestamp, ServiceName, SeverityText, Body
FROM otel.otel_logs
WHERE ServiceName IN ('langfuse-web', 'langfuse-worker')
ORDER BY Timestamp DESC
LIMIT 20
```

## When logs do not show up

| What you see                                                           | What to check                                                                                                                                                          |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The Langfuse upgrade succeeded, and `kubectl logs` is still plain text | The upgrade omitted `-f`, or `langfuse.logging.format` is not `json`.                                                                                                  |
| Agent pods are running and ClickStack is empty                         | `otel-config-vars` / `OTEL_COLLECTOR_ENDPOINT` is the gateway base URL (`http://clickstack-otel-collector.langfuse.svc.cluster.local:4318`), in the agent's namespace. |
| Gateway logs show authentication errors                                | The agent's `authorization` header does not match `OTLP_AUTH_TOKEN` on the gateway.                                                                                    |
| Rows exist in `otel_logs` and Service is empty                         | `k8s.deployment.name` was missing, so `service.name` was not set. Confirm the `kubernetesAttributes` preset is enabled.                                                |
| Langfuse traces are absent from the logs ClickHouse service            | This service receives stdout logs. Traces stay on the ClickHouse Cloud service set in `CLICKHOUSE_URL`.                                                                |
| Logs from other namespaces appear                                      | The agent `file_log` include is not limited to `/var/log/pods/langfuse_*/*/*.log`.                                                                                     |

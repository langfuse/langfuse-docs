# Hardening

Langfuse ships with safe defaults and is penetration-tested for the same configuration that runs on [Langfuse Cloud](/security). This guide collects the additional operator-facing knobs that self-hosters typically want to turn on for production: locking down sign-ups, enforcing SSO, restricting which destinations user-configured integrations may reach, and tightening admin surfaces.

For related operational guides, see [Authentication and SSO](/self-hosting/security/authentication-and-sso), [Networking](/self-hosting/security/networking), [Encryption](/self-hosting/configuration/encryption), and [Deployment Strategies](/self-hosting/security/deployment-strategies).

Langfuse Self-Hosted Enterprise supports government and other highly regulated environments with:

- **[FIPS mode](#fips-mode):** Langfuse runs its cryptography on FIPS 140-3 validated cryptographic modules operated in approved mode, and refuses to start when it cannot.
- **[Hardened images](#hardened-images):** the web and worker images are built on Iron Bank's hardened Red Hat Universal Base Image (UBI) 9.

We are also working on end-to-end documentation for operating Langfuse and all required subcomponents as a complete air-gapped deployment stack. [Contact our sales team](/talk-to-us?deployment=self-hosted) to discuss your requirements.

### FIPS mode [#fips-mode]

The Cryptographic Module Validation Program (CMVP) validates cryptographic modules, not products. Langfuse holds no FIPS 140-3 certificate of its own. In FIPS mode, the Langfuse containers use the validated modules listed below in approved mode, and check this at startup. Algorithms that are not approved, such as MD5, fail.

FIPS mode is available from Langfuse v4.55.0. Use v4.57.0 or later: that release hashes passwords with PBKDF2-HMAC-SHA256 instead of bcrypt in FIPS mode, stops computing bcrypt for new API keys, and refuses storage options that need MD5 at startup.

#### Cryptographic modules [#fips-modules]

| Component                                           | Used for                                                                                                                                                       | Validated module                                   | CMVP certificate                                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Node.js (web and worker)                            | TLS to ClickHouse, Redis, blob storage, SSO and LLM providers; hashing; [application-level encryption](/self-hosting/configuration/encryption); session tokens | Red Hat Enterprise Linux 9 - OpenSSL FIPS Provider | [#4857](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/4857) |
| Prisma engines (web and worker)                     | TLS to Postgres                                                                                                                                                | Red Hat Enterprise Linux 9 - OpenSSL FIPS Provider | [#4857](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/4857) |
| ClickHouse migration CLI (`migrate`, web container) | TLS to ClickHouse during migrations                                                                                                                            | Go Cryptographic Module v1.0.0                     | [#5247](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/5247) |

Node.js and the Prisma engines link the image's system OpenSSL library, so their cryptography runs in Red Hat's FIPS provider. The migration CLI is built with `GOFIPS140=v1.0.0`, which turns on the Go module's FIPS 140-3 mode.

**Tested environments:** certificate #4857 lists Red Hat Enterprise Linux 9 on x86_64 (Intel Xeon), IBM POWER10, and IBM z16. Running the `linux/amd64` images on RHEL 9 hosts in FIPS mode matches a tested environment. Confirm other host operating systems and `linux/arm64` with your assessor.

**Module build:** the FIPS provider comes from the `openssl-fips-provider-so` package in the UBI 9 repositories. Red Hat rebuilds this package for security fixes, so the build in the image can be newer than the build listed on the certificate while its revalidation is in process. Check the package version that your image scanner reports against the certificate and the CMVP [Modules In Process list](https://csrc.nist.gov/projects/cryptographic-module-validation-program/modules-in-process/modules-in-process-list).

#### Requirements [#fips-requirements]

- **Enterprise license:** an Enterprise license key (`LANGFUSE_EE_LICENSE_KEY`) on both containers. See [License Key](/self-hosting/license-key).
- **Host FIPS mode:** the hosts that run the containers must boot in FIPS mode (`cat /proc/sys/crypto/fips_enabled` returns `1`). The FIPS provider follows the host kernel's FIPS mode, so a container cannot turn it on by itself.
- **Infrastructure:** you are responsible for running Postgres, ClickHouse, Redis, blob storage, and the load balancer or ingress that terminates TLS for Langfuse with validated modules. In particular:
  - Use `scram-sha-256` password authentication for Postgres. `md5` authentication is not available on a Postgres server in FIPS mode.
  - Do not set `LANGFUSE_S3_DELETE_OBJECTS_CHECKSUM_ALGORITHM=MD5`. MinIO versions before `RELEASE.2025-02-03` require it and are therefore not supported.
  - Do not use the native OCI Object Storage integration (`LANGFUSE_USE_OCI_NATIVE_OBJECT_STORAGE=true`); the OCI SDK hashes every upload part with MD5. Use OCI's S3-compatible API instead.

#### Enable FIPS mode [#enable-fips-mode]

Set the following on both the web and the worker container:

```bash
LANGFUSE_REQUIRE_FIPS=true
LANGFUSE_EE_LICENSE_KEY=<your-license-key>
```

When `LANGFUSE_REQUIRE_FIPS=true` is set, startup fails closed:

1. The image entrypoint sets `OPENSSL_CONF=/etc/pki/tls/openssl-fips.cnf`, which applies Red Hat's FIPS crypto policy to OpenSSL. An `OPENSSL_CONF` you set yourself takes precedence.
2. The entrypoint exits before running database migrations if Node.js reports that the FIPS provider is not active.
3. The web and worker processes check again before they connect to any database. They also require an Enterprise license and reject storage options that need MD5. These checks also run when your deployment overrides the image entrypoint. In that case, set `OPENSSL_CONF=/etc/pki/tls/openssl-fips.cnf` yourself.

If a check fails, the container logs the reason and exits:

| Log message contains                         | Cause                                          | Fix                                       |
| -------------------------------------------- | ---------------------------------------------- | ----------------------------------------- |
| `requires a Langfuse enterprise license`     | No Enterprise license key is configured.       | Set `LANGFUSE_EE_LICENSE_KEY`.            |
| `Node's OpenSSL FIPS provider is not active` | The host does not run in FIPS mode.            | Run the containers on hosts in FIPS mode. |
| `cannot be combined with`                    | A storage option that needs MD5 is configured. | Change the option named in the message.   |

A running container with `LANGFUSE_REQUIRE_FIPS=true` has passed these checks. To check the module by hand, for example during an assessment, run Node.js in the container with the same OpenSSL configuration:

```bash
docker exec <langfuse-web-container> sh -c \
  'OPENSSL_CONF=/etc/pki/tls/openssl-fips.cnf node -p "require(\"node:crypto\").getFips()"'
# 1

docker exec <langfuse-web-container> sh -c \
  'OPENSSL_CONF=/etc/pki/tls/openssl-fips.cnf node -e "require(\"node:crypto\").createHash(\"md5\")"'
# Error: ... unsupported
```

#### Passwords [#fips-passwords]

In FIPS mode, Langfuse hashes and verifies email/password credentials only with PBKDF2-HMAC-SHA256 (600,000 iterations), and never runs bcrypt. Passwords set before you turned on FIPS mode are stored as bcrypt hashes, which FIPS mode does not verify. Those users cannot sign in until they set a new password:

- Sign-in fails with: `This instance runs in FIPS mode and your password must be reset.`
- Users set a new password with the **forgot password?** link on the sign-in page. Password reset sends a code by email, so configure [transactional emails](/self-hosting/configuration/transactional-emails) before you turn on FIPS mode, or move users to [SSO](/self-hosting/security/authentication-and-sso).
- Users who sign in with SSO are not affected.

If you turn FIPS mode off later, PBKDF2 passwords keep working: instances without FIPS mode verify both formats and write bcrypt for new passwords.

#### Known limitations [#fips-limitations]

- **Legacy API keys:** API keys created by early Langfuse versions, before keys were hashed with SHA-256, are checked once with bcrypt on first use and then re-hashed with SHA-256. Rotate such keys to avoid bcrypt entirely.

### Hardened images [#hardened-images]

From v4.55.0, the `langfuse/langfuse` (web) and `langfuse/langfuse-worker` images:

- Are built on Iron Bank's hardened Red Hat UBI 9 images (`registry1.dso.mil/ironbank/redhat/ubi/ubi9` and `ubi9-micro`, version 9.8).
- Run Node.js 24 from Red Hat's packages, which links the system OpenSSL library and its FIPS provider.
- Ship no package manager, `curl`, or Python. The runtime contains `bash`, `sed`, and `wget`; use `wget` for [container health checks](/self-hosting/configuration/health-readiness-endpoints#container-health-checks).
- Run as a non-root user with the numeric UID `1001`.
- Keep the RPM database, so image scanners such as Trivy, Grype, or Syft can list every OS package.
- Are published for `linux/amd64` and `linux/arm64`.

Images that extend the Langfuse images cannot install packages with a package manager. Use a multi-stage build to copy additional files in.

The Dockerfiles default to Red Hat's public UBI 9 images, so you can [build the images yourself](/self-hosting/deployment/infrastructure/containers#build-from-source) without credentials. To build on the Iron Bank images instead, log in to `registry1.dso.mil` and pass both base images:

```bash
docker build -f web/Dockerfile \
  --build-arg BASE_IMAGE=registry1.dso.mil/ironbank/redhat/ubi/ubi9:9.8 \
  --build-arg MICRO_BASE_IMAGE=registry1.dso.mil/ironbank/redhat/ubi/ubi9-micro:9.8 \
  .
```

## Restrict who can sign in [#access]

By default, anyone who can reach the Langfuse web container can sign up with email and password. Pick one of the following profiles before exposing the instance. For more details on authentication configuration, see [Authentication and SSO](/self-hosting/security/authentication-and-sso).

### Disable open sign-up [#disable-signup]

`AUTH_DISABLE_SIGNUP=true` blocks any new account creation, including users who have an open project invite but no account yet. Combine with [headless initialization](/self-hosting/administration/headless-initialization) or invite existing users from inside the app. Nobody signs up on such an instance, so nobody sees the newsletter step that new users get after sign-up either. To get the self-hosting updates, subscribe on the [OSS newsletter](/self-hosting/oss-newsletter) page.

### Force SSO for specific email domains [#sso-enforcement]

`AUTH_DOMAINS_WITH_SSO_ENFORCEMENT=acme.com,corp.example` rejects email/password sign-in (including the password-reset OTP path) for the listed domains and directs those users to sign in through your configured SSO provider instead. Use this when only part of your user base is on SSO.

### Require email verification on signup [#email-verification]

`AUTH_EMAIL_VERIFICATION_REQUIRED=true` adds a one-time-password step before a new email/password user can set their password. SSO sign-in is unaffected. Requires [transactional emails](/self-hosting/configuration/transactional-emails) to be configured. See [Email verification on signup](/self-hosting/security/authentication-and-sso#email-verification-on-signup) for the full flow.

### Session lifetime [#session-lifetime]

`AUTH_SESSION_MAX_AGE` controls how long a signed-in session (JWT) stays valid, in minutes. Default is `43200` (30 days); the value must be greater than 5 minutes because the front-end refreshes its session every 5 minutes. Lower this for shared or kiosk environments.

### Disable email/password entirely [#disable-password]

If every user signs in via SSO, set `AUTH_DISABLE_USERNAME_PASSWORD=true`. Account linking can be enabled per-provider with `AUTH_<PROVIDER>_ALLOW_ACCOUNT_LINKING=true` — only enable it when your IdP guarantees verified emails.

## Outbound URL allowlists (SSRF defense) [#outbound-url-allowlists]

Several features let project members configure a URL that Langfuse then calls on their behalf — LLM API base URLs, webhook targets, blob storage integration endpoints, and external media storage endpoints. Langfuse rejects URLs whose resolved IPs fall into private, link-local, loopback, or special-use ranges (including NAT64 and 6to4 IPv6 ranges), rejects URLs with embedded credentials (`user:password@`), and re-validates the IP at request time and on every redirect hop to defend against DNS rebinding.

On Langfuse Cloud this is always strict. Self-hosted instances validate LLM connection, webhook, and external media storage URLs by default too; blob storage endpoint validation only activates once one of its allowlist variables is set (see below). The allowlist variables let user-configured integrations reach internal services or restrict outbound traffic to specific hosts:

| Use case                                    | Allowlist variables                                                                                                                                                                                                                                            |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User-configured LLM connections             | `LANGFUSE_LLM_CONNECTION_WHITELISTED_HOST`<br/>`LANGFUSE_LLM_CONNECTION_WHITELISTED_IPS`<br/>`LANGFUSE_LLM_CONNECTION_WHITELISTED_IP_SEGMENTS`<br/>`LANGFUSE_LLM_CONNECTION_ALLOWED_HOSTS`                                                                     |
| User-configured webhooks                    | `LANGFUSE_WEBHOOK_WHITELISTED_HOST`<br/>`LANGFUSE_WEBHOOK_WHITELISTED_IPS`<br/>`LANGFUSE_WEBHOOK_WHITELISTED_IP_SEGMENTS`<br/>`LANGFUSE_WEBHOOK_ALLOWED_HOSTS`                                                                                                 |
| User-configured blob storage integrations   | `LANGFUSE_BLOB_STORAGE_ENDPOINT_WHITELISTED_HOST`<br/>`LANGFUSE_BLOB_STORAGE_ENDPOINT_WHITELISTED_IPS`<br/>`LANGFUSE_BLOB_STORAGE_ENDPOINT_WHITELISTED_IP_SEGMENTS`                                                                                            |
| User-configured external media integrations | `LANGFUSE_EXTERNAL_MEDIA_STORAGE_ENDPOINT_WHITELISTED_HOST`<br/>`LANGFUSE_EXTERNAL_MEDIA_STORAGE_ENDPOINT_WHITELISTED_IPS`<br/>`LANGFUSE_EXTERNAL_MEDIA_STORAGE_ENDPOINT_WHITELISTED_IP_SEGMENTS`<br/>`LANGFUSE_EXTERNAL_MEDIA_STORAGE_ENDPOINT_ALLOWED_HOSTS` |

Each variable accepts a comma-separated list. Hostnames in `_WHITELISTED_HOST` short-circuit the IP check entirely; `_WHITELISTED_IPS` / `_WHITELISTED_IP_SEGMENTS` are matched against every IP a hostname resolves to while keeping public hosts allowed. Setting `*_ALLOWED_HOSTS` to a non-empty list of exact lowercase hostnames (no scheme or port; unset or empty keeps default-allow behavior) switches that surface to a positive allowlist where **only** listed hosts are permitted and all other hosts — including public ones — are rejected. You can also set `LANGFUSE_OUTBOUND_BLOCKED_IP_SEGMENTS` to a comma-separated list of IPv4 or IPv6 CIDR ranges to block additional IP ranges across outbound checks. Set `_WHITELISTED_*` values only for trusted internal endpoints (your in-cluster SeaweedFS or MinIO, an internal LLM gateway, …), and note that every host listed in `_WHITELISTED_HOST` or `*_ALLOWED_HOSTS` (including public provider hosts) is trusted even if its DNS resolves to a private IP, bypassing the private-IP and DNS-rebinding checks for that host. Blob storage validation activates only once one of its variables is set on a self-hosted instance; this default will change to strict in a future major release.

Webhook deliveries are additionally restricted to ports 80 and 443, and sensitive headers (`Authorization`, `Cookie`, `Proxy-Authorization`, `x-langfuse-signature`) are dropped on cross-origin redirects. Provide webhook credentials via headers configured in the webhook UI rather than in the URL.

## Code evaluators [#code-evaluators]

[Code evaluators](/self-hosting/configuration/code-evaluators) let project members write evaluator code that Langfuse executes. On self-hosted instances they are disabled until you set `LANGFUSE_CODE_EVAL_DISPATCHER`, and the dispatcher you pick determines the isolation boundary:

- `insecure-local` runs evaluator code in-process on the worker via `node:vm`, which is **not a security boundary** — evaluator code can reach everything the worker can, including your databases, queues, and cloud credentials. Only use it when everyone who can create evaluators is fully trusted.
- `aws-lambda` dispatches evaluator code to Lambda functions you deploy, keeping execution out of the worker process. Langfuse Cloud uses this dispatcher with executor functions running in an isolated network without egress to internal services; apply the same principle when deploying your own — give the functions no network route back into your infrastructure.

See [Code evaluators (self-hosted)](/self-hosting/configuration/code-evaluators) for the full dispatcher setup.

## Admin API [#admin-api]

The self-hosted-only [Instance Management API](/self-hosting/administration/instance-management-api) is gated by `ADMIN_API_KEY`. When you enable it:

- Pick a high-entropy random value (≥ 32 bytes) — short keys are trivially brute-forceable.
- Treat the key as you would a root credential — restrict it to a small set of operators, rotate it on personnel changes, and never expose it to the browser or to less-privileged services.
- Do not expose admin endpoints to the public internet. Bind them to an internal load balancer or restrict them with a reverse proxy.
- Langfuse Cloud blocks the admin API; nothing in this section applies there.

## SSO configuration [#sso]

A few knobs worth knowing about when configuring SSO providers via environment variables:

- **Issuer validation** — set `AUTH_<PROVIDER>_ISSUER` to your IdP's exact issuer URL. Tokens are validated against it at sign-in rather than silently accepted from the wrong issuer, and `AUTH_CUSTOM_ISSUER` must additionally be a valid URL and is checked at startup. GitHub's issuer is pinned in code and needs no configuration.
- **ID token signing algorithm** — set `AUTH_<PROVIDER>_ID_TOKEN_SIGNED_RESPONSE_ALG` to align the expected signing algorithm with your IdP if it rejects the default.

See the full reference in [Authentication and SSO → Additional configuration](/self-hosting/security/authentication-and-sso#additional-configuration).

## Network exposure [#network-exposure]

Only the `langfuse/langfuse` (web) container needs to be reachable by users, the SDKs, and your application code. Langfuse is designed to be exposed publicly, but for high-security environments you can:

- Terminate TLS at a load balancer in front of the web container (see [Encryption](/self-hosting/configuration/encryption)).
- Put the web container behind a VPN, internal load balancer, or zero-trust proxy.
- Peer your application VPCs with the Langfuse VPC for private SDK ingestion traffic. Worker, Postgres, ClickHouse, Redis, and blob storage should never be reachable from the public internet.

See [Networking](/self-hosting/security/networking) for the full architecture diagram and per-component exposure recommendations.

## Data protection [#data]

- **Encryption at rest** — Postgres and ClickHouse should run with disk encryption. Configure [server-side encryption](/self-hosting/deployment/infrastructure/blobstorage#using-aws-kms-encryption) on the event-upload and media buckets.
- **Sensitive integration secrets** (LLM API keys, blob storage credentials, SSO client secrets, webhook secrets) are encrypted at the application layer using `ENCRYPTION_KEY`. Rotate the key per the [Encryption](/self-hosting/configuration/encryption) guide.
- **Data masking** — see [Data masking](/self-hosting/security/data-masking) to redact sensitive content from ingested traces before it lands in storage.

## Telemetry [#telemetry]

Langfuse self-hosted reports anonymized usage telemetry by default. Set `TELEMETRY_ENABLED=false` to opt out; note that instances running with an Enterprise Edition license key always report telemetry. See [Telemetry](/self-hosting/security/telemetry) for the exact fields collected. `TELEMETRY_ENABLED` doesn't cover the [newsletter step](/self-hosting/security/telemetry#hostnames-browser): to stop new users' browsers from contacting `langfuse.com` for it, set `LANGFUSE_DISABLE_SIGNUP_ONBOARDING=true`.

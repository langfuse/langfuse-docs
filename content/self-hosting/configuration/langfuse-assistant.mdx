# Langfuse Assistant

This page covers self-hosted infrastructure setup. For an introduction to the feature, see [Langfuse Assistant](/docs/langfuse-assistant).

Assistant runs are durable jobs. The web service admits and enqueues them, and the worker claims and executes them, so both need the same Postgres, Redis, and Langfuse AI model. The queue consumer and the sandbox are worker-only. The Assistant is available on all self-hosted plans and does not require an Enterprise Edition license key.

[Ask AI](/docs/observability/features/filter-search-bar#ask-ai) in the filter search bar uses the same instance-wide model. It is not gated by the Assistant instance switch.

<Callout type="info">
  The Langfuse Assistant is in public beta on self-hosted deployments, from
  version `>=v4.19.0`. Configuration may still change between releases, and new
  capabilities may need infrastructure this page does not describe yet.
</Callout>

## Requirements

| Requirement       | What to set                                                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Instance switch   | `LANGFUSE_IN_APP_AGENT_ENABLED=true` on web and worker. Unset or `false` hides the Assistant.                                           |
| Langfuse AI model | One instance-wide model on web and worker: Amazon Bedrock or the Anthropic Messages API.                                                |
| Worker consumer   | `QUEUE_CONSUMER_IN_APP_AGENT_RUN_QUEUE_IS_ENABLED=true` on the worker that executes runs. The code default is `false`.                  |
| MCP reachability  | The worker must reach this instance's MCP server. See [Worker access to the MCP server](#langfuse-mcp).                                 |
| Organization gate | An organization owner or admin enables **AI Features**. Required for the Assistant and for Ask AI.                                      |
| Sandbox           | Recommended. `LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER=lambda-microvm` on the worker. Without it, the Assistant runs Langfuse tools only. |

## Setup

### 1. Enable the Assistant

Set this on both the web and worker services. Self-hosted instances show the Assistant only when the value is `true`:

```bash
LANGFUSE_IN_APP_AGENT_ENABLED=true
```

Unset or `false` hides the Assistant even when **AI Features** is enabled for the organization. This switch does not gate Ask AI or natural-language filters.

### 2. Configure the model [#configure-the-model]

One instance-wide Langfuse AI model serves the Assistant, Ask AI, and natural-language filters. Set the model on both the web and worker services. `LANGFUSE_AI_PROVIDER` selects between them. Langfuse resolves an unset value to Bedrock.

<Tabs items={["Amazon Bedrock", "Anthropic Messages"]}>

<Tab>

Bedrock authenticates through the instance AWS credential chain or IRSA, so it needs no API key:

```bash
LANGFUSE_AI_PROVIDER=bedrock
LANGFUSE_AI_MODEL=eu.anthropic.claude-opus-5
LANGFUSE_AI_SMALL_MODEL=eu.anthropic.claude-haiku-4-5-20251001-v1:0
LANGFUSE_AI_AWS_BEDROCK_REGION=eu-west-1
```

`LANGFUSE_AI_SMALL_MODEL` generates conversation titles and Ask AI completions, and falls back to `LANGFUSE_AI_MODEL`. The Region is optional when the workload already runs in the Bedrock Region. IDs such as `eu.anthropic.claude-opus-5` are geo inference profiles (`eu.*`, `us.*`, `jp.*`) rather than on-demand foundation-model IDs, so use the profile ID as the model value and enable model access for it in Bedrock.

</Tab>

<Tab>

The Anthropic Messages API needs a provider, a model, and an API key. Incomplete configuration counts as unconfigured:

```bash
LANGFUSE_AI_PROVIDER=anthropic
LANGFUSE_AI_MODEL=claude-opus-5
LANGFUSE_AI_SMALL_MODEL=claude-haiku-4-5
LANGFUSE_AI_API_KEY=sk-ant-...
```

`LANGFUSE_AI_BASE_URL` is optional and accepts any Anthropic-protocol origin. Set an origin only, because Langfuse appends `/v1` when it is missing.

Langfuse Cloud runs on Bedrock in every Region, so the Bedrock path carries more production usage than this one.

</Tab>

</Tabs>

For Bedrock, prefer a workload role or IRSA so both services pick up temporary credentials from the [AWS SDK default credential chain](https://docs.aws.amazon.com/sdkref/latest/guide/standardized-credentials.html). Grant invoke-only permissions. A geo inference profile invokes a foundation model in a destination Region while the SDK still calls `bedrock-runtime` in your configured Region, so a single-Region `foundation-model/*` ARN is not sufficient. Langfuse Cloud uses `Resource: "*"`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": "*"
    }
  ]
}
```

This grants invoke-only access to models, not broader Bedrock administration. If you scope `Resource` to ARNs, include every destination Region the profile can invoke. See [Bedrock inference profile permissions](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html).

### 3. Enable the worker

Set these on the worker that executes Assistant runs. Do not enable them on an ingestion-only worker:

```bash
QUEUE_CONSUMER_IN_APP_AGENT_RUN_QUEUE_IS_ENABLED=true
LANGFUSE_IN_APP_AGENT_INTEGRITY_RUNNER_ENABLED=true
```

Without the queue consumer, background runs are committed but never claimed, and they fail at queue timeout. The integrity runner reconciles runs that a crashed or redeployed worker abandoned, so without it those runs stay in a non-terminal state. Enable it on one worker only. Both variables default to `false`.

### 4. Enable AI Features for your organization

1. Sign in as an organization owner or administrator.
2. Open organization **Settings** and enable **AI Features**.
3. Open the Langfuse Assistant in a project.

### 5. Verify

1. Check the worker log line that reports registering the in-app assistant queue consumer.
2. Send a request such as asking the Assistant to summarize a recent trace. The run should move from queued to running to complete.
3. Ask the Assistant to write a file. That confirms the sandbox. Without a sandbox provider, file tools are unavailable by design.

## Sandbox

The sandbox backs the Assistant's file and code-execution tools. Set `LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER` on the worker to one of the available providers:

| Sandbox            | Value              | Use for                            | Tools                                     |
| ------------------ | ------------------ | ---------------------------------- | ----------------------------------------- |
| AWS Lambda MicroVM | `lambda-microvm`   | Production self-hosted deployments | Langfuse tools, files, and code execution |
| None               | unset              | Deployments that are not on AWS    | Langfuse tools only                       |
| Local Docker       | `dangerous-docker` | Local development                  | Langfuse tools, files, and code execution |

With no provider set, the Assistant still runs its Langfuse tools, and the file and code-execution tools are unavailable. `dangerous-docker` is rejected when `NODE_ENV=production` and is not a sandbox boundary for production workloads.

<Callout type="warning">
  There is no non-AWS sandbox yet. For sandboxed execution on other platforms,
  let us know what support you need in [GitHub
  Discussions](https://github.com/orgs/langfuse/discussions).
</Callout>

Provider, image, execution role, and Region are required together. A partial `lambda-microvm` configuration fails at worker boot:

```bash
LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER=lambda-microvm
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_IMAGE_IDENTIFIER=arn:aws:lambda:<region>:<account-id>:microvm-image:<image-name>
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EXECUTION_ROLE_ARN=arn:aws:iam::<account-id>:role/<execution-role>
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_REGION=<region>
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EGRESS_NETWORK_CONNECTOR_ARN=arn:aws:lambda:<region>:<account-id>:network-connector:<egress-connector-name>
```

<Callout type="warning">
  Production isolation requires the egress network connector. When
  `LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EGRESS_NETWORK_CONNECTOR_ARN`
  is unset, AWS attaches its default `INTERNET_EGRESS` connector and sandboxed
  code reaches the public internet. An invalid connector ARN fails the MicroVM
  launch rather than falling back to internet egress. See [Lambda MicroVM
  networking](https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html).
</Callout>

### Build the MicroVM image

Langfuse does not publish a pullable MicroVM image. AWS builds it in your account from a zip artifact plus an Amazon Linux 2023 base image. You need Lambda MicroVMs in the Region, an AWS CLI with `lambda-microvms` support (2.36.1 is known to work), Docker, pnpm, zip, git, and a checkout of the Langfuse repository.

Create an S3 bucket for the artifact and a MicroVM **build** role that Lambda assumes during `CreateMicrovmImage`. Trust `lambda.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`, allow `s3:GetObject` on the artifact object and writes to the build CloudWatch log groups, and grant it no Langfuse database, application, or secret access.

The caller that runs the script is a separate identity. It needs `s3:PutObject` on the artifact bucket, `lambda:CreateMicrovmImage`, `ListMicrovmImages`, `GetMicrovmImage`, `UpdateMicrovmImage`, and `iam:PassRole` on the build role. Without that `iam:PassRole`, `CreateMicrovmImage` returns `AccessDeniedException`.

Run [`build-microvm-image.sh`](https://github.com/langfuse/langfuse/blob/main/packages/in-app-agent-sandbox-runtime/build-microvm-image.sh) from the repository root:

```bash
export AWS_PROFILE=<profile>
export AWS_REGION=<region>
export S3_BUCKET=<artifact-bucket>
export MICROVM_IMAGE_NAME=langfuse-in-app-agent-sandbox
export LAMBDA_MICROVM_BUILD_ROLE_ARN=arn:aws:iam::<account-id>:role/<build-role>
export BASE_IMAGE_ARN=arn:aws:lambda:<region>:aws:microvm-image:al2023-1
export BASE_IMAGE_VERSION=0

bash packages/in-app-agent-sandbox-runtime/build-microvm-image.sh
```

These values can also live in `packages/in-app-agent-sandbox-runtime/.env`. On success the script prints `IMAGE_ARN`. Use it as `LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_IMAGE_IDENTIFIER`.

### IAM and network isolation [#iam-and-network-isolation]

Create an **execution** role that the MicroVM runs as. Trust `lambda.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`, and attach no policies. User-provided sandbox code runs with this role, so it must not reach Langfuse databases, storage, or secrets.

For production isolation, create a VPC egress network connector that leaves the guest without network access:

1. A security group with no ingress rules and no egress rules.
2. Private or unrouted subnets with no default route to the internet.
3. An operator role that trusts `lambda.amazonaws.com` and `network-connectors.lambda.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`.
4. A Lambda network connector of type VPC egress, associated with MicroVM compute, using that security group and those subnets.

Grant the worker permission to run the image, pass the execution role, and pass the two connectors Langfuse uses. `HTTP_INGRESS` is the AWS-managed connector that carries the worker's tool calls into the guest. `ALL_INGRESS` is a different named connector, not a wildcard, and Langfuse never passes it:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "lambda:RunMicrovm",
        "lambda:GetMicrovm",
        "lambda:CreateMicrovmAuthToken",
        "lambda:ResumeMicrovm",
        "lambda:SuspendMicrovm",
        "lambda:TerminateMicrovm"
      ],
      "Resource": "arn:aws:lambda:<region>:<account-id>:microvm-image:<image-name>"
    },
    {
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::<account-id>:role/<execution-role>"
    },
    {
      "Effect": "Allow",
      "Action": "lambda:PassNetworkConnector",
      "Resource": [
        "arn:aws:lambda:<region>:aws:network-connector:aws-network-connector:HTTP_INGRESS",
        "arn:aws:lambda:<region>:<account-id>:network-connector:<egress-connector-name>"
      ]
    }
  ]
}
```

See [Lambda MicroVM networking](https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html).

## Worker access to the MCP server [#langfuse-mcp]

The Assistant reaches Langfuse data through this instance's native [Langfuse MCP server](/docs/api-and-data-platform/features/mcp-server#set-up). There is no separate MCP process to install. The worker derives the endpoint from `NEXTAUTH_URL` as `{NEXTAUTH_URL}/api/public/mcp`.

Set the same public `NEXTAUTH_URL` on web and worker when the worker can reach that URL through DNS, TLS, and the load balancer. The MCP `Host` header then matches the web service and no allowlist is needed.

When it cannot, point the worker at the internal web URL and add that hostname to `LANGFUSE_MCP_ALLOWED_HOSTS` on web. This applies to Docker Compose service names, Kubernetes in-cluster services, and reverse proxies that rewrite `Host`. Published [`docker-compose.yml`](https://github.com/langfuse/langfuse/blob/main/docker-compose.yml) shares one `NEXTAUTH_URL` between both services and defaults it to `http://localhost:3000`, which inside the worker is not the web container, so Compose deployments need an overlay:

```yaml filename="docker-compose.mcp.yml"
services:
  langfuse-web:
    environment:
      LANGFUSE_MCP_ALLOWED_HOSTS: langfuse-web
  langfuse-worker:
    environment:
      NEXTAUTH_URL: http://langfuse-web:3000
```

```bash
docker compose -f docker-compose.yml -f docker-compose.mcp.yml up -d --force-recreate langfuse-web langfuse-worker
```

Recreate both services after changing these values. A restart does not re-interpolate environment variables.

## Kubernetes

The [Langfuse Helm chart](https://github.com/langfuse/langfuse-k8s) has no first-class Assistant values yet. Pass these variables through `langfuse.additionalEnv`, which applies to web and worker, and through `langfuse.worker.pod.additionalEnv` for the worker-only variables. For Bedrock, attach the workload role with `langfuse.serviceAccount.annotations`:

```yaml filename="values.yaml"
langfuse:
  additionalEnv:
    - name: LANGFUSE_IN_APP_AGENT_ENABLED
      value: "true"
    - name: LANGFUSE_AI_MODEL
      value: eu.anthropic.claude-opus-5
    - name: LANGFUSE_AI_AWS_BEDROCK_REGION
      value: eu-west-1
  worker:
    pod:
      additionalEnv:
        - name: QUEUE_CONSUMER_IN_APP_AGENT_RUN_QUEUE_IS_ENABLED
          value: "true"
        - name: LANGFUSE_IN_APP_AGENT_INTEGRITY_RUNNER_ENABLED
          value: "true"
  serviceAccount:
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::<account-id>:role/<langfuse-role>
```

The chart gives web and worker a single shared ServiceAccount, so on Kubernetes both services assume the same IAM role. Scope that role to Bedrock invoke and, if you run the sandbox, the MicroVM permissions above.

## Trace the Assistant in your own instance

Langfuse Cloud records its own Assistant into a Langfuse project, and self-hosted deployments can do the same. Set `LANGFUSE_AI_FEATURES_PROJECT_ID` on web and worker to the ID of a project on this instance:

```bash
LANGFUSE_AI_FEATURES_PROJECT_ID=<project-id>
```

Assistant turns and Ask AI completions then appear as traces in that project, under the environment `langfuse-in-app-agent` and tagged with the project the request came from. Langfuse writes them through the same internal ingestion path as any other data on the instance, so this needs no API keys and makes no outbound requests.

Leave the variable unset to record nothing. On self-hosted deployments it is the only control: the organization-level AI telemetry switch is Cloud-only.

<Callout type="warning">
  Use a project dedicated to this. Assistant traces contain the prompts, tool
  calls, and model output of every run, which includes data the Assistant read
  from your other projects. Anyone with access to the target project can read
  it.
</Callout>

`LANGFUSE_AI_FEATURES_PUBLIC_KEY`, `LANGFUSE_AI_FEATURES_SECRET_KEY`, and `LANGFUSE_AI_FEATURES_HOST` are separate and optional. They let Ask AI attach parse-outcome scores to its traces. They have no effect on the Assistant, which always uses its bundled system prompt when self-hosted.

## Queue and runtime knobs

These optional variables tune execution behavior:

| Variable                                                 | Description                                                                     |
| -------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `LANGFUSE_IN_APP_AGENT_RUN_QUEUE_PROCESSING_CONCURRENCY` | Concurrent Assistant runs on the worker. Defaults to `5`.                       |
| `LANGFUSE_IN_APP_AGENT_INTEGRITY_RUNNER_INTERVAL_MS`     | How often the integrity runner reconciles runs. Defaults to `900000`.           |
| `LANGFUSE_IN_APP_AGENT_MAX_ACTIVE_RUNS_PER_USER`         | Concurrent runs admitted per user on the web service. Defaults to `5`.          |
| `LANGFUSE_IN_APP_AGENT_MAX_ACTIVE_RUNS_PER_ORG`          | Concurrent runs admitted per organization on the web service. Defaults to `20`. |

## Troubleshooting

- **The Assistant is not visible.** Confirm `LANGFUSE_IN_APP_AGENT_ENABLED=true` on both web and worker, then recreate both services. Organization **AI Features** does not show the Assistant on its own.
- **Runs stay queued or time out.** Confirm the worker is running, shares Redis with the web service, and has `QUEUE_CONSUMER_IN_APP_AGENT_RUN_QUEUE_IS_ENABLED=true`.
- **Runs never reach a terminal state.** Enable `LANGFUSE_IN_APP_AGENT_INTEGRITY_RUNNER_ENABLED` on one worker so abandoned runs are reconciled.
- **Runs fail with `Error initializing agent`.** The worker could not connect to the MCP server. Confirm it can reach `{NEXTAUTH_URL}/api/public/mcp`. On Docker Compose the first symptom is `ECONNREFUSED` on loopback, followed by `MCP_CLIENT_CONNECT_FAILED`. A `403` with `Invalid Host header` instead means the worker reached web on a hostname that is not in `LANGFUSE_MCP_ALLOWED_HOSTS`. See [Worker access to the MCP server](#langfuse-mcp).
- **The UI reports that the model is not configured.** Set `LANGFUSE_AI_MODEL` on both services, plus `LANGFUSE_AI_API_KEY` when the provider is `anthropic`, then recreate both services.
- **Bedrock returns access denied or model not found.** Check the Region, Bedrock model access, and the invoke permissions in [step 2](#configure-the-model). An `AccessDeniedException` naming a `foundation-model` ARN in another Region means the role is scoped to the invoke Region only.
- **Sandbox tools are missing.** Expected when `LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER` is unset. Set `lambda-microvm` along with the image, execution role, Region, and egress connector.
- **File or bash tools fail in the sandbox.** These errors surface in the tool result in the UI rather than as worker error logs. Confirm that `lambda:PassNetworkConnector` covers both `HTTP_INGRESS` and your egress connector.
- **The image build fails.** Confirm Lambda MicroVMs are available in the Region, the AWS CLI supports `lambda-microvms`, the build role can read the artifact, and the caller has `iam:PassRole` on the build role.

# Langfuse Assistant

This page covers self-hosted infrastructure setup. For an introduction to the feature, see [Langfuse Assistant](/docs/langfuse-assistant).

Assistant runs are durable jobs. The web service admits and enqueues them, and the worker claims and executes them, so both need the same Postgres, Redis, and Langfuse AI model. Web calls the model directly for [Ask AI](/docs/observability/features/filter-search-bar#ask-ai) and conversation titles; the worker runs the Assistant itself. The sandbox is worker-only. The Assistant is available on all self-hosted plans and does not require an Enterprise Edition license key.

Configure the model, the sandbox, and worker MCP access first, then [turn the Assistant on](#turn-on-the-assistant). Every variable on this page is also listed in the [configuration reference](/self-hosting/configuration#langfuse-assistant).

<Callout type="info">
  The Langfuse Assistant is in public beta on self-hosted deployments, from
  version `>=v4.22.0`. The Langfuse Assistant is not covered by SemVer.
  Configuration may change between releases.
</Callout>

## Configure the model [#configure-the-model]

`LANGFUSE_AI_MODEL` sets the model used for the Langfuse Assistant. If `LANGFUSE_AI_SMALL_MODEL` is set, it is used for supplementary calls, such as chat naming, instead. Set both on the web and the worker service.

We recommend Claude Opus 5. The Assistant's system prompt and tool loop are developed against it, and it handles the long multi-step tool use the Assistant depends on. Other models work, and the `openai` provider accepts any OpenAI-compatible endpoint, but expect more variance in tool calling and instruction following.

`LANGFUSE_AI_PROVIDER` selects the backend. An unset provider resolves to `bedrock`. An incomplete configuration counts as unconfigured, and the UI then reports that the model is not configured.

| Variable                         | `bedrock` | `anthropic` | `openai` |
| -------------------------------- | --------- | ----------- | -------- |
| `LANGFUSE_AI_MODEL`              | required  | required    | required |
| `LANGFUSE_AI_SMALL_MODEL`        | optional  | optional    | optional |
| `LANGFUSE_AI_API_KEY`            | not used  | required    | required |
| `LANGFUSE_AI_BASE_URL`           | not used  | optional    | optional |
| `LANGFUSE_AI_EXTRA_HEADERS`      | not used  | optional    | optional |
| `LANGFUSE_AI_USE_RESPONSES_API`  | not used  | not used    | optional |
| `LANGFUSE_AI_AWS_BEDROCK_REGION` | optional  | not used    | not used |

Bedrock authenticates through the AWS credential chain rather than an API key. Set `LANGFUSE_AI_BASE_URL` to the full API base including `/v1`, such as `https://gateway.internal/v1`. `LANGFUSE_AI_EXTRA_HEADERS` takes a JSON object of header names and values; invalid JSON fails validation at boot.

<Tabs items={["Amazon Bedrock", "Anthropic Messages", "OpenAI-compatible"]}>

<Tab>

```bash
LANGFUSE_AI_PROVIDER=bedrock
LANGFUSE_AI_MODEL=eu.anthropic.claude-opus-5
LANGFUSE_AI_SMALL_MODEL=eu.anthropic.claude-haiku-4-5-20251001-v1:0
LANGFUSE_AI_AWS_BEDROCK_REGION=eu-west-1
```

Activate model access for these models in the AWS account you point Langfuse at. You can confirm access by running the same model from the Bedrock model catalog in the AWS console before configuring Langfuse.

IDs such as `eu.anthropic.claude-opus-5` are geo inference profiles (`eu.*`, `us.*`, `jp.*`) rather than on-demand foundation-model IDs, so use the profile ID as the model value. The Region is optional when the workload already runs in the Bedrock Region.

Langfuse resolves AWS credentials the same way the AWS CLI does, through the [default credential chain](https://docs.aws.amazon.com/sdkref/latest/guide/standardized-credentials.html): environment variables, then the shared config file, then the container or instance role. Prefer an ECS task role, an EC2 instance role, or IRSA on Kubernetes so both services pick up temporary credentials and you store no key. Grant invoke-only permissions:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": "*"
    }
  ]
}
```

</Tab>

## Sandbox

The sandbox backs the Assistant's file and code-execution tools. Set `LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER` on the worker:

| Sandbox            | Value            | Use for                            | Tools                                     |
| ------------------ | ---------------- | ---------------------------------- | ----------------------------------------- |
| AWS Lambda MicroVM | `lambda-microvm` | Production self-hosted deployments | Langfuse tools, files, and code execution |
| None               | unset            | Deployments that are not on AWS    | Langfuse tools only                       |

With no provider set, the Assistant still runs its Langfuse tools and the file and code-execution tools are unavailable.

<Callout type="warning">
  There is no non-AWS sandbox yet. For sandboxed execution on other platforms,
  let us know what support you need in [GitHub
  Discussions](https://github.com/orgs/langfuse/discussions).
</Callout>

`lambda-microvm` is not a single switch. It needs AWS resources you create yourself, an image you build in your own account, and five variables. Provider, image, execution role, and Region are required together, and a partial configuration fails at worker boot:

```bash
LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER=lambda-microvm
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_IMAGE_IDENTIFIER=arn:aws:lambda:<region>:<account-id>:microvm-image:<image-name>
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EXECUTION_ROLE_ARN=arn:aws:iam::<account-id>:role/<execution-role>
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_REGION=<region>
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EGRESS_NETWORK_CONNECTOR_ARN=arn:aws:lambda:<region>:<account-id>:network-connector:<egress-connector-name>
```

<Callout type="warning">
  Production isolation requires the egress network connector. Langfuse starts
  without it, but AWS then attaches its default `INTERNET_EGRESS` connector and
  sandboxed code reaches the public internet. An invalid connector ARN fails the
  MicroVM launch rather than falling back to internet egress. See [Lambda MicroVM
  networking](https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html).
</Callout>

### AWS prerequisites

Create these before configuring the worker:

| Resource                   | Purpose                                                         | Notes                                                                                                                                                                                                            |
| -------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S3 bucket                  | Holds the zip artifact that Lambda reads during the image build | Can be deleted after the build                                                                                                                                                                                   |
| MicroVM **build** role     | Lambda assumes it during `CreateMicrovmImage`                   | Trust `lambda.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`; allow `s3:GetObject` on the artifact and writes to the build CloudWatch log groups; no Langfuse database, application, or secret access |
| MicroVM **execution** role | The identity the MicroVM guest runs as                          | Trust `lambda.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`, and attach no policies                                                                                                                  |
| Security group             | Denies all guest traffic                                        | No ingress rules and no egress rules                                                                                                                                                                             |
| Subnets                    | Carry the egress connector                                      | Private or unrouted, with no default route to the internet                                                                                                                                                       |
| Connector operator role    | Creates and operates the network connector                      | Trust `lambda.amazonaws.com` and `network-connectors.lambda.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`                                                                                            |
| Egress network connector   | Leaves the guest without network access                         | Type VPC egress, associated with MicroVM compute, using the security group and subnets above                                                                                                                     |

The build role and the execution role are separate on purpose. User-provided sandbox code runs as the execution role, so it must not reach Langfuse databases, storage, or secrets.

### Build the MicroVM image

Langfuse does not publish a pullable MicroVM image. AWS builds it in your account from a zip artifact plus an Amazon Linux 2023 base image. You need Lambda MicroVMs in the Region, an AWS CLI with `lambda-microvms` support (2.36.1 is known to work), Docker, pnpm, zip, git, and a checkout of the Langfuse repository.

The caller that runs the script is a separate identity from the build role. It needs `s3:PutObject` on the artifact bucket, `lambda:CreateMicrovmImage`, `ListMicrovmImages`, `GetMicrovmImage`, `UpdateMicrovmImage`, and `iam:PassRole` on the build role. Without that `iam:PassRole`, `CreateMicrovmImage` returns `AccessDeniedException`.

Run [`build-microvm-image.sh`](https://github.com/langfuse/langfuse/blob/main/packages/in-app-agent-sandbox-runtime/build-microvm-image.sh) from the repository root:

```bash
export AWS_PROFILE=<profile>
export AWS_REGION=<region>
export S3_BUCKET=<artifact-bucket>
export MICROVM_IMAGE_NAME=langfuse-in-app-agent-sandbox
export LAMBDA_MICROVM_BUILD_ROLE_ARN=arn:aws:iam::<account-id>:role/<build-role>
export BASE_IMAGE_ARN=arn:aws:lambda:<region>:aws:microvm-image:al2023-1
export BASE_IMAGE_VERSION=0

bash packages/in-app-agent-sandbox-runtime/build-microvm-image.sh
```

These values can also live in `packages/in-app-agent-sandbox-runtime/.env`. On success the script prints `IMAGE_ARN`. Use it as `LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_IMAGE_IDENTIFIER`.

### IAM and network isolation [#iam-and-network-isolation]

Grant the worker permission to run the image, pass the execution role, and pass the two connectors Langfuse uses. `HTTP_INGRESS` is the AWS-managed connector that carries the worker's tool calls into the guest. `ALL_INGRESS` is a different named connector, not a wildcard, and Langfuse never passes it:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "lambda:RunMicrovm",
        "lambda:GetMicrovm",
        "lambda:CreateMicrovmAuthToken",
        "lambda:ResumeMicrovm",
        "lambda:SuspendMicrovm",
        "lambda:TerminateMicrovm"
      ],
      "Resource": "arn:aws:lambda:<region>:<account-id>:microvm-image:<image-name>"
    },
    {
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::<account-id>:role/<execution-role>"
    },
    {
      "Effect": "Allow",
      "Action": "lambda:PassNetworkConnector",
      "Resource": [
        "arn:aws:lambda:<region>:aws:network-connector:aws-network-connector:HTTP_INGRESS",
        "arn:aws:lambda:<region>:<account-id>:network-connector:<egress-connector-name>"
      ]
    }
  ]
}
```

See [Lambda MicroVM networking](https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html).

### Upgrading

Rebuild and republish the MicroVM image whenever you upgrade Langfuse, and treat the image as part of the deployment rather than a one-time setup step. Nothing checks that the image matches the worker, so a stale image surfaces as failing file or bash tools at run time rather than as an error at boot.

## Worker access to the MCP server [#langfuse-mcp]

The Assistant reaches Langfuse data through this instance's native [Langfuse MCP server](/docs/api-and-data-platform/features/mcp-server#set-up). There is no separate MCP process to install. The worker calls `{NEXTAUTH_URL}/api/public/mcp`.

Set the same public `NEXTAUTH_URL` on web and worker when the worker can reach that URL through DNS, TLS, and the load balancer. When it cannot, point the worker at the internal web URL and add that hostname to `LANGFUSE_MCP_ALLOWED_HOSTS` on web. This applies to Docker Compose service names, Kubernetes in-cluster services, and reverse proxies that rewrite `Host`.

Docker Compose shares one `NEXTAUTH_URL` between both services, so Compose deployments need an overlay:

```yaml filename="docker-compose.mcp.yml"
services:
  langfuse-web:
    environment:
      LANGFUSE_MCP_ALLOWED_HOSTS: langfuse-web
  langfuse-worker:
    environment:
      NEXTAUTH_URL: http://langfuse-web:3000
```

```bash
docker compose -f docker-compose.yml -f docker-compose.mcp.yml up -d --force-recreate langfuse-web langfuse-worker
```

Recreate both services after changing these values. A restart does not re-interpolate environment variables.

## Turn on the Assistant [#turn-on-the-assistant]

With the model, the sandbox, and MCP access in place, enable the Assistant on both the web and worker services:

```bash
LANGFUSE_IN_APP_AGENT_ENABLED=true
```

Unset or `false` hides the Assistant even when **AI Features** is enabled for the organization. Workers that have it set consume the Assistant run queue, so set it only on workers you want executing runs. An ingestion-only worker should leave it unset.

Then enable the feature for your organization:

1. Sign in as an organization owner or administrator.
2. Open organization **Settings** and enable **AI Features**.
3. Open the Langfuse Assistant in a project.

To verify, ask the Assistant to summarize a recent trace and confirm the run moves from queued to running to complete. If you configured a sandbox, ask it to write a file.

## Kubernetes

The [Langfuse Helm chart](https://github.com/langfuse/langfuse-k8s) has no first-class Assistant values yet. Pass these variables through `langfuse.additionalEnv`, which applies to web and worker. For Bedrock, attach the workload role with `langfuse.serviceAccount.annotations`:

```yaml filename="values.yaml"
langfuse:
  additionalEnv:
    - name: LANGFUSE_IN_APP_AGENT_ENABLED
      value: "true"
    - name: LANGFUSE_AI_MODEL
      value: eu.anthropic.claude-opus-5
    - name: LANGFUSE_AI_AWS_BEDROCK_REGION
      value: eu-west-1
  serviceAccount:
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::<account-id>:role/<langfuse-role>
```

The chart gives web and worker a single shared ServiceAccount, so on Kubernetes both services assume the same IAM role. Scope that role to Bedrock invoke and, if you run the sandbox, the MicroVM permissions above.

## Trace the Assistant in your own instance [#trace-the-assistant-in-your-own-instance]

Record the Assistant's own runs as traces in a project on this instance, which is useful for debugging it. Set `LANGFUSE_AI_FEATURES_PROJECT_ID` on web and worker to that project's ID:

```bash
LANGFUSE_AI_FEATURES_PROJECT_ID=<project-id>
```

Assistant turns and Ask AI completions then appear as traces in that project, under the environment `langfuse-in-app-agent` and tagged with the project the request came from. Langfuse writes them through the same internal ingestion path as any other data on the instance, so this needs no API keys and makes no outbound requests. Leave the variable unset to record nothing.

<Callout type="warning">
  Use a project dedicated to this. Assistant traces contain the prompts, tool
  calls, and model output of every run, which includes data the Assistant read
  from your other projects. Anyone with access to the target project can read
  it.
</Callout>

## Queue and runtime knobs

These optional variables tune execution behavior:

| Variable                                                 | Description                                                                     |
| -------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `LANGFUSE_IN_APP_AGENT_RUN_QUEUE_PROCESSING_CONCURRENCY` | Concurrent Assistant runs on the worker. Defaults to `5`.                       |
| `LANGFUSE_IN_APP_AGENT_MAX_ACTIVE_RUNS_PER_USER`         | Concurrent runs admitted per user on the web service. Defaults to `5`.          |
| `LANGFUSE_IN_APP_AGENT_MAX_ACTIVE_RUNS_PER_ORG`          | Concurrent runs admitted per organization on the web service. Defaults to `20`. |

  <AccordionItem value="init-agent">

      `ECONNREFUSED` on loopback, followed by `MCP_CLIENT_CONNECT_FAILED`. A
      `403` with `Invalid Host header` instead means the worker reached web on a

  </AccordionItem>

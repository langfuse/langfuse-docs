# Langfuse Assistant

This page covers self-hosted infrastructure setup. For an introduction to the feature, see [Langfuse Assistant](/docs/langfuse-assistant).

Assistant runs are durable jobs. The web service admits and enqueues them. The worker claims and executes them. Both services must use the same Postgres, Redis, and Langfuse AI model.

[Ask AI](/docs/observability/features/filter-search-bar#ask-ai) in the filter search bar uses this same instance-wide Langfuse AI model. It does not use the Assistant instance switch.

<Callout type="warning">
  We strongly recommend AWS Lambda MicroVM for production. File and
  code-execution tools require it. Running without a sandbox is a fallback, not
  the default path.
</Callout>

## Requirements

| Requirement           | What to set                                                                                                                                                                      |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Instance switch       | `LANGFUSE_IN_APP_AGENT_ENABLED=true` on web and worker. Unset or `false` hides the Assistant.                                                                                    |
| Organization gate     | An organization owner or admin enables **AI Features**. Required for the Assistant and for Ask AI.                                                                               |
| Langfuse AI model     | One instance-wide model: Amazon Bedrock (default) or Anthropic Messages. Set it on web and worker.                                                                               |
| Langfuse MCP          | Worker must reach this instance's MCP server. See [Langfuse MCP](#langfuse-mcp).                                                                                                 |
| Worker consumer       | `QUEUE_CONSUMER_IN_APP_AGENT_RUN_QUEUE_IS_ENABLED=true` on the execution worker. The code default is `false`.                                                                    |
| Sandbox (recommended) | `LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER=lambda-microvm` plus image, execution role, deny-all egress connector, and Region. Leave unset only as a fallback (Langfuse tools only). |

## Langfuse MCP [#langfuse-mcp]

The Assistant uses this instance's native [Langfuse MCP server](/docs/api-and-data-platform/features/mcp-server#set-up) for Langfuse tools. You do not install a separate MCP process. The worker derives the endpoint from `NEXTAUTH_URL` as `{NEXTAUTH_URL}/api/public/mcp`.

Set the **same public** `NEXTAUTH_URL` on web and worker when the worker can reach that URL (DNS, TLS, and hairpin through the load balancer). The MCP `Host` header then matches web, and you do not need `LANGFUSE_MCP_ALLOWED_HOSTS`.

`localhost` inside the worker is not the web service. Published [`docker-compose.yml`](https://github.com/langfuse/langfuse/blob/main/docker-compose.yml) shares one `NEXTAUTH_URL` with web and worker through a YAML anchor (`environment: &langfuse-worker-env`). The default is `http://localhost:3000`. A `.env` cannot give the two services different values. With that default, the worker logs `ECONNREFUSED` on loopback (`::1:3000` / `127.0.0.1:3000`), then `MCP_CLIENT_CONNECT_FAILED` / `Error initializing agent`.

When `NEXTAUTH_URL` is localhost or the worker cannot hairpin to the public URL, override the worker to the web service and allow that hostname on web. Recreate both services afterward (`docker compose up -d --force-recreate`); restart does not re-interpolate env.

```yaml
# docker-compose.mcp.yml — Compose overlay when NEXTAUTH_URL is localhost
services:
  langfuse-web:
    environment:
      LANGFUSE_MCP_ALLOWED_HOSTS: langfuse-web
  langfuse-worker:
    environment:
      NEXTAUTH_URL: http://langfuse-web:3000
```

```bash
docker compose -f docker-compose.yml -f docker-compose.mcp.yml up -d --force-recreate langfuse-web langfuse-worker
```

Kubernetes in-cluster service names, private workers with no hairpin, and reverse proxies that change `Host` need the same split: worker `NEXTAUTH_URL` is the internal web URL, and web `LANGFUSE_MCP_ALLOWED_HOSTS` is that exact hostname. See [self-hosted MCP setup](/docs/api-and-data-platform/features/mcp-server#set-up) and [`LANGFUSE_MCP_ALLOWED_HOSTS`](/self-hosting/configuration).

## Enable the Assistant [#enable-the-assistant]

Set this on **both** the web and worker services. Self-hosted instances show the Assistant only when the value is `"true"`. Unset or `"false"` hides it, even if **AI Features** is on.

```bash
# web and worker
LANGFUSE_IN_APP_AGENT_ENABLED="true"
```

This switch does not gate Ask AI or natural-language filters.

## Configure the model [#configure-the-model]

One instance-wide Langfuse AI model serves the Assistant, Ask AI, and natural-language filters. Set `LANGFUSE_AI_PROVIDER` to `bedrock` or `anthropic`. Unset defaults to `bedrock`.

These `LANGFUSE_AI_*` variables select the model provider. They are not the optional `LANGFUSE_AI_FEATURES_*` project used for Assistant observability.

If the model is unconfigured, the UI reports that you must set `LANGFUSE_AI_PROVIDER=anthropic` with `LANGFUSE_AI_MODEL` and `LANGFUSE_AI_API_KEY`, or set `LANGFUSE_AWS_BEDROCK_MODEL`.

### Amazon Bedrock [#amazon-bedrock]

Bedrock is the default when `LANGFUSE_AI_PROVIDER` is unset or `bedrock`. Set the model on **both** the web and worker services. Auth is the instance AWS credential chain or IRSA, not `LANGFUSE_AI_API_KEY`.

```bash
# web and worker
# LANGFUSE_AI_PROVIDER="bedrock"   # optional; unset is bedrock
LANGFUSE_AWS_BEDROCK_MODEL="eu.anthropic.claude-opus-4-8"
LANGFUSE_AWS_BEDROCK_SMALL_MODEL="eu.anthropic.claude-haiku-4-5-20251001-v1:0"
LANGFUSE_AI_AWS_BEDROCK_REGION="eu-west-1"
# LANGFUSE_AWS_BEDROCK_REGION="eu-west-1"   # deprecated alias
```

`LANGFUSE_AI_MODEL` and `LANGFUSE_AI_SMALL_MODEL` are Anthropic-only. If Bedrock is selected and `LANGFUSE_AI_API_KEY` or `LANGFUSE_AI_BASE_URL` are set, the app logs a warning and ignores them.

IDs such as `eu.anthropic.claude-opus-4-8` are geo inference profiles (`eu.*`, `us.*`, `jp.*`), not on-demand foundation-model IDs. Use the profile ID as the model value. Enable model access in Bedrock. Region is optional when the workload already runs in the Bedrock Region. Prefer `LANGFUSE_AI_AWS_BEDROCK_REGION`; `LANGFUSE_AWS_BEDROCK_REGION` is the fallback.

Prefer a workload role or IRSA so both services pick up temporary credentials from the [AWS SDK default credential chain](https://docs.aws.amazon.com/sdkref/latest/guide/standardized-credentials.html). Grant invoke-only permissions. Geo profiles invoke destination-Region foundation models, so a single-Region `foundation-model/*` ARN is not enough:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": "*"
    }
  ]
}
```

That is invoke-only access to models, not broader Bedrock administration. If you must scope `Resource`, include every destination Region the profile can invoke. See [Bedrock inference profile permissions](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html).

### Anthropic Messages [#anthropic-messages]

Set `LANGFUSE_AI_PROVIDER=anthropic` with a model and API key on **both** the web and worker services. Incomplete config is treated as unconfigured.

```bash
# web and worker
LANGFUSE_AI_PROVIDER="anthropic"
LANGFUSE_AI_MODEL="claude-opus-4-8"
LANGFUSE_AI_SMALL_MODEL="claude-haiku-4-5"   # titles; falls back to LANGFUSE_AI_MODEL
LANGFUSE_AI_API_KEY="sk-ant-..."
LANGFUSE_AI_BASE_URL="https://api.anthropic.com"   # optional origin; app appends /v1
```

`LANGFUSE_AI_BASE_URL` is optional. If unset, the SDK uses its default. Compatible Anthropic-protocol origins are fine. The app appends `/v1` if it is missing, so set an origin only.

## Worker queue [#worker-queue]

Set this on the worker that executes Assistant runs. Do not enable it on an ingestion-only worker.

```bash
# worker only
QUEUE_CONSUMER_IN_APP_AGENT_RUN_QUEUE_IS_ENABLED="true"
```

The worker schema defaults this to `"false"` so ingestion-only workers do not consume Assistant jobs. Docker Compose sets it to `true` for the bundled worker. Without the consumer, background runs die at queue timeout.

## Available sandboxes [#available-sandboxes]

Set `LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER` on the worker:

| Sandbox            | Value              | Use for                            | Tools                                     |
| ------------------ | ------------------ | ---------------------------------- | ----------------------------------------- |
| AWS Lambda MicroVM | `lambda-microvm`   | Production self-hosted deployments | Langfuse tools, files, and code execution |
| None               | unset              | Fallback                           | Langfuse tools only                       |
| Local Docker       | `dangerous-docker` | Local development                  | Langfuse tools, files, and code execution |

If you do not run Langfuse on AWS, you can still run the Assistant with Langfuse tools. There is no non-AWS sandbox yet. For sandboxed execution on other platforms, let us know what support you need in [GitHub Discussions](https://github.com/orgs/langfuse/discussions).

## AWS Lambda MicroVM sandbox [#aws-lambda-microvm-sandbox]

Use Lambda MicroVM for production self-hosted deployments:

```bash
LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER="lambda-microvm"
```

Langfuse does not publish a pullable MicroVM image. AWS builds the image **in your account** from a zip artifact plus an Amazon Linux 2023 base image.

You need:

- Lambda MicroVMs in the Region
- Docker, pnpm, zip, git, and an AWS CLI with `lambda-microvms` support (2.36.1 is known to work)
- Two IAM roles: a **build** role Lambda assumes, and a **caller** identity (your AWS profile or CI role) that uploads the artifact and creates the image
- The Langfuse repository, for [`packages/in-app-agent-sandbox-runtime/build-microvm-image.sh`](https://github.com/langfuse/langfuse/blob/main/packages/in-app-agent-sandbox-runtime/build-microvm-image.sh)

### Image build [#image-build]

Create an S3 bucket for the artifact and a MicroVM **build** role. Lambda assumes this role during `CreateMicrovmImage`. Trust `lambda.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`. Allow `s3:GetObject` on the artifact object and writes to the build CloudWatch log groups. Do not grant this role Langfuse database, application, or secret access.

The **caller** (the AWS profile or CI role that runs the script) needs `s3:PutObject` on the artifact bucket, `lambda:CreateMicrovmImage` / `ListMicrovmImages` / `GetMicrovmImage` / `UpdateMicrovmImage`, and `iam:PassRole` on the **build** role. Without that `PassRole`, `CreateMicrovmImage` fails with `AccessDeniedException`.

From the Langfuse repository root:

```bash
export AWS_PROFILE="<profile>"
export AWS_REGION="<region>"
export S3_BUCKET="<artifact-bucket>"
export MICROVM_IMAGE_NAME="langfuse-in-app-agent-sandbox"
export LAMBDA_MICROVM_BUILD_ROLE_ARN="arn:aws:iam::<account-id>:role/<build-role>"
export BASE_IMAGE_ARN="arn:aws:lambda:<region>:aws:microvm-image:al2023-1"
export BASE_IMAGE_VERSION="0"

bash packages/in-app-agent-sandbox-runtime/build-microvm-image.sh
```

You can also put these values in `packages/in-app-agent-sandbox-runtime/.env`.

The script builds the runtime, zips `Dockerfile`, `package.json`, and `dist`, uploads the zip, and creates or updates a Lambda MicroVM image (ARM_64, 512 MiB, hooks on port 5000). On success it prints `IMAGE_ARN`. Use that value as `LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_IMAGE_IDENTIFIER`.

### IAM permissions [#iam-permissions]

Create an **execution** role for the MicroVM. Trust `lambda.amazonaws.com` with `sts:AssumeRole` and `sts:TagSession`. Keep it empty of Langfuse database, S3, and secret permissions. User-provided sandbox code runs with this role.

For production isolation, create a VPC **egress** Lambda network connector that gives the guest no network:

1. A security group with no ingress and no egress.
2. Private or unrouted subnets (no default route to the internet).
3. An operator role that trusts `lambda.amazonaws.com` and `network-connectors.lambda.amazonaws.com`, with `sts:AssumeRole` and `sts:TagSession`.
4. A Lambda network connector of type VPC egress, associated with MicroVM compute, using that security group and those subnets.

See [Lambda MicroVM networking](https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html).

Grant the Langfuse worker permission to run the image, pass the execution role, and pass **only** `HTTP_INGRESS` (worker hooks) plus your deny-all connector. Do not allow `INTERNET_EGRESS` or `ALL_INGRESS`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "lambda:RunMicrovm",
        "lambda:GetMicrovm",
        "lambda:CreateMicrovmAuthToken",
        "lambda:ResumeMicrovm",
        "lambda:SuspendMicrovm",
        "lambda:TerminateMicrovm"
      ],
      "Resource": "arn:aws:lambda:<region>:<account-id>:microvm-image:<image-name>"
    },
    {
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::<account-id>:role/<execution-role>"
    },
    {
      "Effect": "Allow",
      "Action": "lambda:PassNetworkConnector",
      "Resource": [
        "arn:aws:lambda:<region>:aws:network-connector:aws-network-connector:HTTP_INGRESS",
        "arn:aws:lambda:<region>:<account-id>:network-connector:<egress-connector-name>"
      ]
    }
  ]
}
```

<Callout type="warning">
  Production isolation requires
  `LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EGRESS_NETWORK_CONNECTOR_ARN`.
  If that variable is unset, Langfuse omits `egressNetworkConnectors` and AWS
  attaches `INTERNET_EGRESS` (public internet in the guest). An invalid
  connector ARN fails `RunMicrovm` closed rather than falling back to the
  internet. See [Lambda MicroVM
  networking](https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html).
</Callout>

Set these on the worker. Provider, image, execution role, Region, and the deny-all egress connector are required together for an isolated sandbox:

```bash
LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER="lambda-microvm"
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_IMAGE_IDENTIFIER="arn:aws:lambda:<region>:<account-id>:microvm-image:<image-name>"
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EXECUTION_ROLE_ARN="arn:aws:iam::<account-id>:role/<execution-role>"
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_REGION="<region>"
LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EGRESS_NETWORK_CONNECTOR_ARN="arn:aws:lambda:<region>:<account-id>:network-connector:<egress-connector-name>"
```

## Without a sandbox [#without-a-sandbox]

If `LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER` is unset, the Assistant still runs with Langfuse tools. File and code-execution tools are unavailable. That is a fallback, not the intended production setup.

## Local Docker [#local-docker]

For local development you can run the sandbox against a local Docker daemon:

```bash
LANGFUSE_IN_APP_AGENT_SANDBOX_PROVIDER="dangerous-docker"
```

`dangerous-docker` is rejected when `NODE_ENV=production`. It is not a sandbox boundary for production workloads.

## Helm [#helm]

There is no first-class Assistant chart value yet. Pass these variables through `langfuse.additionalEnv` and `langfuse.worker.pod.additionalEnv`. Use IRSA via `langfuse.serviceAccount.annotations` when the model track is Bedrock.

```yaml
langfuse:
  additionalEnv:
    - name: LANGFUSE_IN_APP_AGENT_ENABLED
      value: "true"
    # Pick one model track. Unset LANGFUSE_AI_PROVIDER defaults to Bedrock.
    - name: LANGFUSE_AWS_BEDROCK_MODEL
      value: eu.anthropic.claude-opus-4-8
    - name: LANGFUSE_AI_AWS_BEDROCK_REGION
      value: eu-west-1
    # Or Anthropic Messages:
    # - name: LANGFUSE_AI_PROVIDER
    #   value: anthropic
    # - name: LANGFUSE_AI_MODEL
    #   value: claude-opus-4-8
    # - name: LANGFUSE_AI_API_KEY
    #   value: sk-ant-...
    # If the worker reaches web via an internal hostname, also set:
    # - name: LANGFUSE_MCP_ALLOWED_HOSTS
    #   value: langfuse-web
  worker:
    pod:
      additionalEnv:
        - name: QUEUE_CONSUMER_IN_APP_AGENT_RUN_QUEUE_IS_ENABLED
          value: "true"
  serviceAccount:
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::<account-id>:role/<langfuse-role>
```

## Organization opt-in [#organization-opt-in]

1. Sign in as an organization owner or administrator.
2. Open organization **Settings** and enable **AI Features**.
3. Open the Langfuse Assistant in a project.

## Verify [#verify]

1. Confirm the worker logs that it registered the in-app assistant queue consumer.
2. Send a simple request, such as asking it to summarize a recent trace. The run should move from queued to running and then complete.
3. Ask the Assistant to write a file. That confirms the Lambda MicroVM sandbox. If the sandbox provider is unset, file tools are unavailable by design.

## Queue and runtime knobs [#queue-and-runtime-knobs]

These optional variables tune execution behavior:

| Variable                                                 | Description                                               |
| -------------------------------------------------------- | --------------------------------------------------------- |
| `LANGFUSE_IN_APP_AGENT_RUN_QUEUE_PROCESSING_CONCURRENCY` | Concurrent assistant runs on the worker. Defaults to `5`. |

## Troubleshooting [#troubleshooting]

### The Assistant is not visible

Confirm `LANGFUSE_IN_APP_AGENT_ENABLED=true` is set on both the web and worker services, then recreate them. For Docker Compose, use `docker compose up -d --force-recreate`; restart does not re-interpolate env. Organization **AI Features** does not show the Assistant on its own.

### Runs remain queued or time out

Confirm the worker is running, shares Redis with the web service, and has `QUEUE_CONSUMER_IN_APP_AGENT_RUN_QUEUE_IS_ENABLED=true`. A queued run fails with a queue timeout when no worker claims it.

### Runs fail with Error initializing agent [#runs-fail-with-error-initializing-agent]

The worker could not connect to this instance's MCP server. Confirm the worker can reach `{NEXTAUTH_URL}/api/public/mcp`.

On Docker Compose, the first symptom is `ECONNREFUSED` on loopback (`::1:3000` / `127.0.0.1:3000`), then `MCP_CLIENT_CONNECT_FAILED`. Stock Compose shares `NEXTAUTH_URL=http://localhost:3000` with web and worker; `localhost` inside the worker is not the web container. Use the overlay in [Langfuse MCP](#langfuse-mcp) and recreate both services.

A `403` with `Invalid Host header` means the worker reached web on an internal hostname that is not in `LANGFUSE_MCP_ALLOWED_HOSTS`.

### The UI reports that the assistant model is not configured

For Bedrock, set `LANGFUSE_AWS_BEDROCK_MODEL` on both services. For Anthropic, set `LANGFUSE_AI_PROVIDER=anthropic` with `LANGFUSE_AI_MODEL` and `LANGFUSE_AI_API_KEY`. Recreate both services together (`docker compose up -d --force-recreate` on Compose).

### Bedrock returns access denied or model-not-found [#bedrock-returns-access-denied-or-model-not-found]

Check the Region, Bedrock model access, and `bedrock:InvokeModel` / `bedrock:InvokeModelWithResponseStream` on the workload role. Geo inference profiles (`eu.*` / `us.*` / `jp.*`) invoke a destination-Region foundation model while the SDK still calls `bedrock-runtime` in `LANGFUSE_AI_AWS_BEDROCK_REGION`. An `AccessDeniedException` on `arn:aws:bedrock:<other-region>::foundation-model/...` means the role's `Resource` list is scoped to the invoke Region only. Invoke-only `Resource: "*"` avoids that; if you scope ARNs, include every destination Region. See [Amazon Bedrock](#amazon-bedrock).

### Anthropic returns unauthorized or model-not-found

Confirm `LANGFUSE_AI_PROVIDER=anthropic`, `LANGFUSE_AI_MODEL`, and `LANGFUSE_AI_API_KEY` on both services. If you set `LANGFUSE_AI_BASE_URL`, use an origin only and let the app append `/v1`.

### Image build failed [#image-build-failed]

Confirm Lambda MicroVMs are available in the Region, the AWS CLI supports `lambda-microvms`, the **build** role can `s3:GetObject` the artifact, and `BASE_IMAGE_ARN` is `arn:aws:lambda:<region>:aws:microvm-image:al2023-1` with version `0`. The **caller** must also have `iam:PassRole` on that build role; otherwise `CreateMicrovmImage` returns `AccessDeniedException`.

### Sandbox tools are missing

Expected when the sandbox provider is unset. Set `lambda-microvm` and the image, execution-role, Region, and deny-all egress connector variables. Do not use `dangerous-docker` in production.

### File or bash tools fail in the sandbox [#file-or-bash-tools-fail-in-the-sandbox]

File and bash errors show up in the **tool result** in the UI, not as worker `error` lines. Worker info logs typically only show that a MicroVM session was created.

Confirm `PassNetworkConnector` allows `HTTP_INGRESS` and your deny-all egress connector — the named connector `ALL_INGRESS` is not a wildcard and is not what Langfuse passes. If `LANGFUSE_IN_APP_AGENT_SANDBOX_AWS_LAMBDA_MICROVM_EGRESS_NETWORK_CONNECTOR_ARN` is unset, AWS attaches `INTERNET_EGRESS` and the guest has public internet. See [IAM permissions](#iam-permissions).

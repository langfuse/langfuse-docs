# Topics

Topics runs on your existing Langfuse web and worker services, using Postgres, ClickHouse, Redis, and blob storage. Clustering runs inside the worker; the official worker image includes the required native module.

This page covers infrastructure configuration. For project setup and usage, see the [Topics guide](/docs/observability/features/topics).

## Enable Topics [#enable-topics]

On Langfuse v4.85.0 or later, set these environment variables on the indicated services and redeploy them. All three default to `false`.

| Set to `true`                                     | Service                                                                       | Purpose                                                          |
| ------------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `LANGFUSE_TOPICS_ENABLED`                         | Web and worker                                                                | Makes Topics available for project setup and enables processing. |
| `LANGFUSE_EVENTS_DISPATCH_ENABLED`                | Every worker that processes OpenTelemetry ingestion, plus the dispatch worker | Tracks when incoming traces are ready for live maps.             |
| `QUEUE_CONSUMER_EVENTS_DISPATCH_QUEUE_IS_ENABLED` | One worker service with events dispatch enabled                               | Starts the dispatcher and processes its queued jobs.             |

If you run a single worker service, set all three on that service and only `LANGFUSE_TOPICS_ENABLED` on web. In each project, map filters and sampling determine which recorded traces Topics analyzes.

## Configure model access [#model-access]

Create project or inherited organization [LLM connections](/docs/administration/llm-connection), then follow the [Topics setup steps](/docs/observability/features/topics#get-started) to select your models.

Both **web and worker** need access to the configured provider endpoints. Web validates the model configuration, and the worker processes traces and names topics. Use the deployment's existing [`ENCRYPTION_KEY`](/self-hosting/configuration/encryption#application-level-encryption) on both services so they can read the stored credentials.

If you use a private model endpoint or gateway, [allow outbound requests to that endpoint](/self-hosting/configuration/hardening#outbound-url-allowlists) from both services.

### Embedding compatibility

Choose a dimension count supported by your embedding model. Langfuse accepts **64–2,048 dimensions**, with **1,024** as the default. The model must return the configured number of dimensions.

## Configure storage retention [#storage-retention]

Live maps stage temporary transcripts under `events-dispatch/trace-transcript/` in the event-upload bucket. If your deployment sets `LANGFUSE_S3_EVENT_UPLOAD_PREFIX`, prepend its existing value to that path.

Configure a [blob storage lifecycle policy](/self-hosting/deployment/infrastructure/blobstorage) to expire objects at that path after three days, or set `LANGFUSE_EVENTS_DISPATCH_TRANSCRIPT_CLEANER_ENABLED=true` on the worker. The cleaner is disabled by default and needs permission to list and delete those objects.

For versioned storage or soft delete, configure lifecycle expiry for retained versions too.

<Callout type="warning">
  These temporary objects contain trace content. Trace and project deletion do
  not remove them; cleanup depends on the configured cleaner or lifecycle policy.
</Callout>

## Start processing

To verify live processing, create a live map filtered to a test workflow with 100% sampling. Send a matching trace with a recorded model conversation and check that its summary appears after the readiness delay and processing.

## Tune worker load [#worker-load]

The worker runs up to 20 per-trace jobs concurrently per queue shard by default. Set `LANGFUSE_TOPICS_TRACE_QUEUE_PROCESSING_CONCURRENCY` only if you need to tune this, for example to stay within provider rate limits.

Clustering consumes worker CPU and memory too. Allow headroom alongside ingestion and evaluation jobs; see [sizing and scaling](/self-hosting/configuration/scaling) for worker deployment options.

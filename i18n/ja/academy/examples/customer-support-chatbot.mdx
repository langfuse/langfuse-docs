# カスタマーサポートチャットボット

<Callout type="info">
  これは [Langfuse Academy](/academy/japan) の概念を説明するための例です。
</Callout>

## 背景

ある SaaS 企業が、カスタマーサポートのチャットを自動化したいと考えています。
現在はサポートチームがすべての会話に応答しており、チケットシステムには何年分もの解決済みチケットが蓄積されています。
ボットは会社の名前で顧客に話すことになるため、悪い回答は 1 件の会話にとどまらない損害を与えます。顧客はサポート全体への信頼を失うからです。

このリスクがあるため、いきなり顧客向けにリリースする選択肢はありません。
代わりに、3 つのフェーズに分けて展開し、それぞれのフェーズで次に進むための確信を積み上げます。

| フェーズ      | 稼働しているもの                                           | 次のフェーズへのゲート                                                                                                     |
| ------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 1. オフライン | なし。エージェントは開発中                                 | サポートチームが使いたいと思える水準の下書きができること                                                                   |
| 2. 社内       | エージェントが返信を下書きし、サポートチームが編集して送信 | 下書きと実際に送信された返信の差が、チケットのカテゴリを通じて小さいままであり、サポートチームからの定性的な評価も良いこと |
| 3. 顧客向け   | ボットが顧客に直接応答する                                 | なし。ここが最終目標であり、このフェーズではエージェントを継続的に改善し続ける                                             |

この段階的なアプローチによって、多くのリスクを抑えながら、本番のシグナルを早い段階で得られます。

## フェーズ 1: 最初のエージェントを作る

サポートチームに社内向けエージェントを実際に使ってもらうには、最初のバージョンの時点で彼らにとって有用である必要があります。
そこに到達するために、すでに手元にある解決済みチケットの豊富な過去データを活用できます。合成データの生成は不要です。

<Callout type="info">

各実行は次の方法で採点します。

評価器のスコアが十分に良く、手動レビューの結果も良ければ、エージェントをサポートチケットシステムに載せます。

## フェーズ 2: 社内展開

このフェーズでは、届いたチケットごとにエージェントが返信を下書きし、サポートチームのメンバーがそれを使い、送信前に編集できます。
エージェントの下書きと、メンバーが実際に送信した内容の差分は、非常に信頼できる [ユーザーシグナル](/academy/japan/monitoring#user-feedback) として使えます。

もう 1 つ、より明示的なユーザーシグナルとして、下書きに対する良い・悪いのボタンがあります。チームはそこに書き込みのフィードバックを残すこともできます。

<AnnotatedLoopJa
  ariaLabel="フェーズ 2 のループ: 下書きと送信済み返信の差分に駆動され、全体が稼働している"
  stations={{
    trace: { note: "すべての下書きをトレースする" },
    monitor: { note: "すべてのトレースに edit_type" },
    dataset: { note: "大きく編集された下書きが新しいアイテムに" },
    change: { note: "繰り返される編集パターンへの対処" },
    eval: { note: "リリース前にデータセットを回し直す" },
  }}
/>

どちらのシグナルも、下書きの [トレース](/academy/japan/tracing#anatomy-of-a-trace) に [スコア](/docs/evaluation/scores/overview) として記録されます。

<EvaluatorBlockJa
  evaluators={[
    {
      name: "edit_type",
      type: "LLM-as-a-Judge",
      check: (
        <>
          人手による編集を <code>none</code>、<code>tone</code>、{" "}
          <code>corrected</code>、<code>added</code> に分類します
        </>
      ),
      returns: "カテゴリ。トレースに付与",
      details: (
        <>
          下書きと送信された返信を比較する判定器です。<code>tone</code>{" "}
          はメンバーが言い回しを変えたが内容は保った場合、
          <code>corrected</code> は誤りが削除または修正された場合、
          <code>added</code>{" "}
          は下書きは残したうえで不足していた情報が追加された場合を指します。
          言い換えと内容の変更を見分けるには両方のテキストを読む必要があるため、
          判定器でなければなりません。他の判定器と同じく、これも最初は未検証の状態です。下書きと送信された返信のサンプルに手でラベルを付け、
          <a href="/academy/japan/evaluate/writing-evaluators#validate-the-judge">
            判定器が自分と同じように分類するかを確認
          </a>
          してください。
        </>
      ),
    },
    {
      name: "human_feedback",
      type: "人手",
      check: "下書きへの良い・悪いのボタン。任意で書き込みのフィードバック",
      returns: "二値とコメント。トレースに付与",
      details: (
        <>
          チケットシステムのボタンから直接記録され、評価器は不要です。クリックそのものがスコアを書き込みます。書き込まれたコメントは、差分だけでは得られない文脈を与えてくれます。
        </>
      ),
    },
  ]}
/>

スコアの悪いトレースは、その後に確認し、改善し、まだカバーされていなければデータセットに追加できます。
その進め方の 1 つが [エラー分析](/academy/japan/monitoring/error-analysis) のプロセスです。

ループを 1 周する例はこうなります。
[モニタリング](/academy/japan/monitoring#metrics-and-signals) で、`troubleshooting` カテゴリの `corrected` 下書きが急増していることが見えます。
トレースを見ると、ヘルプ記事のインデックスが古いために、エージェントが古いエクスポートダイアログを参照し続けていると分かります。
インデックスを更新し、`troubleshooting` データセットを回し直して修正を確認すると、`corrected` 下書きの割合が下がります。
ここから新しい評価器は生まれません。インデックスが古いことは [一度きりの修正](/academy/japan/evaluate/choosing-what-to-evaluate#fix-first) であって、追跡し続ける失敗モードではないからです。

編集される下書きの割合は、時間とともに下がっていくはずです。
すべてのチケットカテゴリで下書きがほぼ手を入れられずに送られるようになれば、エージェントは顧客に向き合う準備ができています。

## フェーズ 3: 顧客向けの展開

ボットが顧客に直接応答するようになると、フェーズ 2 を駆動していたシグナルは消えます。顧客が見る前に誰も返信を編集しないからです。
代わりに、学習と改善を続けるための暗黙的なユーザーシグナルをいくつか導入します。

<Callout type="info">
  いきなり全面的に自動化するのではなく、フェーズ 2 のゲートを通過した依頼
  カテゴリだけを自動化し、残りはもうしばらくサポートチームを通す、という
  やり方もあります。
</Callout>

<AnnotatedLoopJa
  ariaLabel="フェーズ 3 のループ: 人手の編集ではなく、暗黙的なユーザーシグナルに駆動される"
  stations={{
    trace: { note: "すべての顧客との会話" },
    monitor: { note: "ユーザーシグナルとリスクの監視" },
    dataset: { note: "良くなかった会話が新しいアイテムに" },
    change: { note: "モニタリングで見えたものへの対処" },
    eval: { note: "リリース前にデータセットを回し直す" },
  }}
/>

顧客がサポートチャットを評価してくれることはまれなので、主眼は暗黙的なユーザーシグナルを集めることに置きます。

<EvaluatorBlockJa
  evaluators={[
    {
      name: "handoff_requested",
      type: "LLM-as-a-Judge",
      check: "顧客が有人対応を求めたことを検出します",
      returns: "二値。トレースに付与",
      details: (
        <>
          顧客は自由な文章で有人対応を求めるため、コードベース評価器が一致を取れる対象がありません。トレースを採点することで、顧客がボットを見限ったまさにそのターンに印が付きます。
        </>
      ),
    },
    {
      name: "question_repeated",
      type: "LLM-as-a-Judge",
      check: "顧客が同じ質問を言い換えていることを検出します",
      returns: "二値。トレースに付与",
      details: (
        <>
          <a href="/academy/japan/monitoring#user-feedback">暗黙的フィードバック</a>{" "}
          の一種です。顧客が同じことを繰り返すのは、前の回答が届かなかったことを意味します。言い換えと追加の質問を見分けられるのは、会話を読む判定器だけです。
        </>
      ),
    },
    {
      name: "session_outcome",
      type: "LLM-as-a-Judge",
      check: "会話がどう終わったかを分類します",
      returns: "カテゴリ。セッションに付与",
      details: (
        <>
          会話が終了したときに実行され、<code>resolved</code>、{" "}
          <code>abandoned</code>、<code>handed_off</code>{" "}
          のいずれかに分類します。3 つの終わり方はボットの性能にとってそれぞれ別の意味を持ち、かつ互いに排他的なので、
          <a href="/academy/japan/evaluate/writing-evaluators#binary-verdicts">
            重なり合う二値評価器を複数用意するのではなく、カテゴリ評価器を 1 つ
          </a>
          にしています。結果は会話全体に属するものなので、トレースではなくセッションに対して採点します。
        </>
      ),
    },
  ]}
/>

人手がループから外れたので、評判を損ないうる挙動がないかをすべての返信について監視します。
この 2 つの評価器は、観測された失敗ではなく [絶対条件](/academy/japan/evaluate/choosing-what-to-evaluate#goals-and-hard-constraints) から来ています。どちらも一度も検知したことがありませんが、初日から存在します。
これらは何かをブロックするものではありません。送信済みの返信に印を付け、チームが顧客へすばやくフォローアップできるようにするものです。

<EvaluatorBlockJa
  evaluators={[
    {
      name: "data_leak",
      type: "LLM-as-a-Judge",
      check: "返信が、この顧客以外に関するデータを明かしていないか?",
      returns: "二値。トレースに付与",
      details: (
        <>
          <a href="/academy/japan/evaluate#reference-based-vs-reference-free">
            参照なし
          </a>{" "}
          なので、期待出力なしで本番のすべての返信に対して実行できます。どんな言い回しであれ個人データを認識するには言語理解が必要なため、
          LLM-as-a-Judge を使います。
        </>
      ),
    },
    {
      name: "out_of_scope_help",
      type: "LLM-as-a-Judge",
      check:
        "返信が、引き継ぎではなく返金・割引・約束を提示していないか?",
      returns: "二値。トレースに付与",
      details: (
        <>
          これも参照なしで、本番のすべての返信に対して実行します。キーワードチェックではなく判定器を使うのは、約束の言い方が無数にあるからです。
          「来月には対応します」には禁止語が 1 つも含まれていません。
        </>
      ),
    },
  ]}
/>

これらのシグナルがそろえば、エージェントを継続的に改善する良い体制になります。
良くなかった会話が表に出て、改善され、データセットアイテムになり、構造的にテストできるようになります。
チームはこの体制を使って、より新しい/安い/速いモデルを安全に試し、デプロイするかどうかを根拠を持って判断することもできます。

## まとめ

顧客に直接向き合う自動化は、リスクの高さゆえに立ち上がらないことがよくあります。
この例は、それを現実的に実現するためのベストプラクティスを、継続的な学習と改善を前提に整理したものです。

[他の例](/academy/japan/examples) や [Academy](/academy/japan) も参照してみてください。

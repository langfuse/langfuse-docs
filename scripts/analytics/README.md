# Use-case page analytics

This implements traffic, next-action, CTA exposure, content-interest, and completed-conversion tracking for the three use-case landing pages. The route registry remains the source of truth for which pages receive tracking.

## Dashboards

These dashboards were created in the Main project (7132):

- [Traffic and next steps](https://eu.posthog.com/project/7132/dashboard/942720): visitors and pageviews, daily visitors, first next destination per page visit, benefits opened, stories, integrations, resources, and gateway/hooks selections.
- [CTA visibility and clicks](https://eu.posthog.com/project/7132/dashboard/942721): exposed visitors, exposed clickers, placement CTR, and all clicks including quick activations.
- [Completed conversions](https://eu.posthog.com/project/7132/dashboard/942723): page visits, next destinations, CTA placements, and coding setup paths leading to completed signup or accepted sales inquiries.

Definitions and remote IDs are in [use-case-dashboards.json](./use-case-dashboards.json). These are existing dashboards: update the recorded IDs when changing the definitions instead of creating duplicates.

All source-page queries filter to `$host = langfuse.com`. Preview and localhost traffic is excluded. SQL tables use a fixed rolling 30-day window; their date ranges are in the SQL, not controlled by the dashboard date picker. Native trend and funnel queries use their date picker.

**Deployment requirement:** the dashboard objects are live, but new `use_case:*` and `sales:inquiry_completed` data requires deploying the website changes. At setup on September 9, 2026, these pages had preview traffic only. Empty production charts at that point did not mean the tracking had been deployed or that visitors never clicked.

## Events and dimensions

| Event                     | Trigger                                                                                                                                                   |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `$pageview`               | Once on initial load and once per pathname change; SDK automatic pageview capture is disabled to avoid duplicates.                                        |
| `use_case:page_viewed`    | A use-case page is mounted and PostHog is ready. Path switches do not create another page view.                                                           |
| `use_case:action_viewed`  | At least 50% of a link/card intersects the viewport for one continuous second while the document is in the foreground. Once per placement per page visit. |
| `use_case:action_clicked` | One anchor activation, including keyboard, modifier, middle-button, and whole-card clicks.                                                                |
| `use_case:benefit_opened` | An explicit accordion opening; excludes the initially open benefit.                                                                                       |
| `use_case:path_selected`  | An explicit gateway/hooks change, including keyboard changes; excludes the initial/default selection.                                                     |
| `sales:inquiry_completed` | Marketo's success callback, once per form instance. No form values or contact details are sent in this event.                                             |
| `cloud_signup_complete`   | Existing server-side Cloud completion event. No synthetic signup event is generated by the website.                                                       |

Common page dimensions: `use_case` (`chat_agents`, `coding_agents`, `workflow_automation`), `page_path`, `page_view_id`, `page_version=v1`, and optional `setup_path=gateway|hooks`.

Action dimensions: `section`, `action`, `item`, `placement_id`, `destination`, and `destination_group`. The stable placement ID contains the use case, section, action, item, and setup path. Queries and free-form labels are excluded from destination values; paths and anchors are retained. Integration labels distinguish chips that share a destination, such as Python and TypeScript.

Sections: `hero`, `benefits`, `customer_stories`, `integrations`, `resources`, `closing_cta`, `navigation`, `footer`, and fallback `content`. Source sections are explicit data attributes. Both Get Demo and Talk to sales map to `talk_to_sales` when linking to the sales form.

Destination groups: `signup`, `sales`, `docs`, `stories`, `integrations`, `resources`, `image`, and `other`. Next-destination reporting uses the first outbound click in a page visit and excludes image zoom and same-page links. Content-interest reports include all relevant clicks.

## Placement CTR

The denominator is distinct people with a qualifying exposure. The numerator is distinct people with a later click on the same placement in the same page visit. The query pairs records by person, page visit, and placement before deduplicating people. A click before the one-second threshold remains an action click with `was_exposed=false`; it is not treated as an impression or included in exposed CTR.

Hidden coding panels, invisible accordion sizing copies, disconnected elements, and background tabs do not qualify. Gateway and hooks placements are separate. Scrolling out and back in does not duplicate an exposure within a page visit.

## UTM convention and conversion handoff

Use standard UTMs for inbound campaigns, for example:

```text
https://langfuse.com/chat-agents?utm_source=newsletter&utm_medium=email&utm_campaign=use_cases_2026_09&utm_content=chat_agents
```

Existing acquisition UTMs are preserved. Internal actions use separate parameters:

```text
/cloud?lf_use_case=coding_agents&lf_section=hero&lf_action=start_free&lf_setup_path=hooks
/talk-to-us?lf_use_case=chat_agents&lf_section=closing_cta&lf_action=talk_to_sales
```

Only signup and sales destinations receive these parameters. Docs, stories, and integration URLs remain clean; their source is recorded on the click event. The region selector forwards parameters and fragments on ordinary clicks, new-tab clicks, and copied region links.

A validated, 30-minute sessionStorage record carries the latest use-case action through same-tab intermediate pages. Direct inbound `lf_*` parameters take precedence. This record is best-effort: blocked storage does not prevent navigation or form submission. It is not a replacement for PostHog person identity or campaign attribution.

## Completion and attribution limits

The completion funnels join the existing PostHog person identity across the website and Cloud. Both clients currently use the same project's cookie persistence; the website explicitly enables cross-subdomain cookies, and Cloud identifies the user after authentication. Historical joined website visits and successful signups were verified in the project. Cross-device visits, blocked analytics, and missing identity cannot be reliably joined.

Signup funnels use a 14-day window. The current Cloud `cloud_signup_complete` implementation covers **EU and US only**. Region links for Japan and HIPAA still preserve attribution, but the dashboards do not claim completed-signup coverage for those regions. No Cloud code was changed.

Sales funnels use a 1-day window and the accepted Marketo submission event, not a CTA click or form load. Named source properties are available where the validated URL/session attribution survives. Person-based funnels can also connect intermediate docs/story/integration visits without rewriting those links.

These funnels describe observed associations, not causal lift or mutually exclusive marketing attribution. A recent visitor may still convert within the remaining window.

## Validation

Run:

```sh
node --test scripts/test-use-case-analytics.mjs
pnpm exec tsc --noEmit --pretty false
node scripts/copy_md_sources.js
node scripts/check-h1-headings.js
git diff --check
```

The browser fixture mocks PostHog; tests send no production events and submit no real sales forms. It checks exposure thresholds, hidden content, fast and modifier clicks, whole-card activation, path changes, URL preservation, attribution expiry, and successful-form-only reporting. The local rendered pages and all four regional link destinations were also checked.

After deployment, verify the six new event names in PostHog live events, then confirm production host filters and the first real Marketo/Cloud completion paths. Empty dashboards before deployment are expected. Do not send synthetic production signups or sales inquiries for validation.
